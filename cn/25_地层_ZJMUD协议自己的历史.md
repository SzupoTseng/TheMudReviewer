# 第十四篇　地层学：ZJMUD 协议自己的历史

> 第八到十三篇挖了 LPMud、MudOS、FluffOS、LDMud、DGD、CD 的历史，
> 却漏掉了本书真正的主角——**ZJMUD 这套协议自己**。
>
> 这不是疏忽，是因为它看起来没有历史可挖：没有 ChangeLog、没有版本标签、
> 没有 RFC、没有作者留下任何说明。
>
> **但它有地层。** 三个方言世代（第三篇）、三个握手世代（附录 F.2）、
> 客户端里的死码（§005）、header 里被注解掉的区块——
> 这些都是沉积物，而沉积物是可以断代的。
>

## 079　三份 header 的地层 — 一次断代

**标签**：`#地层学` `#断代` `#可重跑量测` `#方言` `#考古`
**证据等级**：🟢 可重跑量测（17 份封存的 `include/zjmud.h` 逐份比对，方法附于 §082）

**起源**：§005 说 `include/zjmud.h` 是「这个项目最幸运的发现」——
27 个带中文注解的宏。
但当时只读了**一份**（`LPMud-Name`）。

**17 份封存里有 17 份 header。把它们并排，会看到完全不同的东西。**

**技术内核**：先看那份被读了整本书的文件，它的结构其实很奇怪。

```
  1–10   #include、ZJKEY、服务器地址
 11–128  /*  ← 一个 118 行的注解区块，里面有 97 个 opcode 定义
    128  */
    129  //指? MUD转?协?          ← 乱码（见 §082）
 131–133  //#define ZJKEY … （被注解掉的旧常数）
 135–     #define ESA "\x1b" … ← 25 个 opcode 定义，活跃
```

**一个文件里有两套定义：97 个被注解掉的，25 个活跃的。**

直觉会说「旧版被注解掉、新版活着」。**量一下就知道不是。**

| | 注解区块 | 活跃区块 |
|---|--------:|--------:|
| opcode 定义数 | **97** | **25** |
| 只在这一区出现 | **71** | **0** |
| 两区都有 | 25 | 25 |

**活跃区是注解区的严格子集——它没有任何新东西。**

所以那不是「升级」，是**缩减**：有人拿到一份 97 个码的 header，
把整份注解掉，然后在下面重新打了内核的 25 个。

### 那 97 个是谁的？

把注解区块里的宏**按名称前缀**分类：

| 前缀 | 数量 | 内容 |
|------|-----:|------|
| **`XY`** | **47** | 商城、背包、储物袋、副本、综合属性、人物面板…… |
| `ZJ` | 25 | **内核**（房间、出口、描述、对象、按钮、属性条……） |
| `XJ` | 5 | 综合属性样式一～四、体力 |
| `KILL` | 4 | 战斗技能、开始、结束、清场 |
| **`DMJH` / `DMZ` / `DM`** | **10** | 查看自身、判断界面、更改界面…… |
| `SYS` | 2 | 系统 |
| 其他 | 4 | — |

**`DMJH` = 大梦江湖。**

于是有了一个可以直接验证的假设：**去看大梦江湖自己的 header。**

### 决定性的比对

同一支脚本扫四份封存的 `include/zjmud.h`：

| 封存 | 活跃定义 | 注解掉 | 活跃区的前缀分布 |
|------|--------:|------:|-----------------|
| **`damengjianghu`（大梦江湖 新协议版）** | **97** | **0** | **XY 47 · ZJ 25 · XJ 5 · KILL 4 · DMJH 4 · DMZ 4 · 其他 4 · SYS 2 · DM 2** |
| `LPMud-Name`（江湖论剑） | 25 | **97** | ZJ 25（＋SYS） |
| `zhijianxing`（执剑行 7.0） | 25 | 0 | ZJ 23 · SYS 2 |
| `duobaojianghu`（夺宝江湖） | 23 | 0 | ZJ 21 · SYS 2 |
| `xiaoaojianghu`（笑傲江湖） | 20 | 0 | ZJ 18 · SYS 2 |

**第一列与第二列的前缀分布一模一样。**

> **江湖论剑那个 118 行的注解区块，就是大梦江湖的 `zjmud.h`。**

而其他三份封存**只有 ZJ 内核，一个扩充码都没有**。

### 地层的形状

```
┌─────────────────────────────────────────────┐
│ 扩充层  XY 47 · XJ 5 · KILL 4 · DM* 10 · …   │  只有大梦江湖线
│         （带字母的码全在这一层）                │  ← 江湖论剑把它整层注解掉
├─────────────────────────────────────────────┤
│ 内核层  ZJ 18–25 ＋ SYS 2                     │  17 份封存全部都有
└─────────────────────────────────────────────┘
```

### 方向：谁先谁后

§050 用 Jaccard 量血缘时说过，结构相似度**说不出谁先谁后**，方向要靠别的证据。
这里有三条，而且互相印证：

| 证据 | 指向 |
|------|------|
| **内核层在 17 份封存全部出现，扩充层只在一支** | 内核较早——**普世的东西通常是先有的** |
| **活跃区是注解区的严格子集（添加 0 个）** | 这是一次**缩减**，不是升级 |
| **扩充层的前缀是特定 lib 的名字**（`DMJH`、`XY`、`XJ`） | 扩充是**由特定 lib 加上去的**，不是内核规格的一部分 |

**所以江湖论剑不是「还没升级」，是「收到了扩充版然后退回内核」**——
它是这条演化在线的一份**过渡标本**：
扩充层完整地保存在它体内，但没有被激活。

**解决的痛点**：这个量测解了一个本书一直含糊带过的问题——
§005 的表写「大梦江湖（新协议）定义 101、实际使用 81」，
但没说**那 101 个是从哪来的、跟内核是什么关系**。

现在知道了：**扩充层是加在内核层上面的，而且加它的人在宏名里签了名。**

**踩过的坑（本项目的方法论）**：本书读了 `zjmud.h` 整整六篇（第二、三篇），
却**从来没有把 17 份的同一个文件并排比对过**。

原因很平凡：`LPMud-Name` 是唯一以文件树形式存在的封存（其余都是映像），
所以它「最方便读」，于是它变成了缺省样本。

**而缺省样本恰好是最不典型的那一份**——
17 份里只有它有那个注解区块。

> **教训**：当一批样本里有一份特别好取用，要特别小心它是不是典型。
> §050 的老手视角说「先画分布再定门槛」，
> 这里的版本是：**先看全部，再挑一份细读。**

**优点 / 罩门**：这个方法的优点是极便宜——
一支三十行的脚本扫 17 份索引，不必解开任何映像。
罩门是它只看**宏定义**，看不到实际发送点；
一个 lib 可以定义了却不用（§009 那条「定义 ≠ 使用」在这里同样适用）。
**附录 F.3 的实测 opcode 分布就是这个罩门的补偿**——
它量的是线路上真的出现了什么。

**效益**：两份证据合起来，才是完整的图：

| | header 定义（本节） | 线路实测（附录 F.3） |
|---|------------------|-------------------|
| 大梦江湖 | 97 个，含 XY/XJ/KILL/DM 全层 | **`111 234 517 604 605` —— 5 个扩充码，全 17 份里只有它送** |
| 其他 lib | 只有内核 | 只送内核码（`000 002 003 004 005 006 012 021 022`） |

**定义与使用互相印证：扩充层确实只活在那一支上。**

> 💡 君之一席话
> **当一批样本里有一份特别容易读，它往往就是被过度依赖的那一份**——而过度依赖的样本如果刚好不典型，你的整套结论会偏，而且偏得很难察觉。

> 🔍 老手视角──真正的门道
> 这一节做的事叫**同档跨样本比对**——把同一个文件名在 N 份样本里的内容并排。它便宜到不合理，却几乎没有人做，因为直觉会觉得「我已经读懂这个文件了」。但读懂一份和读懂一批是两回事：**一份告诉你它是什么，一批告诉你它在变什么。** 这个技巧在很多场合都成立——比对同一个设置档在十台机器上的差异（找出漂移）、同一个 schema 在各服务里的版本（找出不一致）、同一份 vendored 函数库在各项目里的内容（找出谁改过）。可落地的做法：**接手任何有「多份相似副本」的系统时，第一天就写一支「同名文件跨副本 diff」的脚本**。它产出的清单就是这个系统真正的变异点地图，而那张地图通常没有人画过。

## 080　扩充层的内部结构 — 五个前缀就是五次扩充

**标签**：`#扩充方言` `#命名空间` `#UI协议` `#死码` `#演化痕迹`
**证据等级**：🟢 可重跑量测（`damengjianghu` 与 `LPMud-Name` 的 header 逐条分类）

**起源**：§079 把扩充层当成一整块。**它不是。**
五个前缀代表至少五批不同的人、在不同时间加上去的东西，
而且它们的**设计品味明显不同**。

**技术内核**：把扩充层按前缀拆开看。

### `XY` 层（47 个）— 一整套图形化接口

这是最大的一批，内容是**完整的 App 式 UI**：

| 群组 | opcode | 内容 |
|------|--------|------|
| 商城 | 343–345 | 元宝数量、商城类型、商场物品 |
| 背包／储物袋 | 346–350 | 背包物品／文本、储物袋物品／文本 |
| 副本 | 270–272 | 副本、副本文本、副本列表 |
| 综合属性 | 291–293、296–297 | 标题、选项、文本 |
| 人物面板 | 417–421 | 名称、描述、按钮 ×3 |
| 战斗 | 511–515 | 加敌、加友、减敌、减友、描述 |
| 列表 | 211–215、217 | 通用列表槽 |
| 其他 | 10a、11a、130、308–311、331… | 跑马灯、好友提示…… |

**这一层的设计哲学和内核层完全不同。**

内核层（`ZJ`）的码是**语意性**的：房间标题、出口、描述、对象。
**`XY` 层的码是版面性**的：`XYBEIBAO`(背包物品) / `XYBBTEXT`(背包文本) /
`XYBEIBAOT`(背包文本2) —— **同一个面板的不同槽位各占一个 opcode。**

> 这是一个很清楚的信号：**内核层是为「文本游戏加标记」设计的，
> `XY` 层是为「一个有固定版面的 App」设计的。**
> 两者中间隔着一次产品形态的改变。

### `XJ` 层（5 个）— 样式变体

```
2k1  XJYS1  综合属性样式一
2k2  XJYS2  综合属性样式二
2k3  XJYS3  综合属性样式三
2k4  XJYS4  综合属性样式四
521  XJTILI 体力
```

**四个 opcode 只为了同一个面板的四种排版。**

这在协议设计上是很糟的做法——**版面样式不该占用 opcode 空间**，
它应该是 payload 里的一个字段。
但它揭露了一件事：**加这一层的人把 opcode 当成「函数名」在用**，
而不是当成「消息类型」。

### `KILL` 层（4 个）＋ `XY` 的战斗码（5 个）— 两批人做同一件事

```
XY 层：  511 加敌  512 减敌  513 加友  514 减友  515 战斗描述
KILL 层：516 战斗结束  517 战斗技能  518 战斗开始  519 清理战场
```

**同一个战斗面板，命名前缀却不同、编号连续。**
最合理的解释是：`XY` 先做了一半（实体增删与描述），
后来另一批人补上生命周期（开始／结束／清场）与技能列，
而他们用了自己的前缀。

**编号连续但前缀不同——这是典型的「接手」痕迹。**

### `DM*` 层（10 个）— 大梦江湖自己的

```
111  DMJHLOOK    查看自身
604  DMZHUJMQH   判断界面
605  DMZHUJIU    更改界面
…
```

**最后一批，而且直接用了 lib 自己的名字当前缀。**
§079 已经证明它是最外层——因为整份 header 就叫做大梦江湖的 header。

### ★ 两个直接对上本书前面章节的发现

**① 带字母的 opcode 全部在扩充层。**

```
10a  11a  （XY 层）
2k1  2k2  2k3  2k4  （XJ 层）
```

§004 记过一个坑：

> 一开始把 opcode 的规则写成「ESC + 三个**数字**」，正则是 `/^\d{3}$/`。
> 后来在扩充方言里撞到 `10a`、`11a`、`2k1`–`2k4` 这种**带字母**的码，
> 全部被当成一般消息，把控制字符连同内容印在画面上。

**现在知道那个坑的确切位置：这六个码全部来自 `XY` 与 `XJ` 两层，
也就是「App 化」之后才加的部分。**

内核层的 25 个码**全部是三位数字**——
所以那个正则在内核层上是**完全正确**的。
**它不是写错了，是它的作者只看过内核层。**

> 这是本书「证据等级」规矩的一次漂亮验证：
> 从一份样本归纳出的规则，在那份样本上永远成立。

**② 唯一的「弃用」标记。**

整份 header 只有一个显式的淘汰注记：

```c
#define XYMRX  ESA + "10a"   //跑马灯展示(弃用)
```

**扩充层自己内部也有演化**——有东西被加进来，然后被放弃，
而且放弃时**留下了注记却没有删掉定义**。

这正是 §009 那条「定义 ≠ 使用」的微观版本：
**协议的定义档是只增不减的**，
因为删掉一个定义的风险（可能还有人在用）永远大于留着的成本。

**解决的痛点**：这一节解的是「扩充方言为什么那么乱」——
§005 抱怨过编号没有语意分区（`045` 夹在 `024` 与 `100` 之间、
`900` 不遵循 `9xx = 反向操作`）。

**现在有了解释：那不是一个人设计的编号空间，是五批人各自往里面塞。**

| 前缀 | 它占的号段 | 设计品味 |
|------|-----------|---------|
| `ZJ` | 000–023、9xx | **语意分区**（`9xx` = `0xx` 的反向操作） |
| `XY` | 10a、11a、130、2xx、3xx、4xx、5xx | **按面板分群**，但号段跳跃 |
| `XJ` | 2k1–2k4、521 | **样式当 opcode** |
| `KILL` | 516–519 | 接在 `XY` 的 511–515 后面 |
| `DM*` | 111、604、605… | **散落**，无分区 |

**只有内核层有设计。其余四层是累积。**

**踩过的坑**：本项目的 `dialects.js` 把扩充码组织成 profile（§010），
每一个 opcode 标上 `kind` / `panel` / `slot`——
**那等于是替这五层做了一次事后的统一分类。**

而 §010 记录的四个撞号，正是这种「事后统一」必然会撞上的东西（§081）。

**优点 / 罩门**：扩充层的优点是**它真的做出了一个图形接口**——
47 个 `XY` 码撑起商城、背包、副本、人物面板，
这在一条纯文本 telnet 连接上是很可观的成果。
罩门是**没有任何一层知道其他层的存在**，
所以编号空间、命名惯例、设计哲学全部各自为政。

**效益**：对逆向工作，这一节提供了一个很实用的技巧：
**用命名前缀替一份没有版本的协议断代。**

前缀通常泄漏三件事：谁加的、什么时候（相对顺序）、以及那批人怎么想。
一份 header 如果有五种前缀，它就至少有五层地层。

> 💡 君之一席话
> **编号空间的混乱不是设计失误，是地层**——当你看到一份协议的编号没有规律，先别骂设计者，先数数看它有几种命名前缀。

> 🔍 老手视角──真正的门道
> 「同一个面板的不同槽位各占一个 opcode」（`XYBEIBAO` / `XYBBTEXT` / `XYBEIBAOT`）这个现象，是协议设计里一个很常见的滑坡：**当加一个 opcode 比改一个 payload 格式便宜时，人就会一直加 opcode。** 在这个生态里加 opcode 的成本近乎零（`#define` 一行，§043 说过 driver 完全不知情），而改 payload 格式要动客户端的解析器并考虑兼容性。于是理性的个体选择，累积成了一个 116 个码的编号空间。老手看到这种「某个维度的扩充成本特别低」的系统时，会预期那个维度将来一定会失控——并且提早在那里设一条规矩（号段分区、命名前缀强制、添加需要登记）。可落地的判准：**看你的系统里哪一种扩充最便宜，那里就是三年后最乱的地方**；在它还只有十个项目的时候定规矩，成本是一小时，之后是一次重构。

## 081　第三代与撞号的机制 — 两个团队各自从 600 开始

**标签**：`#撞号` `#指游ZY` `#手机时代` `#命名空间` `#4字符opcode`
**证据等级**：🟡 服务器方言表与转换教程 ＋ 🟢 本项目 `dialects.js` 的冲突诊断

**起源**：§010 记过一件事——本项目写了一个「列出所有 profile 中意义不同的 opcode」
的诊断函数，**本来只是想做个健康检查，结果它第一次运行就吐出四个。**

**那四个是 602、603、604、605。**

§079–§080 把地层挖开之后，这四个撞号的成因可以完整还原了。

**技术内核**：

### 第三代：指游（`ZY*`）方言

第三个世代来自另一条线——「指游 MUD」，
本项目在封存的 `others/zjmud转zymud教程` 里找到它的转换说明。

它的号段是 **600–618，外加一个 1085**：

| opcode | 名称 | 用途 |
|--------|------|------|
| 600 | `ZYRIGHTBTN` | 方向键右侧按钮 |
| 601 | `ZYHPTXT` | 个人状态 |
| **602** | **`ZYCHARHP`** | 同房间其他 NPC 状态 |
| **603** | **`ZYFIGHTBTN`** | 弹出战斗界面与按钮 |
| **604** | **`ZYHANDLERBTN`** | 弹出操作面板与按钮 |
| **605** | **`ZYCLEARSCREEN`** | 清空主画面 |
| 606–618 | `ZYRIGHTMENU`…`ZYKJ` | 侧菜单、语音、进度条、重登、通知栏、网络状态、选择器、伤害、技能、剧情、震动、快捷键 |
| **1085** | **`ZYMAP`** | 地图——**全协议唯一的 4 字符 opcode** |

### ★ 撞号怎么发生的

把三代的 6xx 号段叠起来：

```
DMJH 层：           604 判断界面      605 更改界面
XY   层：  602 ?    603 ?
                    ↕                 ↕
ZY   方言：602 NPC状态  603 战斗界面  604 操作面板  605 清空画面
```

**两边都把「界面／面板」类的 opcode 放在 6xx 号段。**

而 §043 已经解释过根因：

> **ZJMUD 是 mudlib 层协议，driver 完全不知道它存在**，
> 所以任何人拿到 mudlib 都可以加一行 `#define`，
> **不必跟谁报备，因为根本没有「谁」可以报备。**

**两个团队在互不知情的情况下，各自从一个「看起来还没被用」的号段开始编，
而他们对「哪个号段还没被用」的判断，来自各自手上那份 header。**

大梦江湖那边看到的是 000–599 大致被占，于是往 6xx 走；
指游那边看到的是内核层 000–023 加零星扩充，于是也往 6xx 走。

**两边的判断都是合理的，而结果是必然的。**

### `1085` — 打破的第二个假设

§004 记过第一个被打破的假设（「三个数字」被 `10a`／`2k1` 打破）。
`ZYMAP = 1085` 打破的是第二个：**opcode 是三个字符**。

本项目的解析器因此改成「行首 4 或 5 个字符，视情况」——
规格书 v1.4 明确标注 **「opcode 可为 3 或 4 字符」**。

**一个没有版本协商的协议，只能靠解析器不断放宽来兼容。**

### ★ ZY 方言泄漏了它的年代

看 606–618 这一段的内容：

| opcode | 用途 | 它假设了什么 |
|--------|------|------------|
| 607 `ZYVOICE` | 语音（官方标注「暂未实现」） | 有麦克风 |
| **610 `ZYSTATUSINFO`** | **Android 通知栏** | **对面是一个 Android App** |
| 611 `ZYCLIENTSTATUS` | 开关网络状态与**帧率**显示 | 有 render loop |
| **616 `ZYVIBRATE`** | **震动（时长毫秒）** | **对面是一支手机** |
| 615 `ZYSTORYTEXT` | 逐字剧情 | 有动画能力 |
| 609 `ZYSYSEXIT` | 几毫秒后回登录画面 | 有「画面」的概念 |

**`ZYVIBRATE` 与 `ZYSTATUSINFO` 是决定性的**：
一个会让手机震动、会写 Android 通知栏的 opcode，
**只可能诞生在智能型手机时代**。

而本项目的起点——那个 1.1 MB 的 APK（§001）——
封装日期是 **2022-10-03**。

**三代的年代序因此可以排出来：**

```
第一代  内核 ZJ 层         纯文本 MUD 加标记        （最早，普世）
第二代  XY/XJ/KILL/DM* 层   App 式固定版面           （PC 图形客户端时代）
第三代  ZY 层               震动、通知栏、帧率、语音   （智能型手机时代，最新）
```

**规格书 §12 的判断「这是三个方言中最新的一套」，
在这里得到了独立的佐证——不是从版本号看出来的，是从它假设的硬件能力。**

**解决的痛点**：§010 说「撞号的根源是协议演化时没有中央注册」，
这一节把那句话从**断言**变成了**可追溯的过程**：

```
没有中央注册（§043）
  → 每个团队只能从自己手上那份 header 推测哪个号段空着
    → 两边都推测 6xx 空着（因为两边看到的 header 不一样）
      → 撞在 602–605
        → 而且双方都不会知道，直到有人同时支持两个方言
```

**最后一行是关键：撞号在协议层面是没有症状的。**
只有当一个客户端试图同时支持两个方言时，冲突才会显现——
而那个客户端，就是本项目。

**踩过的坑**：§010 说发现撞号「纯属意外」。
现在回头看，**它迟早会被发现，而且必然是被同时支持多方言的实作发现**。

这给了一个一般化的结论：

> **一套没有中央注册的协议，它的冲突只会在「有人试图统一」的那一刻暴露。**
> 在那之前，每个孤岛都是自洽的。

**优点 / 罩门**：ZY 方言的优点是**它把客户端能力纳入了协议**——
震动、通知栏、语音、帧率，这是三代里唯一意识到
「对面是一个有能力的设备，而不只是一个终端」的一代。

罩门有两个：其一，**它假设对面是 Android**
（`ZYSTATUSINFO` 在本项目的 Web 客户端是 `KIND.IGNORE`）；
其二，**它与第二代撞号四次**，而两边都不知情。

**效益**：本项目处理撞号的方式（§010 的 profile 隔离 + 诊断函数）
在这里得到了完整的辩护：

| 做法 | 为什么必要 |
|------|-----------|
| **分 profile** | 因为 602–605 在两个方言里**真的**意义不同，没有正确的合并方式 |
| **判别机制** | 因为要先知道现在是哪个方言 |
| **诊断函数 + 测试** | 因为**撞号是无症状的**，必须主动去找 |

**§010 说「少了第三件，你会在半年后加第四个方言时重蹈覆辙」——
这一节解释了为什么：因为第四个方言的作者，也会从他手上那份 header
去推测哪个号段空着。**

> 💡 君之一席话
> **没有中央注册的协议，它的冲突只在「有人试图统一」的那一刻才出现**——在那之前，每一座孤岛都觉得自己是对的，而且它们都没错。

> 🔍 老手视角──真正的门道
> 这一节最值得带走的，是「撞号是无症状的」这个性质。多数 bug 会叫——例外、错误码、崩溃；而命名空间冲突不会，它只会让某个功能在某些情况下做错事。这类「安静的正确性问题」在分布式系统里到处都是：两个服务对同一个字段的单位理解不同（公尺 vs 英尺）、两个团队对同一个状态码的语意不同、两份设置用同一个 key 表达不同的东西。它们的共同点是**只有在集成的那一刻才会显现，而集成往往发生在上线之后**。老手的对策不是「更小心」，而是**主动制造集成时刻**：写一个把所有命名空间摊平、列出冲突的诊断程序，并且让它跑在 CI 上。本项目那二十行的冲突诊断函数，价值不在它找到的那四个，在于它让第五个在被写出来的当天就会被发现。可落地的做法：**任何有「多个来源往同一个空间注册」的系统（路由、事件名、设置键、指针名、错误码），都要有一支列出重复的检查。**

## 082　协议的年表 — 以及它为什么永远是 1.0

**标签**：`#年表` `#版本号` `#双重转码` `#收束` `#证据等级`
**证据等级**：🟢 本节所有断代证据皆可重跑（方法附于文末）

**起源**：§079–§081 把地层挖开了。这一节把它组装成年表——
然后停在一个很不舒服的观察上。

**技术内核**：

### 三个世代的完整对照

| | **第一代** | **第二代** | **第三代** |
|---|-----------|-----------|-----------|
| 方言代号 | `classic`（经典） | `dmjh`（扩充） | `zymud`（指游 ZY） |
| opcode 前缀 | `ZJ` `SYS` | `XY` `XJ` `KILL` `DM*` | `ZY` |
| 数量 | 18–27 | 再加约 61–72 | 20（600–618、1085） |
| **号段** | 000–023、9xx | 10a、11a、1xx–5xx、2k1–2k4 | **600–618、1085** |
| **编号规则** | **三位数字，`9xx` = `0xx` 反向** | **数字＋字母混用** | 三位数字 ＋ **一个四位数** |
| 产品形态 | 纯文本 MUD 加标记 | **App 式固定版面** | **智能型手机 App** |
| 硬件假设 | 终端机 | 有版面的图形客户端 | **震动、通知栏、麦克风、帧率** |
| 握手（附录 F.2） | `ver1.0:`＋DES crypt ／ `ver1.0,`＋明文 | `ver1.0,` ＋ `$6$` SHA-512 crypt | `version 1.0 key::<crypt>` |
| 在 17 份封存里 | **全部 17 份** | **仅 1 份**（大梦江湖）＋ 1 份保存为注解（江湖论剑） | 0 份（来自转换教程） |
| 实测送出（附录 F.3） | `000 002 003 004 005 006 012 021 022` | **`111 234 517 604 605`** | — |

### ★ 三个世代，三种握手格式，全部自称 1.0

把握手那一列单独拉出来看：

```
第一代   ver1.0:byz0rmpISExtQ                  ← 冒号分隔，13 字符 DES crypt
第一代'  ver1.0,123456789abcd                  ← 逗号分隔，★ 明文密钥
第二代   ver1.0,$6$<16字符salt>$<86字符>         ← 逗号分隔，SHA-512 crypt
第三代   version 1.0 key::<crypt>              ← 完全不同的语法
```

**分隔符换过（`:` → `,`）、哈希算法换过（无 → DES → SHA-512）、
连整个语法都换过（`ver1.0:` → `version 1.0 key::`）——
而版本字符串从头到尾都是 `1.0`。**

三十年、三个世代、116 个 opcode、四个撞号，
**没有任何一次改动反映在版本号上。**

### 为什么？§043 早就回答了

> ZJMUD 是 **mudlib 层协议**，driver 完全不知道它存在。
> 没有 driver 支持、没有 telnet 子协商、**没有注册、没有能力协商**。

**没有能力协商，版本号就没有用途。**

版本号存在的理由是**让对面据以调整行为**。
但 ZJMUD 的服务器不会问客户端「你懂哪个版本」（§056 第 0 代的特征），
客户端也无法据此要求服务器降级——
**服务器一律送，客户端自己看着办。**

在这种架构下，`ver1.0` 不是版本声明，**是一个握手用的固定字符串**。
§044 早就从原代码证明了这一点：`jiance()` **收任何非空输入就放行**——
**它连那行字符串自己有没有被正确解读都不在乎。**

**所以「协议没有版本」不是疏忽，是这个架构的必然结论。**

### 对照：其他三层都有版本机制

本书前面几篇正好提供了三个对照组：

| 层 | 版本机制 | 出处 |
|---|---------|------|
| **driver 语言层** | `__SENSIBLE_MODIFIERS__` —— **可侦测的破坏性变更** | §059 |
| **driver 数据层** | DGD 的 LWO **建议第三格放版本号**，「以防你之后改变类型的建构方式」 | §068 |
| **本项目的映像格式** | `format: 1` —— **第一个字段就是版本** | 附录 F |
| **ZJMUD 协议** | **无** | 本节 |

§068 的老手视角说过：

> 任何会被写进磁盘、送上网络、或存进数据库的结构，第一个字段永远是版本——
> **即使当下只有一个版本，而且你确定不会改。**

**ZJMUD 是那句话的反例教材**：它有一个看起来像版本号的东西，
但因为没有人会依据它做任何决定，**它三十年没有动过，也不需要动。**

### 乱码那一行 — 损坏本身也是史料

`LPMud-Name/world/include/zjmud.h` 第 129 行，
夹在被注解掉的扩充层与活跃的内核层之间，是一行注解：

```
//指?MUD转?协?
```

文件整体可以解为 UTF-8，但这一行的中文本**部分是无法还原的替代字符**。
以 GBK 重新解读会得到 `//指锟斤拷MUD转锟斤拷协锟斤拷`——
而 `锟斤拷` 是中文圈著名的**双重转码残骸**
（UTF-8 的替代字符 U+FFFD 被编成 GBK、再被读回来的产物）。

**推测原文是「指游 MUD 转换协议」**（🔴 推论，标明未验证）——
它正好是这个文件里唯一提到第三代方言的地方，
而它**在成为证据之前就已经被两次编码转换磨掉了**。

> **这一行的价值不在它说了什么，在它证明了这份文件经历过什么。**
> 附录 D.4 说过：优先去找「系统自己写下的东西」——
> swapfile 的文件名、intermud 名录、档头署名。
> **损坏的痕迹也算一种：它记录了这份文件被谁、用什么工具、搬过几次。**

而本项目的导入管线正是为此而存在——
附录 F.5 记录「GBK → UTF-8 转档，最多单一 lib 29,853 档」，
**如果那次转换也做成双重转码，本书引用的每一条中文注解都会变成这个样子。**

### 完整年表

```
1993–1996   TMI-2 mudlib 传入中文圈（附录 D.3）
              ↓ driver 不知道协议存在，于是谁都可以加（§043）
第一代      内核 ZJ 层成形：000–023 ＋ 9xx 反向操作

              ↓

```

**解决的痛点**：这一篇解的是本书一个结构性的空白——
它花了十三篇挖别人的历史，却没挖自己主题的。

而挖完之后，第二篇与第三篇的所有「怪异之处」都有了成因：

| 前面章节的观察 | 这一篇给的成因 |
|--------------|--------------|
| §004 正则 `/^\d{3}$/` 被打破 | 带字母的码全在第二代（§080） |
| §005 编号没有语意分区 | 只有内核层有设计，其余四层是累积（§080） |
| §009 定义 102 个只用 16 个 | 定义档只增不减（`弃用` 标记却不删，§080） |
| §010 四个撞号 | 两批人各自从 6xx 开始（§081） |
| §011 变长 opcode | `1085` 来自第三代（§081） |
| 附录 F.2 三种握手格式 | 三个世代各一种，而版本号从未变（本节） |

**优点 / 罩门**：本篇方法的优点是**全部可重跑**（见下方）。
罩门是**它只能重建相对顺序，给不出绝对日期**——
没有任何一份 mudlib 带着可信的时间戳，
唯一的绝对日期是那个 APK 的 2022-10-03，以及 TMI-2 档头的 1993-08-15。
**中间三十年的刻度是靠地层推的，不是量的。**

**效益**：这一篇补完了本书的自我一致性。
第一篇立下的规矩是「证据等级」，而本书用它挖了六支 driver 的历史；
**最后把同一套方法用回自己身上，是这本书该做的最后一件事。**

> 🔍 老手视角──真正的门道
> 这一篇的方法可以浓缩成一句话：**当一个系统没有版本历史，就去读它的沉积物。** 命名前缀（谁加的）、号段分布（什么时候还空着）、被注解掉但没删的区块（曾经有过什么）、标了「弃用」却留着的定义（放弃的成本高于保留）、硬件假设（震动 → 手机时代）、甚至编码损坏的痕迹（被搬过几次）——这些都是断代证据，而且它们比任何人的回忆可靠，因为**没有人是为了留给后人而写下它们的**。这个技巧在接手任何长寿系统时都适用：数据库里没人用的字段、设置档里注解掉的区块、代码里的 `// TODO: 2014`、路由表里的旧路径，全部都是地层。可落地的做法：**接手一个没有文档的系统时，先花半天把「死掉但没被删的东西」列一遍**——那份清单会告诉你这个系统试过什么、放弃了什么、以及为什么现在长这样。**活着的代码告诉你它做什么，死掉的代码告诉你它经历过什么。**
