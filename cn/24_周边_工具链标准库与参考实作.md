## 075　driver 之外的六支程序 — 被忽略的工具链

**标签**：`#CLI` `#lpcc` `#portbind` `#o2json` `#工具链` `#静态检查`
**证据等级**：🟡 上游 `fluffos/docs/cli/`

**起源**：本书从第八篇起一直在讲 `driver` 这支程序。
但 FluffOS 的建置产物不只一支——**还有五支**，
而其中至少两支能直接改善本项目的工作流程。

**技术内核**：

### `driver` — 主程序，以及它被忽略的旗标

```bash
./driver [flags] config_file
```

| 旗标 | 作用 |
|------|------|
| `-f<flag>` | 初始化后、**开网络之前**，调用 master 的 `flag(string)`（§042 的 `fluffos_flag` 就是它的 WASM 版） |
| `-d<category>` | 开分类调试日志，可重复；等同 `set_debug_level()` |
| `--tracing <file>` | 开 LPC 追踪（§077） |
| **`--generate-config`** | **印出一份含全部选项、默认值与注解的起始设置档** |

**最后一行值得单独标记。**
§039 记过本项目在设置档上栽的三个跟头——
其中两个（设置文件名不一、行尾注解不存在）
**如果一开始就用 `--generate-config` 产一份范本来比对，都不会发生。**

14 个调试分类，粒度比想像中细：

```
call_out  d_flag  connections  mapping  sockets  comp_func_tab
LPC  LPC_line  event  dns  file  add_action  telnet  websocket
```

`telnet` 与 `connections` 那两个，正是 §055 那 6 组协商字节的来源；
**本项目当时是自己在客户端印字节，其实 driver 这一侧就有开关。**

### ★ `lpcc` — 把编译结果倾印出来

```bash
./lpcc config_file lpc_file
```

它会加载 config、加载 simul_efun 与 master，然后把目标档的编译结果印出来：

```
NAME: /single/master.c
INHERITS:
      name                    fio    vio
      ----------------        ---    ---
        inherit/master/valid.c      0      0
FUNCTIONS:
      name                  offset  mods   flags   fio  # locals  # args # def args
      --------------------- ------  ----  -------  ---  --------  ------ ----------
   0: get_inherit_called         0   +--  i-s----    0
   1: valid_shadow               0   +--  i-s----    1
   …
```

**每个函数的修饰词、旗标、区域变量数、参数数、缺省参数数**——
§059 讲的那些修饰词（`private` / `static` / `nomask` / `varargs`）
在这里是可以被机器读出来的。

它同时会印出所有编译警告：

```
/std/base64.c line 56: Warning: Unused local variable 'p'
```

**这件事对本项目的意义很直接。**
§048 的结论是「能力探测对老 mudlib 只能靠实跑」，
因为静态分析抓不到语意变化与封存缺件。
**那个结论仍然成立，但 `lpcc` 补上了静态那一半**——
它能在不启动世界的情况下，把**每一个文件**编译一次并回报错误。

而 §078 会看到：**上游的参考实作正是这样做的**
（`lpcc_check.sh` 批量编译每一个档）。
本项目的 `boot-test.mjs` 只会发现「开机路径上」的问题；
一个玩家永远不会走到的房间里的语法错误，它抓不到。

### `o2json` / `json2o` — 存盘与 JSON 双向转换

```bash
./o2json [-prtty] [-ascii] o_file json_file    # 支持 - 代表 stdin/stdout
```

输出格式：

```json
{ "program_name": "...", "variables": [ { "name": "...", ... } ] }
```

**LPC 的 `.o` 存盘可以被 `jq` 处理，改完再转回去。**

§附录 F.5 记过本项目从 `nt7` 移除了 **630 个含密码栏的玩家存盘**——
当时是整档删除。**有了 `o2json`，那件事可以做得更精细**：
把敏感字段挑掉、其余保留。
（本项目的判断仍然是删除比较安全，但「只能整档删」不再是理由。）

### `portbind` — 特权端口与权限分离

```bash
./portbind -p 23 -u mud -g mud -d ./driver config
```

四个步骤：

```
① 以 root 绑定特权端口（<1024）
② 把绑好的 socket 经 文件描述子 6 交给 driver
③ 卸除权限到指定的 uid/gid
④ exec driver
```

**这是 Unix 「特权分离」的教科书实作**：
需要 root 的只有 `bind()` 那一瞬间，之后整个 driver 以无特权身分运行。

对照 §061 讲的 uid/euid——**那是 mudlib 内部的权限模型**；
`portbind` 是**操作系统层级**的。两者互不相干，而且都需要。

### `symbol` / `generate_keywords` — 建置期工具

`generate_keywords` 产生 LPC 关键字表（§040 提过 WASM 交叉编译要先建原生工具，
就是为了跑这类东西）；`symbol` 处理符号。

**解决的痛点**：这六支工具解的是同一类问题——
**在不启动整个世界的情况下，对 mudlib 做点什么。**

`driver` 是唯一需要完整世界的；其余五支都是脱机工具。

**踩过的坑（本项目的，回头看）**：本项目的整个导入管线
（§附录 F.5：转码、改 `set_encoding`、移除存盘、扫凭证）
**都是用 Node.js 自己写的**，因为当时不知道有这些工具。

结果是：
- 设置档范本靠反推（`--generate-config` 可以直接产）；
- 协商字节靠客户端印（`-dtelnet` 可以开）；
- 编译错误只在开机路径上被发现（`lpcc` 可以全扫）；
- 存盘只能整档删（`o2json` 可以逐栏处理）。

**这不是错误，是信息不足。** 而它示范了一件很常见的事：
**当一个工具的文档在官网的一个不起眼分页里，
它等于不存在。**

**优点 / 罩门**：优点是这套工具让 mudlib 的维护可以脱机、批量、自动化。
罩门是**它们几乎没有能见度**——`docs/cli/` 底下七篇文档，
其中 `lpcc.md` 有 50 KB（几乎全是输出范例），
但没有任何一份 getting-started 会提到它们。

**效益**：对任何要维护一份 mudlib 的人，这是一组立即可用的清单：

```bash
./driver --generate-config > config.ref   # 拿一份权威范本来 diff
./lpcc config <每一个档>                   # 全库静态编译检查
./driver -dtelnet -dconnections config    # 协议层真相
./o2json - - < player.o | jq …            # 存盘数据处理
```

> 💡 君之一席话
> **一个没有能见度的工具等于不存在**——本项目花了三周自己写的东西，有一半在上游的 `docs/cli/` 底下躺着。

> 🔍 老手视角──真正的门道
> 这一节真正的教训不是「要读完文档」（没有人读得完），而是**接手任何项目时，先把它的建置产物列一遍**。`make install` 到底装了哪些运行档？`bin/` 底下有什么？这个动作三十秒，而它会告诉你这个项目的作者认为哪些操作值得做成工具——**那是一份没有写成文档的需求清单**。本项目如果第一天就跑一次 `ls build/bin/`，会看到 `lpcc`、`o2json`、`portbind` 这些名字，然后至少会去查它们是什么。可落地的做法：**评估任何新依赖时，除了读 README，再做两件事——列出它的建置产物、列出它的设置项**（`--generate-config` 这类旗标特别值钱）。这两张清单合起来，比 README 更诚实地描述了这个项目能做什么。

## 076　LPC 标准库与 TUI — 服务器这一侧的反击

**标签**：`#stdlib` `#simul_efun` `#TUI` `#readline` `#终端能力`
**证据等级**：🟡 上游 `fluffos/docs/stdlib/`（含 `tui.md`）

**起源**：§036 讲过 simul_efun 是「mudlib 自己的假 efun」。
但 FluffOS 还提供了**一整套现成的 simul_efun**——
`docs/stdlib/` 底下有一个分类齐全的标准库，而本书一直没提。

其中最值得看的是 **TUI**，因为它直接回应了本书的两个主题。

**技术内核**：

### 标准库的分类

| 分类 | 内容 |
|------|------|
| `arrays` | `reduce` |
| `mappings` | `element_of_weighted`（加权随机采样） |
| `numbers` | `sum`、`array_sum`、`percent`、`percent_of` |
| `objects` | `all_environment`、`present_clone` |
| `string` | `break_string`（断行排版）、`base64encode/decode`、**`bitmap_font`** |
| `db` | `database` |
| `ffi_util` | FFI 辅助 |
| **`tui`** | **整套终端 UI 工具库** |

`break_string` 那一项很能说明 LPC 生态的性质——
**「把一段文本排成固定宽度的段落」竟然需要一个标准库函数**，
因为在 CJK 环境里它牵涉全角宽度计算，而且每个 mudlib 都要用。

### ★ TUI — 用纯 LPC 写的 readline + ncurses

> The testsuite mudlib ships a terminal-UI toolkit **written in pure LPC**,
> layered like **`readline` + `ncurses` + `pterm`**: line editing, history and
> incremental search for the prompt line, inline select/multiselect/confirm
> prompts and pretty-printers for ordinary output, plus a **screen buffer,
> diff renderer and widget set** for full-screen applications.

三层架构：

| 层 | 对应的传统工具 | 提供什么 |
|----|--------------|---------|
| 提示行 | **readline** | 行编辑、历史、增量搜索、补全 |
| 内嵌提示 | **pterm** | select / multiselect / confirm / 美化输出 |
| 全屏幕 | **ncurses** | 屏幕缓冲、**差分渲染**、widget |

**★ 它取代的东西是 `input_to()`：**

```c
void get_command() {
    tui_readline((: got_command :), ([ "prompt": "> " ]));
}

void got_command(mixed line, int state) {
    if (state != TUI_RL_DONE) return;   // TUI_RL_ABORT (^C) / TUI_RL_EOF (^D)
    do_command(line);
    get_command();
}
```

**这一段值得和 §044 对照着读。**

§044 逐行解剖过本项目 mudlib 的登录流程，
那是一条 `logon` → `jiance` → `get_user` 的 `input_to` 接力——
**三个函数，只因为中间要等玩家打字**。

而 §066 说 LDMud 的答案是**协程**（`async`/`await`/`yield`）。

**TUI 是第三种答案**：不改语言，用回呼 + 状态码，
但把「等一行输入」升级成「等一次完整的行编辑会话」，
中途的 Ctrl-C / Ctrl-D 都有明确状态（`TUI_RL_ABORT` / `TUI_RL_EOF`）。

同一个问题（**单线程事件循环上如何表达多步流程**）的三种解：

| 解法 | 谁 | 代价 |
|------|-----|------|
| `input_to` 接力 | 传统 LPC（§044） | 流程被拆成 N 个函数，状态靠对象变量传递 |
| **协程** | LDMud（§066） | 要改语言 |
| **回呼 + 状态码** | FluffOS TUI | 仍是回呼，但**语意完整**（成功/中止/EOF 分得清楚） |

### 它用到的终端能力，正是 §055 那些选项

TUI 提供的功能清单，每一项都对应一个 telnet 选项或终端特性：

| TUI 功能 | 靠什么 |
|---------|--------|
| 密码屏蔽（`"masked": 1`） | **ECHO**（选项 1） |
| 逐键输入（方向键、Ctrl-R） | **SGA**（选项 3）＝字符模式 |
| **即时 resize** | **NAWS**（选项 31）→ `window_size` apply |
| 终端能力判断 | **TTYPE**（选项 24）→ `terminal_type` apply |
| bracketed paste、alternate screen | 终端逃逸串行 |
| **CJK 宽字符感知渲染 ＋ 水平卷动** | ICU 的字素/宽度计算（§041） |

**§055 那张表里「FluffOS 立场」字段为什么要谈那些选项，到这里才完整**：
driver 不是为了好看才协商 ECHO/SGA/NAWS/TTYPE，
**是因为 mudlib 这一层真的有东西要用它们。**

**解决的痛点**：TUI 解的是一个和本书主线互为镜像的问题。

§054 的结论是：**因为服务器只吐文本，客户端三十年来只能靠 trigger 猜状态。**
而 §056 的四代频外协议，是**服务器主动多说一点**的路线。

**TUI 是第三条路：不多说，而是把终端本身的能力用到极致。**

```
路线 A（客户端猜）      trigger / alias        —— §054
路线 B（服务器多说）    ESC opcode / GMCP      —— §043 §056
路线 C（用满终端能力）  TUI：readline + ncurses —— 本节
```

**三条路线的共同前提都是「只有一条文本信道」，但施力点完全不同。**
路线 C 的优点是**不需要任何自订协议**——
它用的全是 telnet 与 ANSI 的标准能力，
所以**任何现代终端机都能用，不需要专用客户端**。

而本项目走的是路线 B，代价已经在 §057 结算过。

**踩过的坑（推论，标为未验证）**：TUI 对本项目的 WASM 展示站有一个潜在障碍——
它需要**字符模式**（SGA）与逐键串流，
而本项目的前端是一个以「行」为单位的 GUI（§024 的 18 个组件）。
上游的参考前端用 xterm.js 处理这一层（§077）。
**两种前端假设不同的输入模型，这是路线 B 与路线 C 难以并存的原因。**
本项目没有实测过，此处标为 🔴 推论。

**优点 / 罩门**：优点是 TUI **完全用 LPC 写成**，可以拷贝到任何 FluffOS mudlib
（只要带上 `include/tui.h`）——**不需要改 driver**。
这是 §036 那三个调用方向的漂亮示范：
一整套终端 UI 框架，住在 simul_efun 与继承层里。
罩门是它假设对面是一个**真的终端机**，
而本书整个第四到六篇做的是一个**不是终端机的客户端**。

**效益**：对本书而言，TUI 补上了「三条路线」里缺的那一条，
让 §057 那个「知识该放在哪一层」的分析完整了：

| | 知识在哪 | 需要专用客户端吗 |
|---|---------|----------------|
| A trigger | 用户脚本 | ❌ |
| B 方言解析 | 客户端代码 | **✅** |
| B' 标准频外 | 协议规格 | ⚠️（要支持 GMCP） |
| **C TUI** | **服务器端 mudlib** | **❌ 任何终端机** |

**C 是唯一「知识全在服务器、且不需要专用客户端」的组合。**

> 💡 君之一席话
> **在只有一条文本信道的世界里，你可以让客户端猜、让服务器多说、或者把那条信道本身用到极致**——三条路，而第三条不需要任何人配合。

> 🔍 老手视角──真正的门道
> TUI 这种「用既有标准把能力做满」的路线，在工程上常常被低估，因为它不产生新东西——没有新协议、没有新规格、没有可以拿出来讲的创新。但它有一个其他路线都没有的性质：**零协调成本**。ANSI 逃逸串行与 telnet 选项已经被所有终端实作了四十年，用它们不需要说服任何人。这个模式在别处也很常见：用 HTTP header 而不是自订字段、用 SQL 而不是自订查找语言、用文件系统而不是自订保存层。老手在面对「我需要一个新能力」时，第一个问题永远是**「既有标准里有没有一个被低估的角落可以用？」**——因为既有标准的兼容性是白送的，而新协议的兼容性要靠三年时间去换。可落地的判准：在设计自订协议之前，**先把目标平台的标准能力清单读一遍**；本书 §055 那张 telnet 选项表列了 18 个选项，而多数 MUD 只用到其中三、四个。

## 077　可观测性与现代网络层 — driver 自己就是一台服务器

**标签**：`#tracing` `#性能剖析` `#WebSocket` `#TLS` `#数据库` `#可观测性`
**证据等级**：🟡 上游 `docs/concepts/general/`（`tracing`、`websocket`、`tls`）＋ `docs/stdlib/db/database.md`

**起源**：§041 那张套件矩阵把 `db`、`compress`、`crypto` 列为「WASM 上关掉」，
但没说它们在原生版上是什么。而 `tracing` 这一项本书从未提过。

**这一节补的是：FluffOS 作为一台现代服务器，它自己带了什么。**

**技术内核**：

### ① tracing — 产出 Chrome Trace Event Format

```c
trace_start("/log/performance.json");   // 缺省 10 秒后写出
…
trace_end();
```

记录的事件：

> LPC function calls and efun calls、object loads and file compilation、
> `catch` evaluation、file I/O、and apply-cache lookups

每个事件带着**持续时间、嵌套关系（调用者／被调用者）、以及对象与函数名**，
输出成 **Chrome Trace Event Format (JSON)**——
**可以直接丢进浏览器开发者工具的性能面板看火焰图。**

而它的设计取舍值得单独记：

> The instrumentation is **always compiled in** and only records while a trace
> is active, so **no special build is required** — `trace_start()` and
> `trace_end()` are ordinary efuns available in normal builds.

**永远编进去、只在启动追踪时记录。**
这是「零成本抽象」的实际取舍：付出的是每个调用点一个分支判断，
换到的是**正式环境随时可以开始剖析，不必重编、不必重启**。

**对照本项目**：§046 那条 11 站的链路，
本项目能量的只有第 ⑥ 站之后（JS 那一侧）；
**第 ①–⑤ 站（LPC → VM → comm → telnet → Transport）一直是黑箱**。
`trace_start()` 加上 `-dLPC` / `-dtelnet`（§075），
**那半条链路是可以被量出来的**——本项目没有用，因为不知道。

`apply-cache lookups` 那一项尤其有意思：§036 说 apply 靠字符串名绑定，
而 driver 显然为此做了缓存——**而缓存命中率是可以被追踪的**。

### ② WebSocket ＋ 官方 Web 客户端

`config.ini` 的 `external_port_N : websocket <port>` 加上 `websocket http dir`
（§039 本项目的设置里就有 `external_port_3 : websocket 5004` 与 `www`），
**driver 本身就能发静态网页并接受 WebSocket 连接。**

而 `src/www/` 底下就是官方的 Web 客户端，
终端仿真用 **xterm.js**（vendored 在 `src/www/vendor/`），
与 WASM 版的前端**共用同一份 vendor 目录**（§040）。

**这解释了本书第四篇那个「双形态」架构的一个前提**：
§013 说浏览器版需要一个桥接进程，因为浏览器开不了 raw TCP。
**但如果 driver 开的是 WebSocket 端口，桥接就不需要了。**

本项目没有走这条路，原因很实际：
**上游 mudlib 的 `config.ini` 开的是 telnet 端口，而本项目的原则是不改 mudlib。**
§045 那句「mudlib 一个字节都不动」是整条路线的前提，
而它的代价之一就是多了一个桥接进程。

> **这是一个值得记录的替代方案**：如果允许改一行设置
> （加一个 `external_port_N : websocket …`），
> 浏览器版的 `bridge/server.mjs`（165 行）就可以整个删掉。

### ③ TLS

`external_port_N_tls : cert=cert.crt key=cert.key`——
**每个端口独立设置凭证**。
§040 提过 WASM 版把 TLS 整个移除（页面／浏览器自己负责），
而原生版有完整支持，包含 `sys_reload_tls` efun 可以热换凭证。

### ④ 数据库层

`db` 套件提供 SQLite3 / MySQL / PostgreSQL；
`async` 套件把查找丢进线程池。

**这对 LPC 是一个结构性的补丁**：§037 说过 LPC 是单线程、
无线程的事件循环，所以**任何阻塞操作都会冻住整个世界**。
`async_db_exec` 这类 efun 的存在，
与 §067 那个 LDMud 的 ERQ（把会阻塞的事赶出主行程）解的是同一个问题——
**只是 LDMud 用外部进程，FluffOS 用线程池。**

而 §052 那棵无 schema 的属性树，
在有了真数据库之后其实有了替代方案——
**但没有任何一份老 mudlib 会改**，理由在 §056 说过（时间轴）。

**解决的痛点**：这一节解的是一个认知问题——
**FluffOS 不是一个「MUD driver」，它是一台通用的应用服务器**，
只是它的脚本语言刚好叫 LPC。

它有：HTTP 静态服务、WebSocket、TLS、三种数据库、异步 I/O、
线程池、性能剖析、结构化调试日志、跨五平台建置与 CI。

**对照 §064 讲 DGD 时提过的那件事**——
1990 年代末 Yahoo 的聊天室跑在 DGD 上。
**这条血脉从来就不只是游戏引擎**，只是它的用户大多在做游戏。

**踩过的坑（本项目，诚实揭露）**：本项目在 §031 写下过一个结论——
「只要协议是原生 TCP、而运行环境是浏览器，中间就一定要有一个能开 socket 的进程」。
§032 记录了那个结论如何被 WASM 推翻（前提被拿掉）。

**现在要记第二次**：那个结论还有另一个出口，而且更早就存在——
**driver 本来就能开 WebSocket 端口。**

§032 的老手视角说「任何架构结论都加一句『这个结论在什么情况下会失效』」。
当时写的失效条件是「协议不再是远程 TCP」；
**漏掉的是「协议可以不是 TCP」——同一台 driver 就支持 WebSocket。**

**一个结论被同一份文档推翻两次，这件事本身值得写下来。**

**优点 / 罩门**：优点是这些能力全部是**可选的**——
不用就不会付出成本（tracing 只有一个分支、db 是编译期套件）。
罩门是**能见度**，和 §075 是同一个问题：
`docs/concepts/general/tracing.md` 有 11 KB，
而本项目做了四个月才知道它存在。

**效益**：这一节给的是一份「下次可以用」的清单：

| 想知道什么 | 用什么 |
|-----------|--------|
| LPC 哪个函数慢 | `trace_start()` → Chrome DevTools |
| 协商到底送了什么 | `driver -dtelnet -dconnections` |
| 某个档编不编得过 | `lpcc`（§075） |
| 不想写桥接 | `external_port_N : websocket` |
| 存盘数据处理 | `o2json` / `json2o`（§075） |

> 💡 君之一席话
> **一个结论被推翻两次，第二次通常比第一次更值得记**——第一次是前提变了，第二次是你一开始就没把选项看全。

> 🔍 老手视角──真正的门道
> 「instrumentation 永远编进去、只在需要时记录」这个取舍，是可观测性设计里最重要的一个决定。另一种做法是「特殊建置才有」（`-DPROFILE`），它的性能是零成本，代价是**你永远无法剖析正式环境**——而性能问题几乎只在正式环境才会出现（负载、数据量、真实使用模式）。老手几乎一律选前者：留下永远存在但缺省关闭的探针，付出百分之一到二的常态成本，换到「随时可以在出事的那台机器上开始量」。这个原则在 eBPF、在 Java 的 JFR、在 Chrome 的 tracing、在 OpenTelemetry 的 sampling 都是一样的。可落地的判准：**如果你的剖析工具需要重启服务才能激活，那它在真正需要的时候就用不上**——因为重启本身会清掉现场。

## 078　`mudlibs.fluffos.info` — 官方参考实作，与本项目的逐项对照

**标签**：`#参考实作` `#对照` `#方法论收敛` `#规模` `#诚实揭露`
**证据等级**：🟢 上游 `fluffos/mudlibs` 的 README 与管线 ＋ 🟢 本项目自己的实测数据（附录 F）

**起源**：本书 §045 提过一句：
「`mudlibs.fluffos.info` 是 FluffOS 社群做的中文 MUD 博物馆，
本项目的 `libs/` 布局就是参考它的」。

**那一句远远不够。** 那个项目和本项目在做同一件事——
**同一台 driver、同一种 WASM 打包、同一批中文 mudlib**——
而它的规模是本项目的十倍以上。

**这一节把两边逐项摊开比较**，因为对照组是本书从第一篇就在强调的东西。

**技术内核**：

### 规模

| | 上游 `fluffos/mudlibs` | 本项目 `libs/` |
|---|---------------------|---------------|
| 收录 | **200 份，158 个独立 codebase** | **17 份** |
| 年代范围 | 1990 年代中至约 2015 | 同 |
| 题材 | 武侠、仙侠为主 | 同 |
| 站点 | `mudlibs.fluffos.info`（GitHub Pages） | 本仓库的 `site/` |

> ⚠️ **数字的证据等级**：撰写当下该站首页显示「97 个可玩」，
> 而仓库 README 记的是「200 份／158 个 codebase」。
> **两者不冲突**——前者是**已通过 WASM 验证**的数量，后者是**已修复收录**的总数。
> 本书引用时分开标示。

### ★ 血缘判定：两边独立收敛到同一个方法

**上游的做法**（README 原文）：

> Lineage determined by **diffing core files (`master.c`, `chinese.c`,
> `logind.c`)** rather than relying on similar Chinese titles alone.

**本项目的做法**（§050）：用 `mudlib.json` 的**文件名集合算 Jaccard 系数**。

两边解的是同一个问题（**中文标题相似不代表同源**），
而且都拒绝了「靠名字判断」这条捷径。

| | 上游 | 本项目 |
|---|------|--------|
| 特征 | **三个内核档的内容** | **全部文件名的集合** |
| 精度 | 高（看内容） | 中（只看路径，§050 已标明此偏差） |
| 成本 | 要解开每一份封存 | **只读一张 JSON 索引** |
| 产出 | 编号体系（001–158，衍生版用 `-1`/`-2` 后缀） | 相似度矩阵（0.012 – 0.90） |

**两种方法互补而不冲突**：上游的精度高，本项目的成本低。
§050 那条「先挑最便宜的特征试一次，看分布有没有明显的断层」的建议，
在这里得到了对照——**断层确实存在（0.90 vs 0.012），所以便宜的特征够用。**

### 分级：上游五级，本项目三级

| 上游 | 意义 |
|------|------|
| `playable` | **完整注册 + 端到端游玩，且在 WASM 上验证过** |
| `limited` | 开得起来，但有已记录的但书 |
| **`native-boot verified`** | **原生跑得起来，WASM 待验** |
| **`partial`** | **政策上只支持原生** |
| `noboot` | 结构性失败，与转换无关 |

本项目只有 `playable` / `limited` / `noboot` 三级（附录 F）。

**差别在于上游把「原生」与「WASM」分开记**——
本项目只跑 WASM，所以没有这个维度。
**上游的分级更诚实**：一份「原生可跑但 WASM 待验」的 lib，
在本项目的体系里会被压成 `limited`，信息有损失。

### 管线逐项对照

| 阶段 | 上游 | 本项目 |
|------|------|--------|
| 解压 | `extract.sh`（zip/rar/7z/tar/**SFX 运行档**） | 手动 + `import-lib.mjs` |
| 转码 | `convert_lib.sh`：**GB18030 → UTF-8**，`.c` → **`.lpc`**，修正交叉引用 | `import-lib.mjs`：GBK → UTF-8（附录 F.5，最多单一 lib 29,853 档） |
| **静态检查** | **`lpcc_check.sh`——用 `lpcc` 批量编译每一个档** | ❌ **没有**（只有开机路径上的错误会被发现） |
| 原生烟雾测试 | `mudclient.py`（Python telnet 客户端） | ❌（本项目不跑原生） |
| WASM 测试 | `wasm_client.js` + `wasm_boot_check.js` | **`boot-test.mjs`**（注册→建角→进世界） |
| 打包 | `pack_lib_for_web.sh` | `pack-lib.mjs`（自订映像格式 `format: 1`） |
| 建站 | `build_site.sh` + `gen_site_index.py` + `wasm_status.json` | `build-site.mjs` |
| 部署 | `.github/workflows/pages.yml` | 本仓库根目录静态发布 |
| 全链路 | — | **`verify-fullstack.mjs`（真 DOM + 真 driver + 真 HTTP，§046）** |

**两个缺口与一个独有：**

- ❌ **本项目缺 `lpcc` 静态检查**（§075 已说明后果：玩家走不到的地方，错误不会被发现）；
- ❌ **本项目缺原生验证**（所以无法区分「WASM 问题」与「mudlib 问题」）；
- ✅ **本项目独有全链路 DOM 验证**——上游测的是 driver 能不能跑完登录，
  **本项目测的是「真浏览器 DOM ＋ 真 driver ＋ 真 HTTP」整条走完**，
  因为本项目的交付物是**客户端**，上游的交付物是**mudlib 收藏**。

### 版控策略：唯一的重大分歧

| | 上游 | 本项目 |
|---|------|--------|
| 进版控的是 | **`work/` 文件树**（可在 GitHub 上直接读 LPC） | **单一映像 `mudlib.data` + 索引** |
| 好处 | 可读、可 diff、可 PR | 写入快、`git status` 快 |
| 代价 | 十几万个小档 | **GitHub 上看不到原代码**，diff 只显示「二进位档已变更」 |

本项目的理由是量出来的（`libs/README.md`）：
跨 WSL 的 9P 文件系统**写入小档约 28 档／分**，
一个 mudlib 约一万个档 = **单一 lib 约 5 小时**，
16 个就是一整周。

> **这是一个环境限制导致的架构决定，而不是普遍更好的做法。**
> 上游没有这个限制（Linux 原生文件系统），所以选了可读性。
> **本项目的补偿是提供一行解开指令**（`unpack-lib.mjs`）。

### 其他技术细节对照

| 项目 | 上游 | 本项目 |
|------|------|--------|
| 扩展名 | **统一改成 `.lpc`** | 保留原样（`.c` 或 `.lpc`） |
| 设置档 | 统一 `config.fluffos` | **保留原名**（`config.ini` / `config.hell` / `config.xajh` / `config.sj`…，§039 那个坑的来源） |
| 管理帐号 | **统一 `fluffos` / `Mud@2026`**，且 `127.0.0.1` **绕过 IP ban 与连接节流** | 无（每个 lib 各自的登录流程） |
| 修复纪录 | 每 lib 一份 `NOTES.md` | 同（**由 `boot-test.mjs` 自动产生**） |
| bug 类别知识库 | **`AGENTS.md`：约 60 类 driver 兼容性 bug**（症状、根因、修法） | §032 的 **8 条通用修正** |

**最后一列值得停下来：本项目那 8 条，是上游那 60 类的一个子集。**

§032 说那八条「每一条修正都对应一次实测失败，而不是预防性猜测」——
这仍然是对的，但现在知道了**完整的问题空间有多大**：
本项目 17 份封存踩到 8 类，上游 200 份踩到约 60 类。

**这是一个很好的比例参考**：样本数 ×12，问题类别 ×7.5。
**问题类别的增长明显慢于样本数**——
说明兼容性问题有很强的长尾，但头部集中。

### 客户端：两边最大的差异

| | 上游 | 本项目 |
|---|------|--------|
| 前端 | **xterm.js 通用终端** | **懂 ZJMUD 方言的 GUI**（§024 的 18 个组件） |
| 对不讲方言的 lib | 没问题（终端机不需要理解内容） | 需要**会话层代打**（§045 `telnetlogin.js`） |
| 对讲方言的 lib | 显示原始 `ESC003…`（当成乱码） | **完整图形接口** |

**这一格把两个项目的目标差异讲完了。**

上游是**保存**：目标是让每一份 mudlib 能被跑起来、被看见。
用通用终端是正确选择——**它对所有 lib 一视同仁**。

本项目是**客户端实验**：目标是验证一套逆向出来的协议规格。
用专用 GUI 是必然选择——**否则没有东西可以验证**。

**所以 §045 那笔「额外费用的帐单」，
本质上是「选择了非通用客户端」的代价**，而不是谁做得不够好。

**解决的痛点**：这一节解的是本书一个潜在的误导。

前面十二篇累积了大量关于「中文 mudlib 长什么样」的分析（§049–§053），
而它们**全部基于 17 份样本**。
现在读者知道：**上游有 200 份，而且它的血缘判定方法比本项目精确。**

**本书的结论仍然成立**（断层明显、方法可重跑、每一条都标了偏差），
**但它的样本代表性有一个明确的上界，而那个上界现在有数字了。**

**优点 / 罩门**：本项目相对上游的优点只有一个，而且很窄——
**它验证的是客户端与协议，不是 mudlib 本身。**
罩门三个：样本少 12 倍、缺静态检查、缺原生对照。

**效益**：对任何要做类似事情的人，这张对照表就是一份路线图：
**要保存 mudlib，去看上游；要做客户端，本书第四到七篇还有用。**
两者不是竞争关系。

> 💡 君之一席话
> **找到那个在做同一件事、而且规模比你大十倍的项目，然后逐项比对**——这是校准自己结论可信度最快的方法，也是最不舒服的方法。

> 🔍 老手视角──真正的门道
> 两个项目在血缘判定上独立收敛到「不要相信名字、去比对内容特征」，这件事的意义比它看起来大：**当两批人在不知道对方的情况下解同一个问题、走到同一个方法上，那个方法通常抓到了问题的本质。** 这是一种很便宜的验证——比自己反复论证有效得多。老手在做技术决策时会刻意去找「别人怎么解同一个问题」，不是为了抄，是为了**看自己的方案是不是收敛点之一**：如果所有独立实作都走同一条路而你走了另一条，你要嘛有一个他们没有的约束（本项目的 9P 写入速度就是），要嘛你错了——**而这两者必须分清楚**。可落地的做法：任何一个你想了很久的方案，落地前花半天找两个独立的同类实作比对；**收敛的地方可以放心，分歧的地方写下你的理由**——那份理由清单，就是未来别人接手时最需要的东西。
