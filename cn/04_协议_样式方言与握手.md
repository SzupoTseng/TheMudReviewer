## 006　telnet 那一层 — 差点让连接在第一个字节就死掉

**标签**：`#telnet` `#IAC` `#MCCP2` `#UTF-8` `#字节层`
**证据等级**：🟢 实机封包（最高）

**起源**：规格书 v1.0 白纸黑字写着「原生 TCP，**非** telnet 选项协商」。这个断言来自客户端反编译——`mudsocketd` 就是开一条 socket、包一层 `BufferedReader`，完全没有处理 IAC 的痕迹。

三方交叉验证里的前两方（反编译、服务器 LPC 码）都没有反驳它。

然后真的连上去一次。

**技术内核**：服务器在连接创建的瞬间送出 **18 个字节**：

```
ff fd 18   IAC DO   TERMINAL-TYPE (24)
ff fd 1f   IAC DO   NAWS          (31)
ff fd 27   IAC DO   NEW-ENVIRON   (39)
ff fb 56   IAC WILL MCCP2         (86)   ← 压缩
ff fb 46   IAC WILL MSSP          (70)
ff fb 2a   IAC WILL CHARSET       (42)
```

这不是 mudlib 写的，是 **FluffOS driver 自己送的**——所以翻遍 `.c` 都找不到。这正是「实机封包能推翻原代码」的典型案例。

**不处理的两个致命后果**：

**① `0xFF` 不是合法 UTF-8。** 如果用 Rust 的 `BufReader::read_line` 读进 `String`，会直接回 `InvalidData`，读取任务当场结束——**连接在第一毫秒就死**，而且错误消息完全指不到真正的原因。

**② 误答应 MCCP2 会让整条连接变成 zlib。** 选项 86 是压缩协商。如果客户端回一个 `IAC DO 86`，服务器之后送的全是压缩串流，你会看到一堆二进位垃圾，且完全不知道发生什么事。

**正确作法**：

```
1. 在字节层剥除所有 IAC 串行，才做 UTF-8 解码
2. 协商一律拒绝：对方 WILL → 回 DONT；对方 DO → 回 WONT
3. 子协商 IAC SB … IAC SE 整段丢弃
4. IAC IAC 是「一个真正的 0xFF 数据字节」，还原成单一 0xFF
5. UTF-8 用宽容解码，坏字节换替换字符，不让一行毁掉整条连接
```

**解决的痛点**：让客户端在面对「文档没写、原代码看不到」的传输层行为时仍能存活。

**踩过的坑**：这一层在**两个地方各实作了一次**——桌面版是 Rust 的 `telnet.rs`（162 行），浏览器版是 JS 的 `bridge/telnet.mjs`（63 行）。两份逻辑必须一致，否则两种形态的行为会分歧。

处理方式是**共用测试数据**：两边的单元测试都直接用那 42 个实机字节当输入，断言剥除后等于 `\r\nver1.0:...\r\n`，且回复恰好是六组拒绝。**同一份事实，两份实作，一组断言。**

**优点 / 罩门**：全部拒绝协商的策略优点是**行为完全可预测**——不会有压缩、不会有子协商状态机。罩门是放弃了 NAWS（窗口大小回报），服务器无法依客户端宽度调整排版。对这套协议影响不大，因为版面本来就由 opcode 决定。

**处理策略对照**：

| 策略 | 实作成本 | 风险 |
|------|---------|------|
| **全部拒绝**（本项目） | 低，约 60 行 | 放弃 NAWS/CHARSET 等便利功能 |
| 选择性接受 | 中，需状态机 | 接受 MCCP2 就要实作 zlib 解压 |
| 完全忽略（不回复） | 最低 | 服务器可能等待逾时；仍须剥除字节 |

**效益**：一个 60 行的过滤器，换来连接层的绝对确定性。

> 💡 君之一席话
> **文档说没有、原代码看不到、两份反编译都同意——然后真机告诉你有。这就是为什么再完美的静态分析，都欠一次真正的连接。**

> 🔍 老手视角──真正的门道
> 这个坑的真正教训不是「要处理 IAC」，而是**「框架会替你做你不知道的事」**。mudlib 作者从没写过协商逻辑，因为那是 driver 的行为；反编译者看不到，因为那在 Java 的 socket 层之下。老手在逆向网络协议时有一条铁律：**先抓一次原始字节再说**——`tcpdump` 或一支二十行的 socket dump，成本是十分钟，能省掉的是「为什么连上就断」这种毫无线索的调试。可落地的提醒：任何「文档说很单纯」的传输层，都值得花十分钟亲眼看一次十六进位。

## 007　ANSI 扩充方言 — 那个要人命的冒号

**标签**：`#ANSI` `#SGR` `#样式` `#超链接` `#ARGB`
**证据等级**：🟡 服务器宏 ＋ 🟢 实机封包

**起源**：payload 内的文本不是纯文本，而是带样式的。ZJMUD 用 ANSI SGR 当基础，再加上四项自己的扩充。这一层决定了画面「好不好看」，也决定了「点不点得动」。

**技术内核**：文本先以 `ESC` 切段，每段开头是样式指令，其后是套用该样式的文本。**样式是跨段有状态的**——设置后持续生效，直到 `[0m` 或任何以 `;0m` 结尾的码把它重置。

标准的部分照抄 ANSI，但**用的是自订调色板**（`[32m` 是 `#00bb00` 而不是纯绿）。真正的扩充有四个：

| 指令 | 语意 | 陷阱 |
|------|------|------|
| `[f#RRGGBBm` | 自订前景色 | 色码可能是 **8 位 ARGB** |
| `[b#RRGGBBm` | 自订背景色 | 同上 |
| `[s:<n>]` | 字级 = 画面宽 ÷ n | **以 `]` 收尾，且参数前有冒号** |
| `[u:<url>]` | 超链接 | **同上** |
| `[9m` | 全角模式 | 后续 ASCII 转 U+FF01–U+FF5E |

**那个冒号**是这一层最贵的细节。服务器宏写得很清楚：

```c
#define ZJURL(w)    ESA + "[u:" + w + "]"
#define ZJSIZE(n)   ESA + "[s:" + n + "]"
```

客户端取值是 `substring(3, indexOf("]"))`——索引 3 正好跳过 `[`、`u`、`:`。少跳一个字符，URL 就变成 `:cmds:look`，**所有可点击链接全部失效，而且不报错**。

实机封包最终证实了这一点：

```
ESC[u:cmds:uplv -l]【角色等级】ESC[0m
```

**ARGB 是第二个陷阱**。服务器实际送的颜色长这样：

```c
sprintf("气血.%d:%d/%d/%d:%s", ..., "#99FF0000")
```

`#99FF0000` 是 **alpha 在前**的 ARGB。直接丢给 CSS 会被当成 RGBA 解读，颜色完全错。转换时必须把 alpha 从头搬到尾：`#99FF0000` → `#FF000099`。

**解决的痛点**：让服务器能在纯文本里表达「这几个字可以点」「这段放大显示」「这个颜色半透明」，而不需要另一条数据信道。

**踩过的坑**：链接的 scheme 有五种，其中两种是官方文档才揭露的：

```
cmds:    送出指令（最重要，服务器用它把任意词句变成按钮）
pops:    打开弹出菜单
voice:   播放语音
tel:     拨打电话      ← 官方文档才有
mailto:  打开邮件      ← 官方文档才有
```

`cmds:` 是整套协议最灵活的机制——它让服务器可以把叙述文本里的任何一个词变成可点击的指令，不需要预先定义按钮。

**优点 / 罩门**：状态式样式的优点是**省带宽**（设置一次持续生效）。罩门是**解析器必须维护状态**，而且一旦某段的重置码遗失，后面全部的颜色都会错——这种 bug 极难重现，因为它取决于前面送过什么。

**两种标记形式对照**：

| 形式 | 样貌 | 用户 | 安全性 |
|------|------|--------|--------|
| **ANSI 式** | `ESC[u:cmds:look]文本ESC[0m` | 经典与大梦江湖 | 安全，解析器完全控制 |
| **HTML 式** | `<a href="cmds:look"><span>文本</span></a>` | 指游 web 版 | ⚠️ 服务器可送任意标记 |

**效益**：一套样式方言让纯文本接口拥有可点击、可缩放、可着色的能力，且对不支持的客户端只是多了几个怪字符。

> 💡 君之一席话
> **一个冒号的差别，能让整个接口看起来完好无缺、却一个字都点不动——这种错误不会让程序崩溃，只会让它安静地失去灵魂。**

> 🔍 老手视角──真正的门道
> `[s:` 和 `[u:` 以 `]` 收尾而非 `m`，是这套方言最反直觉的设计，也是最容易写错的地方——因为 ANSI 解析器的惯性写法就是「找第一个 `m`」。老手在实作任何「扩充自标准」的方言时，会先做一件事：**把所有不遵守标准的例外列成一张表，放在解析器的最前面优先处理**。本项目的 `ansi.js` 正是这样排序：先判 `[u`、`[s`（以 `]` 收尾），再判 `[2J`、`[H`（屏幕控制），最后才进入「找 `m`」的通用路径。这个顺序不是美学，是正确性——**例外必须在通则之前被拦截**。另外那个 HTML 式标记值得警惕：它意味着服务器可以送任意 HTML 到客户端，实作时绝不能直接 `innerHTML`，必须白名单标签与属性。这是协议设计把安全责任外包给客户端的典型案例。

## 008　登录握手 — 三种写法，三种字段数

**标签**：`#握手` `#状态机` `#方言判别` `#逾时` `#验证`
**证据等级**：🟡 三份服务器来源 ＋ 🟢 实机

**起源**：连上之后服务器送的第一行决定了后续一切。问题是——**这一行有三种写法**。

**技术内核**：

| 写法 | 出处 | 对应方言 |
|------|------|----------|
| `ver1.0:<crypt>` | LPMud-Name `logind.c` | 经典／大梦江湖 |
| `ver1.0,<crypt>` | 官方协议文档 | 经典（**逗号不是冒号**） |
| `version 1.0 key::<crypt>` | 指游转换教程 | 指游 ZY |

只认其中一种，另外两种服务器就**完全连不上**。

更麻烦的是**字段数也随方言变动**：

| 消息 | 经典 | 官方文档 | 指游 |
|------|------|----------|------|
| 登录 | `帐号║密码║密文║email`（4 栏） | `帐号║密码║密文`（3 栏） | 4 栏 |
| 建角 | `性别║头像║暱称`（3 栏） | 3 栏 | **`性别║暱称`（2 栏）** |

服务器端是 `sizeof(myinfo)!=N` 的严格检查，**字段数不对直接退回**。

因此正确的设计是：**用第一行同时决定 opcode 表与后续所有字段数**。一个字符串，三个下游决策。

**登录状态机**（实机逐步验证过）：

```
连接 → ver1.0 挑战
     ├─ 有记住的帐密 ──▶ 两行连发（版本回复 + 帐号行）
     └─ 没有 ──────────▶ 跳出登录表单
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
        ESC000 "0007"                   ESC000 "0008"
        登录成功                         帐号无角色 → 建角表单
```

`ESC000` 的 payload **既可能是数字状态码、也可能是中文本串**（`重连完毕`），实作不能假设只有一种。

**解决的痛点**：让同一个客户端能连上三种不同世代的服务器。

**踩过的坑**：这一节有本项目**最严重的一次设计失误**——

初版**没有登录接口**。设计时把「登录」列为已知限制，要用户自己在指令列打三行：版本回复、帐号串、建角串。

但服务器对「连上到登录完成」有时限。人工打字**赶不上**，于是变成：

```
连接 → 逾时被踢 → 自动重连 → 又逾时 → 再踢 → …
```

画面只会反复刷 `ver1.0:...` 和「您花在连线进入手续的时间太久了」。**客户端在功能上完全不可用**，而我把它写成「已知限制」就放着了。

修法是让客户端接手握手：侦测到挑战就跳表单，送出时**两行连发在同一个 tick**，不给服务器逾时的机会。同时加上「连续 3 次逾时就停止自动重连」的止血。

**优点 / 罩门**：由客户端接手握手的优点是用户体验完整，且能在前端先验格式（ID `^[a-z][a-z0-9_]{3,19}$`、角色名 2–4 个中文本），省一次往返。罩门是**客户端无法通过官方的完整验证**——

官方设计是：
```
服务器 → ver1.0,<crypt(ZJKEY, 0)>
客户端 → crypt(ZJKEY, str[2..3])       ← 由官方网关产生
客户端 → 帐号║密码║crypt(ZJKEY,帐号)+crypt(ZJKEY,密码)
```

`ZJKEY` **只存在于服务器端**，第三方客户端拿不到。实务上绝大多数自架服务器把这段检查注解掉了，所以能用固定值蒙混——但这是服务器的宽容，不是协议的允许。

**效益**：一个握手判别函数，让客户端同时兼容三个世代的 mudlib。

> 💡 君之一席话
> **把「用户自己打三行指令」写成已知限制，听起来很诚实——但如果服务器根本不给人打字的时间，那不是限制，是不能用。**

> 🔍 老手视角──真正的门道
> 这里最值得学的是**「已知限制」这四个字的滥用风险**。它本来的意思是「这个功能没做，但不影响内核可用性」；一旦它掩盖的其实是「内核流程走不完」，它就变成一张自我安慰的贴纸。老手审视任何「已知限制」清单时，会逐条问一个问题：**「用户能不能在没有这个功能的情况下，完成一次完整的内核任务？」**——不能的话，它就不是限制，是缺陷。可落地的做法：把「已知限制」拆成两栏——**「缺功能」**和**「挡流程」**，后者一律当 bug 处理，不准留在文档里过夜。
