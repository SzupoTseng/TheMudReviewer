## 导读　三个面向的判读学

在翻开任何一章之前，先花五分钟搞清楚一件事：**你手上的每一条「协议知识」，可信度都不一样。**

这是逆向工程最容易被跳过、也最致命的一课。多数人失败不是因为看不懂汇编语言，而是因为**把「我推论出来的」和「我验证过的」混在同一张表里**，然后在三个月后的某个深夜，被自己三个月前的乐观judge打脸。

---

### 一、三个面向，三种功夫

| 面向 | 符号 | 内核问题 | 失败的样子 |
|------|------|---------|-----------|
| **逆向** | 🔬 | 这个字节凭什么是这个意思？ | 「看起来像」就写进规格，半年后全盘崩溃 |
| **架构** | 🏛 | 怎么让协议知识不污染 UI？ | 解析器直接操作画面，改一行协议要动十个文件 |
| **工程** | 🔧 | 怎么证明它真的能跑？ | 测试全绿、真机全挂 |

三者的难度曲线完全不同。**逆向的难点在「证据」，架构的难点在「边界」，工程的难点在「你以为你测了」。**

这个项目在逆向上做得还行，在架构上算干净，但在工程上摔得最重——连续四次把「不能用」的东西交出去。原因后面会讲到。

---

### 二、证据等级：本书的度量衡

每一条协议断言，都必须能回答一个问题：**你怎么知道？**

#### 🟢 实机封包（最高）

真的创建连接、真的抓到字节。这是唯一能推翻其他所有来源的证据。

```
ff fd 18 ff fd 1f ff fd 27 ff fb 56 ff fb 46 ff fb 2a
0d 0a 76 65 72 31 2e 30 3a ...
```

这 42 个字节是本项目最贵的一份证据——它一口气推翻了「这协议没有 telnet 协商」这个写在文档里的断言，也解释了为什么一个用严格 UTF-8 解码的读取器会在连接的第一毫秒就死掉。

**它的限制**：你只能看到服务器「这次」送了什么。没触发的功能，你看不到。

#### 🟡 服务器原代码（高）

LPC 的 `#define` 与 `.c` 里的实际发送点。

它比反编译强，因为它是**作者亲手写的意图**，而且常常带中文注解。但有一个巨大的陷阱：

> **「定义了」不等于「用得到」。**

本项目扫过的一份 header 定义了 **102 个 opcode**，实际在 `.c` 里被使用的只有 **16 个**——其余 86 个是从别处拷贝过来的，从未出现在线路上。如果只看 header 就开工，会为了七十几个永远不会出现的 opcode 写一堆处理器。

**判读规则**：看 header 知道「可能有什么」，看 `.c` 才知道「真的有什么」。

#### 🟠 客户端反编译（中）

从 APK 还原出的 Java。

它证明的是**「客户端会怎么解读」**，不是「服务器会怎么送」。这两件事有时不一致——本项目就抓到一段客户端里的 `ESC006` 分支写了两次，第二次因为 if/else 链的顺序**永远不可能被运行**。那是一段死码，照着它实作只会浪费时间。

**它的独门价值**：反编译能看到服务器原代码看不到的东西——**客户端自己的行为**。例如「收到某个字符串就自动回送 `l`」这种客户端主动逻辑，只有反编译看得到。

#### 🔴 推论（最低，但不可避免）

由结构相似性推得。例如「这个 payload 长得像那个已知格式，所以应该也是同一套解析」。

**推论不是罪，隐藏推论才是。** 本书所有推论都明确标注，并且优先安排验证。第二篇有两处被标为「未验证」的字段，后来一处被服务器原代码证实、一处被证伪——证伪的那次，如果没标，就是一个潜伏半年的 bug。

### 二之二、后来扩充的三种来源（第八、九篇）

前四级是为了**还原一套私有协议**而定的。第八、九篇把镜头转向服务器那一端（driver、mudlib、客户端史），出现了三种原本的分级涵盖不到的来源。它们的位阶如下：

#### 🟡 上游官方文档与原代码

FluffOS 的 `docs/`、`src/`。它与「服务器原代码」同级（🟡），理由一样——**它是作者亲手写的意图**，而且同一个陷阱也适用：

> **文档写了不等于这台 driver 编了。**

§048 整节在讲这件事：能力面是**编译期**决定的，所以「官方文档说有这个 efun」与「你手上这台有」是两回事。**对照 header 与 `.c` 的规矩，在这里变成对照文档与套件矩阵。**

#### 🟡 一手史料（同时代的原始文献）

`Credits.LPmud`（1989）、`History.MudOS`（1992 年的 Usenet 贴文）、TMI-2 的档头署名。

它们的可信度来自一个性质：**写的时候还不知道后来会怎样**。1992 年那篇贴文不是回忆录，是当事人在骂战中途写的辩护文——**它有立场，但没有事后诸葛的空间**。

**判读规则**：一手史料证明「当时有人这样说」，不证明「事实如此」。所以 §034 引它时，引的是**可查证的技术细节**（版号怎么烂掉、哪些子系统重写了），而不是它对动机的自述。

#### 🟢 可重跑的量测

§050 的 Jaccard 血缘矩阵、附录 F 的开机测试、§055 的实测字节。

它与「实机封包」同级（🟢），因为它有实机封包唯一重要的那个性质：**别人可以重跑，并得到相同结果**。附录 F 因此附上了每一张表的重跑指令。

**但它有一个实机封包没有的弱点**：量测有**方法**，而方法有偏差。所以本书的规矩是——

> **每一张量测表都必须写明「它会漏掉什么」。**

附录 F 的 opcode 分布表附了两条已知偏差；§050 的血缘量测写明它量的是路径而非内容；§005 的 opcode 频率统计在 §052 发现漏算之后，补上了那条说明。**一个标了偏差的量测是证据，没标的是宣传。**

#### 扩充后的完整顺序

```
🟢 实机封包 ≈ 🟢 可重跑量测（需附方法与偏差）
      >  🟡 服务器原代码 ≈ 🟡 上游文档 ≈ 🟡 一手史料
            >  🟠 客户端反编译  >  🔴 推论
```

**同级之间冲突怎么办？** 本书遇过一次，处理方式记在附录 D.3：史料说「侠客行 1996 年外流导致大量分支」，量测看到「16 份 lib 彼此 0.44–0.90」，档头写着 `Creator : ken@XAJH`——**三条独立的线指向同一张图，才算钉死**。如果只有其中一条，本书会标成推论。

### 三、每一节的固定骨架

为了让不同性质的主题可以被横向比较，本书每个「单元」都用同一套结构：

> **标签 → 证据等级 → 起源 → 技术内核 → 解决的痛点 → 踩过的坑 → 优点／罩门 → 对照表 → 效益**，最后收在一句「君之一席话」与一段「🔍 老手视角」。

其中两栏是本书的偏心：

- **证据等级**不是装饰。它让你在三个月后回头看时，知道哪些结论可以直接信、哪些要重验。
- **踩过的坑**写的是**真的发生过的事**，包含当下的错误判断。不美化。

### 四、给不同读者的路径

**想学逆向的**：第一篇 → 第二篇 → 附录 A。重点在「怎么把猜测逼成证据」。

**要接手这个项目的**：导读 → 第四篇 → 第五篇 → 附录 B。重点在架构边界与已知的坑。

**要写自己的 MUD 客户端的**：第二篇 → 第三篇。那是完整的协议规格。

**只想看教训的**：直接翻第五篇。七次事故，七种完全不同的死法。

### 五、关于数字

书里所有的行数、opcode 数量、测试数量，都是**撰写当下实际数出来的**，不是估计：

| 项目 | 数量 |
|------|------|
| 产品代码 | 约 6,613 行（前端 JS 4,428、Rust 455、桥接 191、HTML/CSS 1,370、WASM 绑定 524） |
| 测试代码 | 约 2,756 行 |
| 测试数量 | **202 条**（12 个文件，全过） |
| 内核 opcode | 27 个（14 个 mudlib 共用） |
| 扩充 opcode | 89 个（跨三个方言，其中 4 个撞号） |
| 实机验证的封包 | 53 行 |

**测试代码占产品代码的 42%**——这个比例不是刻意追求的，是被七次事故逼出来的。

> 数字会长大：本书初稿时是 4,977 行产品码／177 条测试，第八、九篇写成时已是 6,613 行／202 条。
> **书里所有数字都标了「撰写当下」，并且附上重数的方法**（附录 B、附录 F.6）——
> 一个数字如果没有办法重新量一次，它迟早会变成谎言。

> 💡 君之一席话
> **在黑箱面前，最危险的不是无知，而是「我觉得我知道」——证据等级这件事，本质上是替未来的自己标好哪些话不能信。**

> 🔍 老手视角──真正的门道
> 资深工程师看逆向项目，第一眼不看「解出了多少」，而看**「有没有可重跑的验证管道」**。一个能一键连上真机、抓封包、跑过解析器并报告失败数的探针，价值远高于一份漂亮但静态的规格书——因为协议会变、服务器会改版，而规格书不会自己告诉你它过期了。本项目最终把 53 行实机封包固化成回归测试，正是为了让「协议变了」这件事在 CI 就爆出来，而不是在用户面前。可落地的做法：任何逆向项目，**第一天就先写探针，再写规格**——先有量尺，再谈测量。
