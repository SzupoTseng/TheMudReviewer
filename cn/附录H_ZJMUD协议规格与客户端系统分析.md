### H.0.2　规范用语

本附录采 RFC 2119 精神，但用中文表述：

| 用语 | 意义 |
|------|------|
| **必须** | 不做就无法与既有服务器互通，或会造成连接中断／数据遗失 |

## H.1　传输层

### H.1.1　总览

| 项目 | 值 | 等级 |
|------|-----|------|
| 协定 | 原生 TCP（**非** WebSocket、**非** HTTP） | 🟢 |
| 分帧 | 以 `\n` 分行；一行 = 一个协议单元。服务器实际送 `\r\n` | 🟢 |
| 编码 | **依端口而定**，见 H.1.4 | 🟡🟢 |
| 加密 | **无** | 🟢 |
| Keep-alive | 打开 socket `SO_KEEPALIVE` | 🟠 |
| 服务器地址 | 由帐号侧信道下发（H.6.2），**不写死** | 🟠 |

整条管线由外而内共四层，每一层都必须完整剥完才能进下一层：

```
┌────────────────────────────────────────────────────────────┐
│ ① TCP 字节流                                              │
│   └─ ② telnet IAC 协商（必须在字节层剥除，H.1.2）          │
│       └─ ③ 文本解码（UTF-8 或 GBK，依端口，H.1.4）             │
│           └─ ④ 以 \n 分行 → 每行一个协议单元                 │
│               └─ ⑤ 行首 opcode：ESC + 3~4 字符（H.2）        │
│                   └─ ⑥ payload：$zj# 分记录、: 分字段（H.4） │
│                       └─ ⑦ 字段文本内：样式方言（H.5）        │
└────────────────────────────────────────────────────────────┘
```

> ⚠️ **层序不可对调。** 最常见的致命错误是「先做 UTF-8 解码，再剥 IAC」——
> IAC 的 `0xFF` 不是合法 UTF-8，严格解码器会在这里直接失败。见 H.1.3。

### H.1.2　telnet 选项协商（必须处理）🟢

连接创建后，服务器**立刻**送出 18 个字节，共 6 组协商：

```
ff fd 18   IAC DO   TERMINAL-TYPE (24)
ff fd 1f   IAC DO   NAWS          (31)
ff fd 27   IAC DO   NEW-ENVIRON   (39)
ff fb 56   IAC WILL MCCP2         (86)   ← 压缩，必须拒绝
ff fb 46   IAC WILL MSSP          (70)
ff fb 2a   IAC WILL CHARSET       (42)
```

**客户端必须实作的五条规则**

| # | 规则 |
|---|------|
| 1 | 在**字节层**（不是字符串层）剥除所有 IAC 串行，剥干净之后才做文本解码 |
| 2 | 对协商**一律拒绝**：收到 `IAC WILL x` → 回 `IAC DONT x`；收到 `IAC DO x` → 回 `IAC WONT x` |
| 3 | 子协商 `IAC SB … IAC SE` **整段丢弃** |
| 4 | `IAC IAC`（`ff ff`）是「一个真正的 0xFF 数据字节」，必须还原成单一 `0xFF` |
| 5 | 文本解码**应**用宽容模式（坏字节换成替换字符），不让一行坏数据弄断整条连接 |

**不处理的两个后果**

| # | 后果 | 症状 |
|---|------|------|
| 1 | `0xFF` 不是合法 UTF-8 | 严格逐行读取器在第一个字节回 `InvalidData` 并中止 —— **连接瞬间死掉，且看起来像「连不上」** |
| 2 | 误答应 **MCCP2（选项 86）** | 服务器之后改送 zlib 压缩串流，整条连接变成无法解读的二进位 —— **看起来像「协议完全错了」** |

> ⚠️ 这两个症状都会把人引到错误的方向去查。
> 第 1 个像「服务器没开」，第 2 个像「opcode 表抄错了」。
> 实作时**第一件事**就是把 IAC 剥干净并印出剥除后的前 200 个字节确认。

### H.1.3　为什么不能用「标准的逐行读取器」🟢

多数语言的标准库都有「从串流读一行」的便利函数（例如 Rust `BufReader::read_line`、
Python `socket.makefile().readline()`）。**这些函数在此协议上不能直接用**，理由有二：

1. 它们多半在内部做严格 UTF-8 检查 —— 撞到 IAC 的 `0xFF` 就失败
2. 它们把「分帧」与「解码」绑在一起，而本协议必须**先剥 IAC、再解码、最后分帧**

**正确的读取管线**

```
loop:
  buf ← 从 socket 读取任意长度的字节
  (clean, replies) ← telnet_filter(buf)      # 剥 IAC，产生要回送的拒绝封包
  若 replies 非空 → 写回 socket
  accum ← accum + clean
  while accum 中含有 \n:
      line, accum ← accum 以第一个 \n 切开
      line ← line 去掉结尾的 \r
      text ← decode(line, encoding)          # 宽容模式
      dispatch(text)                          # 进 H.2
```

> ⚠️ `telnet_filter` **必须是有状态的**。IAC 串行可能跨越两次 `read` 的边界
> （例如这次读到 `ff fd`，下次才读到 `18`）。无状态的实作在网络稍有抖动时就会漏剥。

### H.1.4　端口与编码 🟡

出处 `world/adm/single/master.c` 的 `connect(int port)`：

```c
object connect(int port)
{
    if (port == 5003){
        set_encoding("GBK");     // ← 只有 5003 是 GBK
    }
    ...
}
```

| 端口 | 编码 | 用途 | 新客户端 |
|----|------|------|---------|
| **5001** | **UTF-8** | 行动／Web 客户端 | ✅ **连这个** |
| 5003 | **GBK** | 传统 telnet 客户端（ZMud／MushClient） | 仅兼容需求时 |
| 5004 | UTF-8 | driver 内置 websocket | 视部署而定 |

> ⚠️ **连错端口的症状是「整页中文乱码」，不是「连不上」。**
> 这一点每年都会骗走一些人半天：画面出得来、按钮也在、就是字全花——
> 于是去查样式解析器，其实只是端口号差 2。
> **先确认端口，再怀疑解析器。**

### H.1.5　送出方向 🟡

送出即「写一行文本 + 换行」。指令就是 MUD 原生指令字符串（`look`、`north`、`score`…）。

**多行指令模式**由服务器以 opcode 控制：

| 模式 | 触发 opcode | 行为 |
|------|------------|------|
| `multiline = true`（**缺省**） | `ESC998` | 字符串内的 `\n` 原样送出 |
| `multiline = false` | `ESC997` | 送出前把字符串内所有 `\n` 取代为 `;` |

`;` 是 LPMud 惯用的「一行多指令」分隔符。此开关让服务器决定客户端要用哪种方式打包复合指令。

## H.2　行级分派

### H.2.1　前置样式重置 🟢

若整行以 **`ESC[2;37;0m`**（9 个字符）开头：

1. 清空所有目前套用中的样式状态（前景色、背景色、粗体、字级、链接、全角旗标）
2. 从第 10 个字符起继续当作正常行处理

> ⚠️ **这个重置码可能出现在 opcode 之前，也可能在之后。**
> 实机数据同时存在 `ESC[2;37;0mESC002…` 与 `ESC002ESC[2;37;0m…` 两种顺序。
> 取 opcode 的进程**必须**两种都能处理，否则第二种会被当成无 opcode 的一般消息，
> 房间标题就永远不会更新。

### H.2.2　opcode 截取（变长）🟢🟡

opcode 的形式是 **`ESC`（U+001B）+ 3 个或 4 个 ASCII 英数字元**。

**这里有两个陷阱，两个都会让画面大面积坏掉：**

| 陷阱 | 错误写法 | 后果 |
|------|---------|------|
| 以为一定是「三个**数字**」 | `/^\d{3}$/` | `10a`、`11a`、`2k1`–`2k4` 这些扩充码被当一般消息，**整段内容连同控制字符印在画面上** |
| 以为一定是「**三**个字符」 | 固定 `slice(1,4)` | `ESC1085`（地图）被解成 `108`，多出来的 `5` 混进内容开头 |

**规范算法**

```
parse_line(raw):
  1. raw 非字符串 → { op: null, payload: "" }
  2. 若 raw 以 ESC + "[2;37;0m" 开头 → reset_styles = true；raw ← raw 去掉前 9 字符
  3. 若 len(raw) < 4 或 raw[0] != ESC → { op: null, payload: raw }
  4. three ← raw[1:4]
     若 three 不符合 /^[0-9a-z]{3}$/i → { op: null, payload: raw }
  5. four ← raw[1:5]
     若 four 符合 /^[0-9a-z]{4}$/i
        且 is_known(four)
        且 NOT is_known(three)          ← 两个条件缺一不可
        → { op: four, payload: raw[5:] }
  6. 否则 → { op: three, payload: raw[4:] }
```

`is_known(op)` = 该 op 存在于内核表 **或**「目前生效的方言 profile」的扩充表中（见 H.3.3）。

> ⚠️ **第 5 步的 `NOT is_known(three)` 不能省。**
> 少了它，`ESC004` 后面接「5 个人站在这里」会被读成 `ESC0045`（打开网页），
> 房间描述消失、还会试图打开一个叫「个人站在这里」的网址。
> 这是变长 opcode 唯一安全的消歧义规则：**三字符优先，只有在「四字符认得而三字符不认得」时才升级。**

### H.2.3　分派结果

| 情况 | 处理 |
|------|------|
| opcode 命中表 | 依该 opcode 的规则处理，payload = opcode 之后的剩余内容 |
| opcode 未命中 | **整行**（含原始控制字符）视为一般消息送进主消息区，并标记 `unknownOpcode` |
| 无 opcode | 整行视为一般消息 |

> ⚠️ **未知 opcode 绝不可静默丢弃。**
> 丢弃的后果是「换一个 mudlib 之后，某些内容凭空消失，而且完全不会报错」——
> 这种 bug 可以藏好几个月。正确作法是降级显示并打标记，让它**吵**。

### H.3.2　实作优先级（依服务器实际发送量）🟡

这是本附录最有价值的一张表。它来自对服务器约 4,000 处发送点的统计：

| opcode | 宏 | 发送点数 | 意义 |
|--------|------|--------:|------|
| `ESC007` | `ZJOBLONG` | **531** | 目标详情 |
| `ESC009` | `ZJOBACTS2` | **448** | 动作列② |
| `ESC001` | `INPUTTXT` | **147** | 文本输入 |
| `ESC014` | `ZJFORCECMD` | **98** | 服务器代送指令 |
| `ESC015` | `ZJTMPSAY` | 44 | 顶部飘字 |
| `ESC008` | `ZJOBACTS` | 30 | 动作列① |
| `ESC003` | `ZJEXIT` | 16 | 出口 |
| `ESC006` | `ZJBTSET` | 10 | 自订按钮 |
| `ESC000` / `ESC011` | `SYSY` / `ZJMAPTXT` | 各 8 | 状态／地图 |
| `ESC021` | `ZJTTMENU` | 5 | 标题列按钮 |
| `ESC005` / `ESC012` / `ESC022` | | 各 4 | 对象／属性条／血条 |
| `ESC010` | `ZJYESNO` | **0** | ← 对话框在此服务器**完全没用到** |
| `ESC016` / `ESC017` | `ZJFMSG` / `ZJFNOMSG` | **0** | ← 战斗面板未激活 |
| `ESC913` / `ESC023` / `ESC999` | | **0** | 未使用 |

**三个直接可用的结论**

1. **先做 `007` + `009`。** 这两个合计近 1,000 处，几乎所有 NPC 交互都走这条路。
   做完这两个，玩家 95% 的时间都有东西看。
2. **`014` 必须做，而且要早做。** 服务器用了 98 次来「叫客户端代送指令」驱动流程。
   不实作的症状是**交互走到一半莫名其妙卡住**，而且画面上完全没有错误迹象。
3. **`010` 对话框可以最后做。** 它在这台服务器 0 次使用；NPC 交互走的是 `007`+`009`。
   ——但别把它从表里删掉，其他 mudlib 会用。

> 🔍 老手视角──真正的门道
> 拿到一份新协议时，多数人按 opcode 编号从 `000` 开始往下实作。这是最慢的路径。
> **正确的第一步是去服务器原代码里数「每个 opcode 被发送几次」**，然后照次数由大到小做。
> 上面那张表就是这么来的：它把「33 个 opcode」压缩成「先做 4 个就能玩」。
> 更重要的是它会告诉你哪些是**定义了但没人用的**（`010`/`016`/`017`/`913` 全是 0）——
> 那些如果按编号顺序做，你会在完全没有回报的地方花掉好几天。

### H.3.3　方言 profile（撞号隔离）🟡

扩充 opcode **不得**合并成单一张表。已知撞号：

| opcode | 大梦江湖 | 指游 ZY |
|--------|----------|--------|
| `602` | 主页文本 | NPC 状态 |
| `603` | 主页文本 2 | 战斗按钮 |
| `604` | 判断界面 | 操作面板 |
| `605` | 更改界面 | **清空主画面** |

合并的后果：后定义的静默覆盖前者，画面上表现为「某些功能莫名其妙变成别的东西」，
**而且完全不会报错**。特别是 `605` —— 一边是「更改界面」、一边是「清空主画面」，
合并之后会出现「玩家打开某个面板，主画面消息全部消失」这种极难追查的现象。

**规范作法**

1. 每个方言是一个独立的 **profile**，各自持有自己的扩充表
2. 由连接第一行的版本挑战字符串决定套用哪个 profile（见 H.6.1）
3. 查表顺序：**内核表 → 目前 profile 的扩充表 → 未知**
4. `is_known()`（H.2.2）只查内核表与**目前**profile

### H.3.4　扩充 opcode 只有 8 种结构 🟡

61 个扩充 opcode 摊开来看，payload 结构只有 8 种，且全部与内核 opcode 同构：

| 结构 | 说明 | 同构的内核 opcode |
|------|------|------------------|
| `TITLE` | 面板标题（样式文本） | — |
| `TEXT` | 内文（可含 `$br#`） | `ESC004` / `ESC007` |
| `LIST` | `label:cmd` × `$zj#` | `ESC005` / `ESC021` |
| `ACTIONS` | 带版面前缀的按钮网格 | `ESC008` / `ESC009` |
| `BARS` | `║` 分隔的数值条 | `ESC012` |
| `ENTITY_ADD` | `id$zj#名字$zj#a:b:max` | `ESC005` + `ESC022` |
| `ENTITY_DEL` | id | `ESC905` |
| `MESSAGE` | 进某个消息频道 | `ESC015` / `ESC016` / `ESC100` |

> 💡 这是整个扩充层最重要的一个发现：
> **不需要为 61 个扩充 opcode 各写一个处理器。**
> 只要一张「opcode → 结构 + 目的面板」的对照表，再加上 8 个结构解析器即可。
> 工作量从「61 个 handler」降到「一张表 + 8 个函数」。

## H.4　payload 结构（逐 opcode 规范）

### H.4.0　通用分隔符 🟡

| 标记 | 用途 | 适用范围 |
|------|------|---------|
| `$zj#` | **记录分隔符**（主力） | 几乎所有结构化 opcode |
| `$z2#` | 记录分隔符 | ⚠️ **仅** `ESC020` 弹出菜单 |
| `$br#` | 换行（等同 `\n`） | 样式文本、按钮标签 |
| `$dh#` | 对话框区块分隔 | 仅 `ESC010` |
| `$sock#` | 指令串行分隔（一次送多条） | 仅 `ESC010` 的确定钮 |
| `:` | 字段分隔符 | 通用 |
| `\|` | 次级字段（主标题 \| 副标题） | `ESC008`/`ESC009`/`ESC020` |
| `║` (U+2551) | 属性条记录／登录字段 | `ESC012`、登录握手 |
| `$N` | 数量占位符 | ⚠️ **仅** `ESC010` |
| `$txt#` | 输入占位符／保持面板打开旗标 | ⚠️ **仅** `ESC001` 与 `ESC008`/`ESC009` |

> ⚠️ **`$N` 与 `$txt#` 是两套完全不同的机制，不可混用。**
> `$txt#` 是 `ESC001` 的「把用户输入的**自由文本**塞进样板」；
> `$N` 是 `ESC010` 的「把用户选的**数量**塞进指令」。
> 这是本项目规格书 v1.0 两个错误中的一个，代价是整个文本输入功能做错方向。

### H.4.0.1　版面前缀（optional layout header）🟡

`ESC008` / `ESC009` / `ESC012` / `ESC020` 的 payload **可以**用 `$` 开头带一个版面参数区块：

```
$<a>,<b>,<c>,<d>#<实际内容>
```

**解析规则**：`payload[0] == '$'` → 取到第一个 `#` 之间的字符串，以 `,` 切成 4 个整数；
非数字的字段用该 opcode 的默认值补；实际内容从 `#` 之后开始。

**各 opcode 的默认值（不同，必须分开记）**

| opcode | 默认值 | 四个参数的意义 |
|--------|--------|--------------|
| `008` / `009` | `[1, 3, 9, 30]` | cols、widthDiv、heightDiv、fontDiv |
| `012` | `[0, 0, 22, 35]` | cols（0=自动）、**未使用**、heightDiv、fontDiv |
| `020` | `[1, 2, 8, 25]` | cols、widthDiv、heightDiv、fontDiv |

- `widthDiv` / `heightDiv` / `fontDiv` 的语意是**除数**：按钮宽 = 画面宽 ÷ widthDiv，依此类推
- `012` 的 `cols` 为 0（未指定）时 → `cols = ceil(条目数 / 2)`，即缺省排成两列
- `012` 的第 2 个参数服务器**会送**（例 `ZJMENUF(6,6,25,40)`），但客户端**忽略**它 🟠

### H.4.1　`ESC003` 出口列表 🟢

```
<方向键>:<显示文本>[:<指令>]  $zj#  <方向键>:<显示文本>[:<指令>]  $zj#  …
```

| 栏 | 意义 |
|----|------|
| 1 | **方向键** —— 决定放在方向盘的哪个位置 |
| 2 | 显示文本（可含样式） |
| 3 | 点击时送出的指令。**省略时，指令 = 第 1 栏** |

**方向键 → 方向盘位置**

| 位置 | 接受的方向键 |
|------|-------------|
| 北 | `north`, `northup`, `northdown` |
| 南 | `south`, `southup`, `southdown` |
| 东 | `east`, `eastup`, `eastdown` |
| 西 | `west`, `westup`, `westdown` |
| 西北 / 东北 | `northwest` / `northeast` |
| 西南 / 东南 | `southwest` / `southeast` |
| **其他任意字符串** | 放进方向盘下方的「额外出口」清单（例 `enter`、`out`、`up`、`down`） |

> ⚠️ **第 1 栏可能含空白。** 实机出现过 `update here` 这种值。
> 因此判断规则**必须**是「不在上表的一律归额外出口」，
> **不得**假设它是单一英文本、也不得对它做分词。

**范例**
```
ESC003north:北面是大门$zj#east:东$zj#enter:进入客栈:enter inn
```

### H.4.2　`ESC005` 房间对象列表 🟢

```
<显示文本>:<指令>  $zj#  <显示文本>:<指令>  $zj#  …
```

- 每笔创建一个清单项目，**`tag` = 指令栏**（`ESC022` 血条更新靠它寻找）
- 点击时：记录「目前目标」的 id（= 指令）与名称（= 显示文本），然后送出该指令
- payload 长度 ≤ 4 时视为**空清单**，不创建任何项目

> ⚠️ **只切第一个冒号。**
> 指令栏常是 LPC 对象 id，形如 `look /d/city/npc/wolf#1686` —— 里面有 `/` 也有 `#`，
> 但**不会**再有第二个 `:` 之前的内容。对整串做 `split(':')` 会把指令切碎。

### H.4.3　`ESC006` 自订指令按钮 🟡

```
<槽位>:<显示文本>:<指令>  $zj#  …
```

**解析前**先把 payload 中的 `$br#` 换成 `\n`（让按钮标签可以两行）。

| 槽位 | 位置 |
|------|------|
| `bs` | **房间名称本身**（让房间名变可点击）。此槽**不使用**显示文本栏 |
| `b1` – `b5` | 自订按钮列 第 1 排（5 格） |
| `b6` – `b10` | 自订按钮列 第 2 排（5 格） |
| `b11` – `b17` | 底部工具列 |

**副作用**：任何 `b1`–`b17` 出现时，**隐藏方向盘、显示自订按钮列**，并把「自订」钮文本改成「关闭」。

### H.4.4　`ESC008` / `ESC009` 交互动作列 🟢

```
[$<cols>,<widthDiv>,<heightDiv>,<fontDiv>#]  <项目>$zj#<项目>$zj#…
```

缺省版面 `[1, 3, 9, 30]`。`008` 是左栏、`009` 是右栏，两者格式完全相同。

**单一项目格式**
```
<主标题>[|<副标题>]:<指令>
```

| 规则 | 说明 |
|------|------|
| 主标题中的 `$br#` | 先换成 `\n` |
| `\|` 分隔副标题 | 副标题常用来显示数量、价格 |
| 指令栏含 `ESC020` | 点击时**不送指令**，而是把其后内容当弹出菜单打开 |
| 指令栏含 `$txt#` | 点击后**保持面板打开**（供连续操作）；否则点完关闭面板 |
| 主标题等于 `发送语音` | 触发录音接口而非送指令 🟠 |

### H.4.5　`ESC012` 属性条群 🟢

```
[$<cols>,<未用>,<heightDiv>,<fontDiv>#]  <条目>║<条目>║…
```

缺省版面 `[0, 0, 22, 35]`，`cols = 0` 时取 `ceil(条目数 / 2)`。

**单一条目格式**
```
<标签>:<数值>:<颜色>[:<指令>]
```

**`<数值>` 的三种形态决定呈现**

| 写法 | 模式 | 呈现 |
|------|------|------|
| `<a>/<b>/<max>`（max > 0） | `dual` | 双层条：A 层 = a/max，B 层 = b/max |
| `<a>/<max>`（max > 0） | `single` | 单层条：A 层 = a/max，B 层满格 |
| 其他（含纯数字） | `text` | **不画条**，直接显示 `标签:原字符串` |

- **`<颜色>`**：A 层填充色。常是 8 位 **ARGB**（如 `#99FF0000`），转 CSS 要把 alpha 从头搬到尾
- **`<指令>`**（第 4 栏，可省略）：有此栏时该条可点击

> ⚠️ **标签常含全角冒号 `：`。**
> 用 ASCII `:` 切字段刚好安全（全角冒号不会被误切），
> 但**不得**写成 `[:：]` 这种「两种冒号都切」的正则——那会把标签本身切断。

**范例**
```
ESC012$2,0,22,35#气血:180/200/200:#ff0000:hp║内力:95/120/120:#0000ff:hp
```

### H.4.6　`ESC020` 弹出菜单 🟡

```
[$<cols>,<widthDiv>,<heightDiv>,<fontDiv>#]  <项目>$z2#<项目>$z2#…
```

缺省版面 `[1, 2, 8, 25]`。单一项目格式：`<显示文本>|<指令>`。

点击后依序：送出指令 → 关闭菜单 → 关闭遮罩 → 关闭交互面板。

> ⚠️ **此 opcode 的记录分隔符是 `$z2#`，不是 `$zj#`。**
> 全协议只有这一个例外。写错的症状是「整个菜单变成一个超长的项目」。

### H.4.7　`ESC021` 标题列按钮 🟢

```
<显示文本>:<指令>  $zj#  …
```

创建在房间标题右侧的横向卷动按钮列。点击送出指令并关闭交互面板。

### H.4.8　`ESC022` 对象血条更新 🟡

```
<对象tag>$zj#<a>:<b>:<max>
```

在对象清单中寻找 `tag` 相符者（tag = H.4.2 的指令栏），设置双层血条：
A 层宽 = `a/max`，B 层宽 = `b/max`。

**找不到相符 tag 时应静默忽略**——对象可能已经离开房间，这不是错误。

### H.4.9　`ESC001` 文本输入面板 🟡

```
<说明文本>  $zj#  <指令样板>
```

服务器宏：`#define INPUTTXT(a,b) ESA + "001" + a + ZJSEP + b`

**送出规则（点「确定」时）**

| 条件 | 送出内容 |
|------|---------|
| 样板含 `$txt#` | 把 `$txt#` **就地替换**成用户输入 |
| 样板不含 `$txt#` | `样板` + **一个空格** + 用户输入 |

> ⚠️ **输入是自由文本，不是数字。**
> 这是最容易误判的地方：面板长得像数量输入框，但服务器实际拿它接
> 角色名称、以空格分隔的四项属性数列、聊天内容等。
> **必须**用文本输入框，不得限制成数字类型。

**服务器真实用例**（147 处中的 5 个）🟡

| 样板 | 用户输入 | 实际送出 |
|------|-----------|---------|
| `name $txt#` | `张三 zhangsan` | `name 张三 zhangsan` |
| `edroom size $txt#` | `5` | `edroom size 5` |
| `washto $txt#` | `20 20 20 20` | `washto 20 20 20 20` |
| `chat $txt#` | `大家好` | `chat 大家好` |
| `jishou sword $txt#` | `500` | `jishou sword 500` |

看第 3 列就知道为什么不能做成数字框：`20 20 20 20` 是四个数字加空格。

### H.4.10　`ESC010` NPC 对话框 🟡

payload 先以 **`$dh#`** 切成多个区块，逐块依**前 5 个字符**判断：

| 前缀 | 意义 |
|------|------|
| `ok11.` | 「确定」钮要送的指令。**可出现多次**，依序累积成指令串行 |
| `no11.` | 「取消」钮要送的指令。**出现此块才显示取消钮** |
| `numb.` | 显示数量输入框（最多 3 位数，默认值 `1`）。⚠️ **长度刚好等于 5 也要接受** |
| 其他 | **内容区块**，再以 `$br#` 切成多行逐行处理 |

**内容行格式**

| 前缀 | 呈现 |
|------|------|
| `$exp#<文本>` | 经验值标签（绿） |
| `$god#<文本>` | 金钱标签（金） |
| `$obj#<tag>,<图文件名>,<品阶>` | 物品图标。点击送出 `litem <tag>`；框依品阶着色 |
| `#RRGGBB<文本>` | 指定颜色的文本行（**前 7 字符**是色码） |
| 其他 | 一般文本行（走 H.5 样式解析） |

**物品品阶**：`1` 白、`2` 绿、`3` 蓝、`4` 紫、`5` 金、`6` 红、`7` 灰，其他为缺省框。

**「确定」钮行为（顺序不可改）**

```
1. 若有数量输入框且为空 → 拒绝关闭，提示「各项不能为空」
2. 关闭对话框
3. 若有数量输入 → 把累积指令字符串中的 $N 全部替换成输入的数字
4. 以 $sock# 切开指令字符串，逐条依序送出
```

**「取消」钮**：若有 `no11.` 指令则送出，然后关闭。

**范例**
```
ESC010掌柜笑道：「客官要几坛女儿红？」$br#$god#你身上有 320 两银子$dh#numb.$dh#ok11.buy $N wine$dh#no11.say 算了
```

### H.4.11　空记录的处理 🟢

**记录尾端常有多余的分隔符**，例如 `a:1$zj#b:2$zj#`（结尾多一个 `$zj#`）。

所有以 `$zj#` / `$z2#` 切分的地方，**必须**滤掉切出来的空字符串记录，
否则画面上会多出一个空白按钮／空白清单项。

## H.5　行内样式方言

### H.5.1　ANSI 形式（主要）🟢

payload 文本先以 **`ESC`（U+001B）切段**。每段开头是样式指令，其后是套用该样式的文本。
**样式是有状态的**：设置后持续生效，直到被重置或覆写。

| 指令 | 语意 |
|------|------|
| `[0m` 或任何以 `;0m` 结尾者 | **重置全部**（色、粗体、字级、链接、全角） |
| `[1m` | 粗体 |
| `[9m` | **全角模式**：后续 ASCII 转全角（U+FF01–U+FF5E） |
| `[2J` | **清空主消息区** |
| `[H` | 光标归位（无视觉效果，移除此标记即可） |
| `[30m`–`[37m` | 前景色（一般） |
| `[1;30m`–`[1;37m` | 前景色（高亮） |
| `[40m`–`[47m` | 背景色（一般） |
| `[40;1m`–`[47;1m` | 背景色（高亮） |
| `[f#RRGGBBm` | 自订前景色（扩充） |
| `[b#RRGGBBm` | 自订背景色（扩充） |
| `[s:<n>]` | **字级**（扩充；⚠️ 结尾是 `]` 不是 `m`，参数前有冒号） |
| `[u:<url>]` | **超链接**（扩充；同上） |

**判断顺序（不可改）**

```
① 以 "[u" 开头 → 找 "]"，取参数 → 设为链接
② 以 "[s" 开头 → 找 "]"，取参数 → 设为字级
③ 以 "[2J" 开头 → 清空主消息区，切掉 3 字符
④ 以 "[H"  开头 → 切掉 2 字符
⑤ 其余 → 找第一个 "m"，依上表比对
```

> ⚠️ **①② 必须在 ⑤ 之前。**
> `[u:` 与 `[s:` 以 `]` 收尾。若先运行「找第一个 m」，
> `[u:cmds:look me]` 会一路找到后面某个不相干的 `m`，把整段文本吃掉。

> ⚠️ **那个冒号。**
> 服务器宏是 `ZJURL(w) → "[u:" + w + "]"`、`ZJSIZE(n) → "[s:" + n + "]"`，
> 参数前**有冒号**。取参数时要跳过 `[`、`u`、`:` 三个字符。
> 少跳一个的后果：URL 变成 `:cmds:…` 而点击完全失效、字级解析失败。
> 这两个宏在服务器用了 **638 次**——解错的话画面会大面积失效。
> **建议两种写法都接受**（取出参数后若首字符是 `:` 就剥掉）。

### H.5.2　调色板 🟠

原始客户端不使用标准 ANSI 色值，而是自订的一组。**必须逐值照抄**，否则颜色会整体偏掉：

```
前景（一般 [30m–[37m）
#000000  #aa3300  #00bb00  #eeee00  #0000aa  #aa00aa  #00bbbb  #aaaaaa

前景（高亮 [1;30m–[1;37m）
#000000  #ff3300  #88ff00  #ffff00  #0000ff  #ff00ff  #88ffff  #ffffff

背景（一般 [40m–[47m）
#222222  #aa0000  #00aa00  #aaaa00  #0000ff  #aa00aa  #00aaaa  #aaaaaa

背景（高亮 [40;1m–[47;1m）
#000000  #ff0000  #00ff00  #ffff00  #0000ff  #ff00ff  #00ffff  #ffffff
```

**浅底（白天）模式改写**：索引 `{2, 3, 6, 7}`（即 `32`/`33`/`36`/`37`）一律改成索引 4（蓝），
高亮版同理。理由是绿／黄／青／灰在浅色背景上几乎看不见。

**ARGB → RGBA**：色值可能带 alpha 前缀（如 `#99aa3300`，8 位）。
这是 **ARGB** 不是 RGBA，转 CSS 时**必须**把 alpha 从头搬到尾。

### H.5.3　链接 scheme 🟡🟠

`[u:<url>]文本[0m` 中的 `<url>` 依前缀决定行为：

| 前缀 | 行为 | 等级 |
|------|------|------|
| `cmds:` | **送出指令**（去前缀），并关闭交互面板 | 🟡 |
| `http://` `https://` | 打开网页 | 🟡 |
| `tel:` | 拨打电话 | 🟡 |
| `mailto:` | 打开邮件程序 | 🟡 |
| `pops:` | 打开弹出菜单，参数格式同 `ESC020` | 🟠 |
| `voice:` | 播放语音频息 | 🟠 |
| 其他 | 交给系统以外部浏览器打开 | 🟠 |

> `cmds:` 让服务器能把消息里的**任意词句**变成可点击指令。
> 这是整个协议最灵活的一点，也是服务器用量最大的扩充（302 处）。

### H.5.4　HTML 形式（指游 ZY 方言）🟡

指游的 web 版把样式标记换成 HTML：

```c
#define ZYURL(cmds,msg)    "<a href=\"" + cmds + "\"><span>" + msg + "</span></a>"
#define ZYSIZE(size,msg)   "<font style=\"font-size:" + (650/size) + "rem;\">" + msg + "</font>"
#define ZYCOLOR(color,msg) color + msg + "</font>"
```

同一份 header 也保留了被注解掉的 ANSI 版，两者同构：
`ZYSIZE(n)` 的 `650/n` rem 对应 ANSI 版 `[s:n]` 的「画面宽 ÷ n」。

> ⚠️ **安全要求（不得违反）**
> HTML 形式代表**服务器可以送任意标记到客户端**。
> 实作**不得**直接把 payload 塞进 `innerHTML` 或等价的原始 HTML 插入 API。
> **必须**只白名单 `<a>` / `<font>` / `<span>` 三个标签与其有限属性
> （`href`、`style` 的 `font-size` / `color` / `background-color`），
> 其余一律转义成纯文本。
> 这不是理论风险：聊天消息会被原样广播给所有玩家，
> 一个玩家送出的标记会在**每一个**其他玩家的客户端上运行。

## H.6　登录串行与侧信道

### H.6.1　三种版本挑战（必须全部支持）🟡

连上后服务器送的**第一行**决定后续一切。三个来源写法各不相同：

| 写法 | 对应方言 |
|------|---------|
| `ver1.0:<crypt>` | 经典／大梦江湖（**冒号**） |
| `ver1.0,<crypt>` | 经典（**逗号**） |
| `version 1.0 key::<crypt>` | 指游 ZY |

**只认其中一种，另外两种服务器就完全连不上**（而且症状是「连上了但什么都没发生」）。

客户端**必须**以这一行**同时决定**两件事：套用哪个方言 profile（H.3.3）、以及后续字段数（H.6.3）。

### H.6.2　帐号与服务器列表（HTTP 侧信道）🟠

帐号系统**不走 TCP**，而是独立的 HTTP GET API。

| 端点 | 参数 | 回传 |
|------|------|------|
| `/mobi/vers.php` | — | `<版本号>\|<公告文本>[\|…]` |
| `/mobi/reg.php` | `id`, `pass`, `phone`, `email`, `key` | 注册结果 |
| `/mobi/loginto.php` | `id`, `pass`, `key`, `page` | 服务器列表（见下） |
| `/mobi/check.php` | `ip`, `port`, `key` | 服务器可用性 |
| `/mobi/userinfo.php` | `id` | 用户数据 |
| `/mobi/updateuser.php` | `id`, `newpwd` / `phone` / `email` | 修改数据 |

**服务器列表格式**：`loginto.php` 成功时回传字符串以 **`$l#`** 开头，去掉前 3 字符后：

```
<分区1>|<分区2>|…|<email>
```

每个分区再以 **`&`** 分栏：

```
<分区名>&<ip>&<port>&<栏4>&<栏5>&<验证key>
```

- 栏 1 = 显示名称、栏 2 = 游戏服务器 IP、栏 3 = port、栏 6 = 验证 key（TCP 登录时要送）
- ⚠️ **最后一段是用户 email，不是分区** —— 切分后必须把最后一段取走再处理

> ⚠️ **安全立场（新实作必须改掉）**
> 原始设计的签章是 `key = MD5(<字段串接> + <SALT>)`，而 SALT 是一个**写死在客户端内的常数**。
> 这**没有任何实质安全性**：任何人拿到客户端就拿到 SALT，可以自行伪造任意请求。
> 新实作若要自架帐号系统，**不得**沿用此设计，**必须**改成服务器端验证
> （例如短期 token + HTTPS）。本附录记录它只是为了与既有部署互通。

### H.6.3　TCP 登录状态机 🟢🟡

出处 `world/adm/daemons/logind.c:72-300`，并经实机连接逐步验证。

```
Client                              Server
  │                                    │
  │◀── IAC ×6 + 版本挑战行 ─────────────┤   H.6.1
  │                                    │
  ├── 任意非 "//" 字符串 ───────────────▶│   → "版本验证成功"
  │                                    │
  ├── 帐号║密码║密文║email ───────────▶│   字段数见 H.6.4
  │                                    │
  │◀── ESC000 "0007" ──────────────────┤   登录成功 → 直接进世界
  │    或                               │
  │◀── ESC000 "0008" ──────────────────┤   帐号无角色 → 需创建
  │                                    │
  ├── 性别║头像║暱称 ─────────────────▶│
  │                                    │
  │◀── ESC000 "0007" ──────────────────┤   创建成功
  │◀── ESC002/003/004/005/… ───────────┤   进入世界
```

**`ESC000` 状态码**

| 码 | 意义 | 等级 |
|----|------|------|
| `0007` | 登录成功 | 🟡 `logind.c:241,253,318` |
| `0008` | 帐号存在但**没有角色**，需送建角数据 | 🟡 `logind.c:268` |
| `0009` | 暱称不符合要求 | 🟡 |
| `重连完毕` | 断线重连完成 → 客户端**自动送 `l`** | 🟠 |

> ⚠️ **`ESC000` 的 payload 既可能是数字状态码、也可能是中文本串。**
> 不得假设它一定是其中一种，更不得对它做 `parseInt` 之后就当数字用。

### H.6.4　字段数随方言变动 🟡

服务器端是 `sizeof(myinfo) != N` 的**严格检查**，字段数不对会被直接退回。

| 消息 | 经典 | 官方文档版 | 指游 ZY |
|------|------|-----------|--------|
| 登录 | `帐号║密码║密文║email`（**4** 栏） | `帐号║密码║密文`（**3** 栏） | 4 栏 |
| 建角 | `性别║头像║暱称`（**3** 栏） | 3 栏 | `性别║暱称`（**2** 栏） |

- 分隔符是 **`║`（U+2551）**，不是 ASCII 的 `|`
- 行动客户端建角时把「头像」栏**留空**（送 `男║║名字`）——中间那栏是有意义的头像字段，不是笔误
- 暱称需通过 `check_legal_name(name, 4)`：中文、长度上限 4

### H.6.5　登录逾时（自动化必读）🟡

服务器对「连上到完成登录」有时间限制。超时会送：

```
您花在连线进入手续的时间太久了，下次想好再来吧。
```

然后关闭连接。

> ⚠️ **自动化测试或脚本登录时，三个步骤必须在同一轮连续送出。**
> 不要分次、不要中间等待人工操作，否则会被踢。
> 被踢之后客户端若有自动重连，表现为「画面又出现版本挑战」——
> 很容易被误判成「握手失败」，其实是逾时。

### H.6.6　完整验证机制与第三方客户端的限制 🟡

官方文档揭露了本来的设计（多数自架服务器把它注解掉了）：

```
服务器 → ver1.0,<crypt(ZJKEY, 0)>
客户端 → crypt(ZJKEY, str[2..3])       ← 需由官方网关产生
服务器 → 版本验证成功
客户端 → 帐号║密码║crypt(ZJKEY,帐号)+crypt(ZJKEY,密码)
```

**`ZJKEY` 只存在于服务器端**，客户端拿不到——官方作法是把挑战串丢给官方网关换回应。

因此第三方客户端**无法通过完整验证**，除非服务器停用该检查（实务上绝大多数如此）。
本附录描述的登录流程，前提是服务器已停用此检查。

## H.7　客户端系统架构

> 本节是**语言中立**的架构规范。第六篇 §018–§028 是本项目 JS + Rust 的具体落地，
> 两者可以对照，但实作者不必照抄那个模块切分。

### H.7.1　分层与依赖方向

```
        ┌──────────────────────────────┐
        │  ⑤ 呈现层（UI / DOM / 原生组件）│  ← 唯一可以碰画面的层
        └──────────────┬───────────────┘
                       │ 只读状态、只调用回呼
        ┌──────────────▼───────────────┐
        │  ④ 状态层（单一状态树 + 订阅）  │
        └──────────────┬───────────────┘
                       │ reducer 套用事件
        ┌──────────────▼───────────────┐
        │  ③ 协议层（行 → 事件，纯函数）  │  ← 不得有副作用
        │     ├ opcode 分派（H.2）       │
        │     ├ payload 解析（H.4）      │
        │     ├ 样式解析（H.5）          │
        │     └ 方言表（H.3.3）          │
        └──────────────┬───────────────┘
                       │ 收到完整的一行
        ┌──────────────▼───────────────┐
        │  ② 传输层（TCP + IAC + 解码）   │
        └──────────────┬───────────────┘
        ┌──────────────▼───────────────┐
        │  ① 平台层（socket / 桥接）      │
        └──────────────────────────────┘
```

**四条强制规则**

| # | 规则 | 为什么 |
|---|------|--------|
| 1 | ③ 协议层**不得**引用任何 UI / 平台 API | 让它能在无 UI 环境下被单元测试 |
| 2 | ⑤ 呈现层**不得**直接调用 ② 传输层 | 否则「送指令」会散落各处，无法统一记录与拦截 |
| 3 | ③ 的输出是**数据**，不是副作用 | 同一行输入永远产生同一个事件对象，可比对、可回归 |
| 4 | 没有任何模块反向依赖组装层 | 避免循环相依 |

**可测的验收方式**：在没有 UI 的测试环境中直接加载 ③ 协议层的所有模块，**不得**抛错。

### H.7.2　数据流（单向）

```
socket bytes
   → [传输层] 剥 IAC → 解码 → 分行
   → [协议层] parse_line → decode → Event
   → [reducer] Event + State → State'
   → [状态层] notify 订阅者
   → [呈现层] 重绘受影响的区块

用户操作
   → [呈现层] 产生 Command
   → [组装层] 统一送出
   → [传输层] write socket
```

> ⚠️ **不得**让呈现层直接改状态树，也**不得**让协议层直接碰画面。
> 这两条一旦破一次，之后每个 bug 都要在三个地方找原因。

### H.7.3　事件契约

协议层对每一行产出一个事件对象。建议的事件族群（名称可自订，**分类不应变**）：

| 族群 | 事件 | 来源 opcode |
|------|------|------------|
| `conn.*` | `notice`、`relocate`、`multiline`、`quit`、`echo` | `000`、`900`、`997`/`998`、`999`、`014` |
| `room.*` | `title`、`desc`、`descToggle`、`exits`、`exitRemove`、`exitClear`、`objects`、`objectRemove`、`objectBar` | `002`、`004`、`023`、`003`、`903`、`913`、`005`、`905`、`022` |
| `stat.*` | `bars` | `012` |
| `msg.*` | `main`、`toast`、`combat`、`combatClose`、`chat`、`float` | 缺省、`015`、`016`、`017`、`100`、`024` |
| `overlay.*` | `prompt`、`detail`、`actions`、`dialog`、`map`、`pagedText`、`popMenu`、`web` | `001`、`007`、`008`/`009`、`010`、`011`、`013`、`020`、`045` |
| `ui.*` | `titleButtons`、`quickButtons` | `021`、`006` |

**未知 opcode** → `msg.main`，并带 `unknownOpcode` 标记与**完整原文**。

### H.7.4　状态树与清空规则

状态树**至少**要有这些分支：

| 分支 | 内容 |
|------|------|
| `conn` | 连接状态、目前方言 profile、multiline 旗标 |
| `room` | 标题、描述、出口清单、对象清单（含血条） |
| `stats` | 属性条群 + 版面参数 |
| `messages` | 各频道的消息队列（含容量上限，见 H.7.5） |
| `overlay` | 目前打开的叠层与其内容 |
| `ui` | 标题列按钮、自订按钮槽位 |

**`ESC002`（房间标题）的清空副作用是整个协议唯一的「批量重置」**，
必须在 reducer 中集中实作，**不得**散在各处：

```
on room.title:
    room.title  ← 新标题
    room.exits  ← 清空
    room.objects← 清空
    ui.dirPad   ← 隐藏
    overlay.combat ← 关闭
    ui.quickButtons← 关闭
```

### H.7.5　容量上限 🟠

不设上限的后果是挂机一夜之后内存被消息吃光。

| 区域 | 上限（则） | 超过时 |
|------|----------:|--------|
| 主消息区 | 50 | 移除最旧 |
| 战斗面板 | 50 | 移除最旧 |
| 迷你聊天列 | 100 | 移除最旧 |
| 「全部」聊天页 | 500 | 移除最旧 |
| 「系统」聊天页 | 500 | 移除最旧 |

### H.7.6　客户端自动送出的指令 🟡🟠

除了用户手动输入，客户端会在下列情境**自动**送出：

| 情境 | 送出内容 |
|------|---------|
| 收到 `ESC014` | payload 原文 |
| 收到 `ESC000` 且 payload == `重连完毕` | `l` |
| TCP 连接创建、通过版本挑战后 | `<帐号>║<密码>║<key>║<email>` |
| 点击出口／对象／自订按钮／标题列／动作列／弹出菜单 | 各自的指令栏 |
| 点击属性条（有第 4 栏时） | 该条的指令栏 |
| 对话框「确定」 | `ok11.` 累积字符串（`$N` 已替换），以 `$sock#` 拆成多条依序送出 |
| 对话框「取消」 | `no11.` 指令 |
| 对话框物品图标 | `litem <tag>` |
| 文本中的 `cmds:` 链接 | 前缀后的字符串 |

> ⚠️ **所有自动送出都应经过同一个出口函数**，并且可被记录。
> 否则一旦出现「客户端疯狂送指令」这类问题，会完全查不出是哪一条路径触发的。
> 本书第五篇记录过一次同类事故：客户端每秒对服务器登录一次，被发现时已累计五万次。

### H.7.7　错误处理原则

| 情况 | 处理 | **不得** |
|------|------|---------|
| 未知 opcode | 降级为一般消息 + 标记 | 静默丢弃 |
| 样式指令无法辨识 | 忽略该指令、**保留文本** | 丢弃整段 |
| 字段数不足 | 用默认值补、记录警告 | 抛例外中断整行 |
| 色值格式错误 | 保留原值或用缺省色 | 让整个消息不显示 |
| 单行解析抛错 | 捕捉、记录、该行降级为纯文本 | 让一行坏数据弄断连接 |
| 文本解码失败 | 宽容模式，坏字节换替换字符 | 中止串流 |

> 💡 贯穿全表的一句话：**坏掉的应该是一行，不是一条连接。**

## H.8　验收测试矩阵

> 这一节的目的是让实作者能**自己判断做完了没有**，不必等别人验收。
> 每一列都是可自动化的。

### H.8.1　分层测试

| 层 | 测什么 | 最小测项 |
|----|--------|---------|
| L1 传输 | IAC 剥除 | 18 字节协商完整剥除；`IAC IAC` 还原成单一 `0xFF`；串行跨 read 边界仍正确 |
| L1 传输 | 拒绝策略 | 对 6 组协商各回一个拒绝；**MCCP2 必须拒绝** |
| L2 分行 | 分帧 | `\r\n` 与 `\n` 都能切；半行留在缓冲区等下一次 |
| L3 opcode | 变长消歧义 | `ESC1085` → `1085`；`ESC004` + 「5 个人…」→ `004`（**不得**变 `0045`） |
| L3 opcode | 含字母 | `10a`、`2k1` 能被辨识 |
| L3 opcode | 重置码两种顺序 | `ESC[2;37;0mESC002…` 与 `ESC002ESC[2;37;0m…` 都要取到 `002` |
| L4 payload | 每个结构化 opcode | H.4 各节至少一个正例 + 一个边界例 |
| L4 payload | 空记录 | 结尾多一个 `$zj#` 不产生空项目 |
| L4 payload | 只切第一个冒号 | `look /d/x/npc#1686` 保持完整 |
| L5 样式 | 判断顺序 | `[u:cmds:look me]` 不被「找第一个 m」吃掉 |
| L5 样式 | 冒号两种写法 | `[u:x]` 与 `[ux]` 都取到 `x` |
| L5 样式 | ARGB → RGBA | `#99aa3300` → `#aa330099` |
| L6 状态 | `ESC002` 副作用 | 送房间标题后，出口与对象确实被清空 |
| L6 状态 | 容量上限 | 送 60 则主消息后只剩 50 则 |
| L7 端到端 | 登录串行 | 三种版本挑战各跑一次，都能进到「送帐号」那一步 |

### H.8.2　四条不可省的不变式

这四条是「测试全绿但实际会坏」的最后一道防线：

| # | 不变式 | 怎么测 |
|---|--------|--------|
| 1 | **协议层无副作用** | 同一行输入调用两次，产出的事件对象深度相等；过程中不得写入任何外部状态 |
| 2 | **协议层可在无 UI 环境加载** | 在无 UI 的测试 runtime 中加载所有协议层模块，不得抛错 |
| 3 | **未知 opcode 不遗失信息** | 送一个表中没有的 opcode，事件的 `text` 必须包含**完整原行**（含控制字符） |
| 4 | **撞号被隔离** | 在方言 A 下送 `605`、在方言 B 下送 `605`，必须产生**不同**事件 |

### H.8.3　实机验收（最终）

自动化测试全绿**不等于**能用——本书第五篇整篇都在讲这件事。最后三步必须用真服务器：

```
① 连上 UTF-8 端口，确认 IAC 被剥干净、第一行是版本挑战
② 完成登录 → 应看到房间标题、描述、出口按钮同时出现
③ 点一个 NPC → 应看到详情文本（007）+ 动作列（009）
```

第 ③ 步是最有代表性的：它同时验证了发送量最大的两个 opcode、
`cmds:` 链接、以及交互面板的清空副作用。**这一步通了，协议层基本就是对的。**

## H.10　最小可玩集合

如果只想先做出「能登录、能走路、能看 NPC」的版本，这是最短路径：

| 顺序 | 做什么 | 对应章节 |
|-----:|--------|---------|
| 1 | TCP + IAC 剥除 + 拒绝协商 + UTF-8 宽容解码 | H.1 |
| 2 | 分行 + 变长 opcode 截取 + 未知降级 | H.2 |
| 3 | 版本挑战 → 登录 → `ESC000` 状态码 | H.6 |
| 4 | `ESC002` / `ESC004`（房间标题与描述） | H.3.1 |
| 5 | `ESC003`（出口）→ **此时已经可以走路** | H.4.1 |
| 6 | `ESC005`（对象清单）+ 一般消息 | H.4.2 |
| 7 | `ESC007` + `ESC009`（详情 + 动作列）→ **此时已经可以跟 NPC 交互** | H.4.4 |
| 8 | `ESC014`（代送指令）→ **此时大部分流程不会卡住** | H.3.2 |
| 9 | 样式方言（颜色 + `cmds:` 链接） | H.5 |
| 10 | `ESC012`（属性条）+ `ESC001`（文本输入） | H.4.5、H.4.9 |

前 8 步做完就是一个**可玩**的客户端。第 9、10 步之后就是一个**好用**的客户端。
其余所有 opcode 都是锦上添花，可以按 H.3.2 的发送量统计排序慢慢补。

> 💡 君之一席话
> **一份规格是否够用，不看它写了多少，而看读的人能不能在第 5 步就跑起来。**
> 上面这张表刻意把「可以走路」放在第 5 步、「可以交互」放在第 7 步——
> 因为一个三个月才会动的实作，不管规格写得多完整，都会在中途被放弃。
