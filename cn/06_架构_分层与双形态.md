# 第四篇　客户端架构

## 012　把协议关进纯函数 — 原客户端最大的架构债

**标签**：`#架构` `#纯函数` `#单向数据流` `#可测性` `#关注点分离`
**证据等级**：🟠 原客户端反编译（反面教材）＋ 本项目实作

**起源**：反编译原客户端时，最刺眼的不是协议有多复杂，而是**协议解析与 UI 操作完全混在一起**。

opcode 分派器里直接写着 `setVisibility()`、`addView()`、`setTextColor()`。要理解「`ESC003` 的 payload 格式」，你得同时读懂 Android 的 View 树。

更糟的是样式解析器的状态是**静态字段**（`static ForegroundColorSpan colsp`），多处共用同一份状态。

**技术内核**：本项目的第一个架构决策是**把协议关进纯函数**：

```
protocol.js   行 → 事件对象      不碰 DOM、不碰 store、不送指令
ansi.js       文本 → span 树     不碰 DOM
     ↑ 这两个文件不依赖任何东西，可以在 Node 里直接测
```

`decodeLine()` 的输出是一个 discriminated union：

```javascript
{ type: 'room.title',   text }
{ type: 'room.exits',   exits: [{ dir, slot, label, cmd }] }
{ type: 'stat.bars',    layout, bars: [{ label, a, b, max, color, cmd }] }
{ type: 'msg.chat',     text }
```

**解析器不知道 DOM 存在**，它回传的是数据。UI 层订阅这些数据。

依赖方向严格单向：

```
        main.js
       ╱   │   ╲
   net.js  │   ui.js
      │    │    │
      │  store.js
      │    ▲    │
      └────┴────┘
           │
      protocol.js ──▶ ansi.js
```

**没有任何模块反向依赖 `main.js`。**

**解决的痛点**：让「协议正确性」与「画面正确性」变成两个可以独立验证的问题。57 条协议测试不需要浏览器、不需要服务器、跑完只要 180 毫秒。

**踩过的坑**：纯函数的边界很容易在不知不觉中被打破。本项目有一次差点失守——`ansi.js` 的 `[2J`（清空主消息区）需要通知 UI 清画面。诱惑是直接在解析器里调用 UI，但那会让 `ansi.js` 从此依赖 DOM。

最后的做法是**把它变成回传值的一部分**：

```javascript
return { spans, clearScreen };   // 由调用端决定要不要清
```

**一个布尔值，守住了整个模块的纯度。**

**优点 / 罩门**：纯函数的优点是可测、可重放、可以拿实机封包当 fixture 直接喂。罩门是**有状态的东西必须显式传递**——样式状态跨段延续，所以 `parseStyled()` 接受一个可选的 `state` 参数，由调用端决定要不要延续。这比静态变量啰嗦，但它让「同时解析两条独立串流」变成可能。

**架构对照**：

| 设计 | 协议变更成本 | 可测性 | 典型症状 |
|------|-------------|--------|---------|
| **解析器直接操作 UI**（原版） | 高，要动十个文件 | 几乎不可测 | 改协议就改坏画面 |
| **纯函数 + 事件**（本项目） | 低，只动一个档 | 好 | — |
| 全域状态机 | 中 | 中 | 状态互相污染 |

**效益**：协议层 170 条测试里有 100 条完全不需要 DOM 或网络，在 CI 里秒级跑完。

> 💡 君之一席话
> **把协议关进纯函数，等于把「我理解得对不对」和「我画得对不对」拆成两个问题——能分开问的问题，才能分开答。**

> 🔍 老手视角──真正的门道
> 「解析器不碰 UI」听起来是常识，但真正困难的是**守住它**——每一次「就这一行、就这一次」的例外，都是边界的裂缝。老手的做法不是靠自律，而是靠**物理隔离**：让纯函数模块跑在一个没有 DOM 的环境里（本项目就是 `node --test`），一旦有人偷偷引用 `document`，测试立刻爆炸。这比 code review 可靠得多。可落地的提醒：**如果你的「内核逻辑」测试需要 mock 浏览器，那它就还不够内核。**

## 013　双形态 — 同一份前端，两条传输路径

**标签**：`#Tauri` `#WebSocket` `#Transport抽象` `#跨平台` `#桥接`
**证据等级**：本项目实作 ＋ 🟢 实机验证

**起源**：协议是**原生 TCP**。浏览器开不了 raw socket，所以纯网页版必须有一支桥接进程。而桌面版如果用 Tauri，Rust 端可以直接连 TCP，完全不需要桥接。

两种形态，两种取舍：

| | 桌面版 | 浏览器版 |
|---|--------|----------|
| 传输 | Rust 直接开 TCP | WebSocket → 桥接 → TCP |
| 需要 | Rust 工具链 | 只要 Node.js |
| 手机可用 | ✗ | **✓** |
| 额外进程 | 无 | 一支桥接 |

**技术内核**：关键设计是**一个 Transport 接口，两个后端**：

```javascript
tauriBackend      → __TAURI__.core.invoke('mud_connect' | 'mud_send')
websocketBackend  → new WebSocket(`${scheme}//${location.host}/mud`)
```

两者实作同一组方法（`open` / `send` / `close`），共用同一台**连接状态机**（含指数退避重连）。上层的 `main.js` 与 `ui.js` 完全不知道自己跑在哪一种底下。

环境判别只有一行：

```javascript
const backend = isTauri() ? tauriBackend(...) : websocketBackend(...);
```

**前端代码一行都不用改**——3,107 行 JS 在两种形态下完全相同。

**解决的痛点**：不必为了「桌面要性能、手机要可及性」而维护两套客户端。

**踩过的坑**：桥接必须**代替浏览器做 telnet IAC 处理**。浏览器收到的是 WebSocket 文本帧，没有字节层可以剥 IAC——所以那 63 行的 `bridge/telnet.mjs` 是 Rust 版 `telnet.rs` 的 JS 对应实作。

**两份实作、一组断言**：两边的测试都用同一份 42 字节的实机数据，确保行为不会分歧。

另一个坑是**开放代理风险**。桥接如果让前端指定任意 `host:port`，它就变成一个公开的 TCP 代理。本项目的缺省是**只允许连到启动时设置的目标**，要放宽得明确加 `--allow-any`：

```javascript
if (!ALLOW_ANY && want.host !== MUD_HOST) {
  sendState({ state: 'error', message: `此桥接只允许连到 ${MUD_HOST}:${MUD_PORT}` });
  ws.close();
}
```

这条规则有专门的测试守着。

**优点 / 罩门**：双形态的优点是**覆盖面最大**——桌面要性能有性能，手机开浏览器就能玩。罩门是**两份 telnet 实作要同步维护**，这是真实的重复成本，只能靠共用测试数据缓解。

**方案对照**：

| 方案 | 手机 | 额外进程 | 前端改动 |
|------|------|---------|---------|
| 只做 Tauri | ✗ | 无 | — |
| 只做浏览器 | ✓ | 桥接 | — |
| **双形态**（本项目） | ✓ | 浏览器版需桥接 | **零** |

**效益**：一份前端、两种部署形态；浏览器版让手机在同区网直接连上，这是原本 Tauri-only 方案完全做不到的。

> 💡 君之一席话
> **当两种平台的差异只在「怎么把字节送出去」，那就别让它蔓延到第三个文件——抽象的价值不在优雅，在于把差异关在一个盒子里。**

> 🔍 老手视角──真正的门道
> 这个抽象之所以成立，是因为 Transport 的接口**极窄**——只有连接、送一行、关闭、两个回呼。窄接口是抽象能活下来的前提；一旦接口开始长出 `setTimeout`、`getStatistics`、`enableCompression` 这种东西，两个实作就会开始各自漂移。老手设计跨平台抽象时有个经验法则：**如果接口超过五个方法，先问是不是抽象抓错层次了**。另外值得注意的是，本项目的桥接刻意**不解析协议**——它只做 IAC 剥除与分行，opcode 解析仍然全在前端。这让桥接保持在 165 行、几乎不需要维护；如果当初把协议解析也搬进桥接，就会变成第三份需要同步的实作。**中介层要薄，薄到你不想在它里面加功能。**

## 014　失败隔离 — 一个 `scrollTo` 让整个客户端变成摆设

**标签**：`#错误处理` `#失败隔离` `#可观测性` `#挂载` `#防御性设计`
**证据等级**：🟢 实机（四次故障中的第一次）

**起源**：初版的 `mount()` 是一长串直接调用：

```javascript
UI.Toast(...)
UI.ConnBadge(...)
UI.MessageList($('msg-main'), ...)   // ← 这里抛例外
bindCommandInput(...)                 // ← 从未运行
bindConnectForm(...)                  // ← 从未运行
```

`MessageList` 内部调用了 `root.parentElement.scrollTo(...)`。`Element.scrollTo()` 不是所有运行环境都有——一抛例外，**整个 `mount()` 中断**。

结果是：画面渲染得完全正常（那些都是 CSS 和先跑完的组件），但「连接」按钮**没有任何事件处理器**。按下去毫无反应，也没有任何错误提示。

**更狡猾的是**：连接面板的 host/port 字段显示着 `127.0.0.1` 和 `5001`——那其实是 HTML 的 **placeholder，不是值**。因为 `bindConnectForm()` 从没跑到，没有填值。画面看起来一切正常。

**技术内核**：修法有两层。

**表层**：`scrollTo` 换成 `scrollTop = scrollHeight`——等价但所有环境都支持。

**深层**：让 `mount()` 逐项独立保护：

```javascript
const mountErrors = [];
function step(name, fn) {
  try { fn(); }
  catch (err) { mountErrors.push(`${name}: ${err.message}`); console.error(...); }
}

step('MessageList', () => UI.MessageList(...));
step('ConnectForm', () => bindConnectForm());   // 这一项挂掉 = 客户端完全不能用
...
if (mountErrors.length) showConnectError(mountErrors.join('\n'));
```

**任何一个组件失败，都不会拖垮其他组件的事件绑定。**

**解决的痛点**：把「一个小组件的环境兼容问题」与「整个客户端能不能用」解耦。

**踩过的坑**：这个 bug 之所以能活到用户手上，是因为**当时的 98 条测试全绿**——它们全都绕过了「HTML + main.js」这一层，也就是用户唯一会碰到的那一层。

修完之后补了一支 jsdom 冒烟测试，**真的加载 `index.html`、真的运行 `main.js`、真的派发 click 事件**。它一跑就抓到这个 bug：9 条里有 8 条失败。

其中一条断言特别关键：

```javascript
assert.equal(host.value, '127.0.0.1', 'main.js 未运行或 bindConnectForm 失败');
```

**检查的是「字段有没有被填值」，而不是「画面上看不看得到文本」**——因为 placeholder 会让后者通过。

**优点 / 罩门**：失败隔离的优点是**局部故障不会全域瘫痪**，而且错误被收集起来显示。罩门是它可能**掩盖问题**——如果没有把 `mountErrors` 显示出来，就变成安静地少了一个组件。因此隔离必须配上可观测性，两者缺一不可。

**错误处理策略对照**：

| 策略 | 局部故障 | 可诊断性 | 适用 |
|------|---------|---------|------|
| 不处理（原版） | 全域瘫痪 | 无 | — |
| 全域 try/catch | 全域瘫痪但不崩 | 差 | 顶层兜底 |
| **逐项隔离 + 收集**（本项目） | 局部降级 | 好 | 挂载期 |

**效益**：一个组件的环境兼容问题，从「整个客户端不能用」降级成「少一个消息区」。

> 💡 君之一席话
> **一个永远不会失败的初始化流程是幻想；能在失败之后还让用户按得动「连接」的初始化流程，才是工程。**

> 🔍 老手视角──真正的门道
> 这个故障的真正教训藏在顺序里：**最关键的绑定排在最后**。`bindConnectForm()` 是用户唯一的操作入口，却排在十几个装饰性组件之后——前面任何一个失败，它就永远等不到。老手在写初始化流程时会做一件事：**把「没有它就完全不能用」的项目排到最前面**，或者至少确保它们彼此独立。这不是性能考量，是失败语意的排序。可落地的提醒：初始化清单写完后，逐项问一句「这个挂了，用户还能不能完成内核任务？」——不能的话，它就该被独立保护，而且该往前排。
