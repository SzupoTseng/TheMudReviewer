# 第二篇　协议解剖

## 004　三层结构 — 一句话说完 ZJMUD 是什么

**标签**：`#协议` `#分层` `#telnet` `#ANSI` `#行级opcode`
**证据等级**：🟢 实机封包 ＋ 🟡 服务器原代码

**起源**：所有中文 MUD 客户端都面对同一个矛盾——**服务器只会吐纯文本，但手机屏幕需要按钮、血条、面板**。ZJMUD 的解法不是换一套二进位协议，而是**在文本串流上叠三层标记**，让旧的 telnet 客户端还能用，新的图形客户端也能解析。

**技术内核**：

```
┌──────────────────────────────────────────────────────┐
│ TCP，连接瞬间有 telnet IAC 协商（必须剥除并拒绝）        │
│  └─ UTF-8（端口 5001；端口 5003 是 GBK），以 \n 逐行分帧    │
│      └─ 行首 4 字符 opcode：ESC + "003"                │
│          └─ payload：用 $zj# 分记录、: 分字段           │
│              └─ 字段内：ANSI 扩充方言 + $br# 换行       │
└──────────────────────────────────────────────────────┘
```

四层，由外而内：

**① 传输层**：原生 TCP，UTF-8，`\n` 分帧。看起来单纯，但外面裹着一层 telnet 选项协商——这是最容易漏掉的一层，详见 006。

**② 行级 opcode**：每一行的前 4 个字符是 `ESC`(U+001B) 加三个英数字元。命中就分派到对应的 UI 区块，没命中就当一般消息。**这一层决定了「这行文本要显示在哪里」**。

**③ 字段结构**：payload 用字符串标记切分——`$zj#` 分记录、`:` 分字段、`|` 分次级字段、`║`(U+2551) 分属性条。没有长度前缀，全靠分隔符。

**④ 行内样式**：ANSI SGR 的扩充方言，加上自订色、字级、超链接、全角模式。

**解决的痛点**：让同一条连接同时服务「传统 telnet 玩家」与「图形客户端玩家」。不认识 opcode 的客户端会把 `ESC003north:北` 当成一行奇怪的文本印出来——难看，但不会坏。**这是一个刻意的向下兼容设计。**

**踩过的坑**：一开始把 opcode 的规则写成「ESC + 三个**数字**」，正则是 `/^\d{3}$/`。后来在扩充方言里撞到 `10a`、`11a`、`2k1`–`2k4` 这种**带字母**的码，全部被当成一般消息，把控制字符连同内容印在画面上。更狠的是还有一个 `1085`——**四个字符**。

**优点 / 罩门**：分层设计的优点是**每一层可以独立测试**——本项目的样式解析器与 opcode 解析器都是纯函数，加起来 57 条单元测试不需要任何网络或 DOM。罩门是**分隔符没有跳脱机制**：如果房间名里真的出现 `$zj#` 这四个字，协议就会解错。实务上靠「中文内容不会出现这种组合」硬撑过去。

**设计对照**：

| 协议 | 分帧方式 | 结构化方式 | 向下兼容 |
|------|---------|-----------|---------|
| **ZJMUD** | `\n` 逐行 | ESC+opcode ＋ 字符串分隔符 | ✅ 旧 telnet 可读（虽然难看） |
| MXP | telnet 子协商 | 类 HTML 标签 | ✅ 标签可被忽略 |
| GMCP | telnet 子协商 | JSON | ❌ 纯 telnet 看不到 |
| 纯二进位 | 长度前缀 | 自订结构 | ❌ 完全不兼容 |

**效益**：一套协议同时养活两种客户端，服务器端只需要多送几行带前缀的文本，不必维护两条数据路径。

> 💡 君之一席话
> **最务实的协议演进，往往不是推倒重来，而是在既有的文本流上偷偷加一层记号——让不认识它的人只觉得有点杂讯，让认识它的人看见一整个接口。**

> 🔍 老手视角──真正的门道
> 这种「在人类可读串流上叠机器标记」的设计，在协议史上反复出现：HTTP 的 header、email 的 MIME、终端机的 ANSI 本身都是。它们的共同代价也一样——**没有跳脱串行的分隔符，就是一颗延迟引爆的地雷**。ZJMUD 用 `$zj#` 这种罕见组合降低碰撞几率，但没有消灭它。真正的解法是长度前缀或跳脱规则，代价是失去人类可读性。老手在选型时会问一个问题：**「这条串流未来会不会承载用户可控的内容？」**——如果玩家能把 `$zj#` 打进聊天消息，这个协议就有注入风险。本项目的服务器没有过滤，这是一个已知但未修的弱点。

## 005　行级 opcode — 33 个码撑起整个接口

**标签**：`#opcode` `#分派器` `#UI映射` `#副作用` `#死码`
**证据等级**：🟡 服务器 `zjmud.h` ＋ 🟠 反编译 ＋ 🟢 实机

**起源**：服务器端的定义档 `include/zjmud.h` 是整套协议最权威的来源——27 个激活中的宏，每一个都带中文注解。这份文件是这个项目最幸运的发现。

**技术内核**：opcode 分成几个清楚的家族：

| 家族 | 码 | 职责 |
|------|-----|------|
| **房间** | 002 标题、004 描述、003 出口、005 对象 | 构成主画面 |
| **反向操作** | 903 删出口、905 删对象、913 清空出口 | `9xx` = `0xx` 的反向 |
| **叠层** | 007 详情、008/009 动作列、010 对话框、011 地图、013 长文本、020 弹出菜单 | 盖在主画面上 |
| **消息** | 015 顶部飘字、016 战斗、100 聊天 | 分流到不同区块 |
| **状态** | 012 属性条、006 快捷钮、021 标题按钮、022 血条更新 | 周边 HUD |
| **控制** | 000 登录状态、014 代送指令、997/998 传输模式、999 退出 | 不显示内容 |

其中 **`ESC014` 特别值得注意**——它让服务器可以**叫客户端主动送出一条指令**。服务器原代码里用了 98 次，是整套流程的驱动骨干。没实作它，大量交互会断在半路。

**另一个关键是 `ESC002` 的副作用**。它不只设置房间名，还会**连带清空出口区、对象区、标题按钮、战斗面板**。这是「换房间」的隐含信号——服务器不会另外送一个「清空」指令，它假设客户端知道。

**解决的痛点**：把一条线性的文本串流，拆解成十几个各自更新的 UI 区块。

**踩过的坑**：客户端反编译里的分派链，`ESC006` **出现了两次**——第一次是「设置自订按钮」，第二次是「依 tag 删除对象」。因为是 if/else-if 链，**第二个分支永远不可达**。

照着死码实作，会浪费时间写一个永远不会被触发的处理器，还可能在某天「修好」它而引入真正的 bug。**辨识死码是反编译阅读的基本功**。

**优点 / 罩门**：27 个内核码撑起一个完整的图形接口，密度很高。罩门是**编号没有语意分区**——`045`（打开网页）夹在 `024` 和 `100` 中间，`900` 不遵循 `9xx = 反向操作` 的规律。这种历史累积的不规则，让添加 opcode 时很容易撞号（第三篇会看到真的撞了）。

**规模对照**：

| mudlib | 定义的 opcode | 实际使用 | 落差原因 |
|--------|--------------|---------|---------|
| LPMud-Name | 27 | 21 | 部分功能未开 |
| 大梦江湖（新协议） | 101 | 81 | 真正的扩充方言 |
| nt7 | **102** | **16** | header 从别处拷贝，扩充码从未使用 |

**效益**：实作 27 个内核码，就能与收藏中 14 个不同 mudlib 互通——这 27 个是所有方言的最大公因数。

> 💡 君之一席话
> **一个 opcode 表最有价值的信息，不在它列了什么，而在它的编号空隙与撞号——那是协议演化留下的地层。**

> 🔍 老手视角──真正的门道
> 判断一套协议的实作优先级，老手不看 opcode 表的顺序，而看**服务器原代码里的使用次数**。本项目扫出来的分布极度不均：`ZJOBLONG`（详情）用了 531 次、`ZJOBACTS2`（动作列）448 次、`ZJFORCECMD`（代送指令）98 次，而 `ZJYESNO`（NPC 对话框）在该服务器**一次都没用**。这意味着：花力气做对话框的精美动画，不如先把「详情＋动作列」这条主干做扎实——那才是玩家 95% 的时间会看到的东西。可落地的做法：拿到任何协议规格，**先写一支统计脚本扫 server 端的实际发送点**，用频率排出实作顺序，而不是照着文档从第一页做到最后一页。
