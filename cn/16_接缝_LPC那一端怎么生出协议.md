## 043　一行 `write()` — ZJMUD 是一套 driver 不知道的协议

**标签**：`#协议分层` `#mudlib` `#GMCP` `#MXP` `#撞号` `#逆向着力点`
**证据等级**：🟡 服务器原代码（`include/zjmud.h`、约 4,000 处发送点）＋ 🟡 FluffOS apply 清单

**起源**：本书前七篇解剖了 116 个 opcode，却一直没有回答一个很基本的问题：
**这些 opcode 是谁定义的、谁实作的、谁有权添加？**

答案让人有点意外：**driver 完全不知道它们存在。**

**技术内核**：把 `include/zjmud.h` 摊开看，整套协议的实作就是几行宏。

```c
#define ESA         "\x1b"              // 原代码里是一个裸的 ESC 字节
#define ZJSEP       "$zj#"
#define ZJBR        "$br#"

#define SYSY        ESA + "000"         // 登录状态
#define ZJTITLE     ESA + "002"         // 房间标题
#define ZJEXIT      ESA + "003"         // 出口
#define ZJLONG      ESA + "004"         // 房间描述
#define ZJOBLONG    ESA + "007"         // 详情
#define ZJOBACTS2   ESA + "009"         // 动作列
#define ZJFORCECMD  ESA + "014"         // 代送指令
```

`ESA + "002"` 是 **LPC 的字符串串接**——没有任何魔法，
它在编译期变成一个四字符字符串 `"\x1b002"`。

而「送出一个 opcode」长这样：

```c
write(ZJTITLE + query("short") + "\n");
```

**就这样**。没有 driver 支持、没有 telnet 子协商、没有注册、没有能力协商。
从 driver 的角度看，这只是 mudlib 调用了 `write()` efun 送出一串字节，
其中第一个字节刚好是 0x1B。

**这件事的三个后果，正好解释了本书前面留下的三个谜题。**

### 后果一：换 driver，协议还在

driver 不知道协议存在，所以协议不会因为 driver 升级而坏掉。
本项目把一份 1990 年代的 mudlib 丢进 2026 年编出来的 WebAssembly driver，
opcode 一个不少地照样出现在在线——**因为它们对 driver 而言只是字符串**。

这也是为什么本书 §032 那批兼容性修正里，**没有任何一条和协议有关**：
坏掉的是 `static` 修饰词、类型检查、字符串索引、文件权限——
全是 LPC 语言与运行环境的问题，协议层毫发无伤。

### 后果二：没有注册中心，所以会撞号

任何人拿到 mudlib，都可以加一行 `#define`。不必跟谁报备，
因为根本没有「谁」可以报备。
于是三个世代的方言各自往同一个编号空间里加码，
撞了 4 个号（§010）；`045`（打开网页）夹在 `024` 和 `100` 中间（§005）；
一份 header 定义了 102 个 opcode 而实际只用 16 个（§009）。

**这些不是设计失误，是「没有中央权威」这个前提的必然结果。**
本书第三篇整篇在描述的现象，根因只有这一句。

### 后果三：逆向的着力点在 mudlib，不在 driver

这是对本项目最实际的一条。
如果协议住在 driver 里，本书第二篇要做的事会是反编译一个 5.5 MB 的 C++ 运行档。
但它住在 mudlib 里——**一份带中文注解的 LPC 标头档**，
外加约 4,000 处可以直接 grep 的发送点。

§005 那个「按使用次数排实作优先序」的做法之所以可行
（`ZJOBLONG` 531 次、`ZJOBACTS2` 448 次、`ZJFORCECMD` 98 次、`ZJYESNO` **0 次**），
也是因为发送点在脚本层，一支 grep 就能统计。

**设计对照：协议住在哪一层，决定了它的一切性质。**

| | **driver 层协议** | **mudlib 层协议** |
|---|-----------------|------------------|
| 例子 | GMCP、MSDP、MXP、MSP、ZMP、NAWS、TTYPE | **ZJMUD**（以及各家中文 MUD 的自订方言） |
| driver 支持 | 有专属 apply（`gmcp` `msdp` `mxp_tag` `zmp` `window_size` `terminal_type`…） | **无** |
| 传输方式 | telnet 选项协商 + 子协商（`IAC SB … IAC SE`） | **就是普通的输出文本** |
| 能力协商 | 有（双方 `WILL`/`DO` 谈好才激活） | **无**（服务器一律送，客户端自己看着办） |
| 谁能添加字段 | 要改 driver，或走标准的扩充机制 | **任何拿到 mudlib 的人** |
| 纯 telnet 客户端看到什么 | 什么都看不到（在子协商里） | **看得到，只是有点乱**（§004 的向下兼容） |
| 撞号风险 | 低（有事实上的注册表） | **高**（本书第三篇） |
| 逆向难度 | 要读 driver 或抓子协商 | **读 header** |

第五列与第七列是同一枚硬币的两面：
**「任何人都能加」与「一定会撞号」是同一件事的两种说法。**

**踩过的坑**：本书 §004 提过一个没修的弱点，现在可以说清楚它为什么难修——
分隔符 `$zj#` 没有跳脱机制，玩家若把 `$zj#` 打进聊天消息就是注入。
修它需要在**每一个发送点**做跳脱，而发送点有约 4,000 处，分散在整份 mudlib 里，
由不同的人在二十年间写成。
**没有中央权威的代价，在需要做全域改动时一次付清。**

**优点 / 罩门**：优点是**演化速度**——加一个 UI 面板不必碰 driver、
不必等任何人 review，写一行 `#define` 加一个 `write()` 就上线了。
本书第三篇看到的三个世代方言（27 → 101 → 102 个 opcode），
是这个自由度的直接产物。
罩门就是上面那三条后果的下半身：撞号、无法做全域改动、没有能力协商
（服务器不知道对面是不是认得 opcode 的客户端，只能一律送，
靠「旧 telnet 客户端会把它当乱码印出来」硬撑）。

**效益**：对任何要逆向一套 MUD 私有协议的人，这一节给的是**第一个该问的问题**：
**「这套协议住在哪一层？」**
在 telnet 子协商里的，去读 driver 与 RFC；
混在一般输出文本里的，去读 mudlib 的 header——
后者通常只要一个下午。

> 💡 君之一席话
> **协议住在哪一层，决定了谁能改它、谁会撞号、以及你该去哪里逆向它**——这是拿到一套私有协议时最先要问的问题，比任何一个字节的意义都更早该问。

> 🔍 老手视角──真正的门道
> ZJMUD 选择不走 telnet 子协商，这在协议设计上是一个**刻意的降级**，而且降得很聪明。子协商的好处是干净（纯 telnet 客户端完全看不到）、有能力协商；代价是你必须让 driver 参与，而 driver 不是你的。ZJMUD 的作者把协议塞进一般输出文本，换到的是「**我一个人就能完成这件事**」——不必等 driver 作者、不必说服任何人、不必发版本。老手在评估这种降级时看的不是技术优劣，而是**组织成本**：一个要跨团队协调才能改的干净方案，往往输给一个当天就能上线的脏方案，而且输得很彻底。真正该做的是把脏方案的代价**明码标出来**——本例的代价是「分隔符没有跳脱」与「一定会撞号」，两者都可以在第一天就写进文档，并在编号规则上预留分区（例如「第三方扩充一律用 5xx」）。可落地的判准：当你要在一个不归你管的东西上加扩充点，先算「请对方加一个 hook」要花几周；若答案大于三，就设计一个不需要对方参与的方案，**然后把它的代价写下来**。

## 044　握手那一行 — `crypt()`、`input_to()` 与一个没在验的验证

**标签**：`#握手` `#登录流程` `#input_to` `#安全` `#证据等级`
**证据等级**：🟡 服务器原代码（`adm/daemons/logind.c`、`adm/single/master.c`）＋ 🟢 实机封包

**起源**：本书 §008 从**线路上**描述了登录握手：
连上之后服务器送一行 `ver1.0:<某串东西>`，客户端回一个东西，然后才轮到帐密。
当时那串东西是什么、验什么、验不验得过，**只能从外部观察**。

现在我们知道 driver 与 mudlib 的关系了，可以直接把 LPC 那一端读出来。

**技术内核**：整条链是四个 apply／efun 接起来的。

### ① 连接抵达 → `master::connect(port)`

```c
object connect(int port)
{
    object login_ob;
    mixed err;
    if (port == 5003) {
        set_encoding("GBK");            // ★ §039／§041 的那条规则
    }
    err = catch(login_ob = new(LOGIN_OB));
    if (err) {
        write("现在有人正在修改用户连线部份的程序，请待会再来。\n");
        write(err);
        destruct(this_object());
    }
    login_ob->set("port", port);
    return login_ob;                    // ← 这条连接从此附着在这个对象上
}
```

三个细节值得停一下：

- **`connect()` 收到的是端口号**，这是服务器唯一知道「这条连接从哪个门进来」的方式，
  也是编码分支的全部依据。
- **整个登录对象的创建被 `catch()` 包住**（§037 的 `F_CATCH`）——
  登录对象炸掉时，连接还活着，还能写一行人话给玩家。
  这是一段写得很好的防御性 LPC。
- 回传的对象就是这条连接的 **interactive object**，
  §036 那一整排 interactive apply 从此往它身上调用。

### ② `logon()` — 握手行在这里产生

```c
void logon(object ob)
{
    string str;
    if (BAN_D->is_banned(query_ip_name(ob)) == 1) { ... destruct(ob); return; }
    write("\n");
    str = crypt(ZJKEY, "byname666");        // ZJKEY = "123456789abcd"
    write("ver1.0:" + str + "\n");          // ← 线路上看到的那一行
    input_to("jiance", ob, str);            // ← 下一行输入交给 jiance()
}
```

`crypt(key, salt)` 是传统 Unix DES crypt，**两个参数都是原代码里的常数**，
所以**这串挑战值每次连接都一样**——它不是 nonce，没有随机性。

`input_to()` 是 LPC 的交互内核：**「下一行输入不要当指令，交给这个函数」**。
整个登录流程就是一串 `input_to` 接力。

### ③ `jiance()` — 「版本验证」

```c
void jiance(string arg, object ob, string str)
{
    if (!arg) { input_to("jiance", ob, str); return; }   // 空行 → 再问一次
    ob->set_temp("web_log", 1);
    if (arg != "//") {
        write("版本验证成功\n");
        input_to("get_user", ob);
    } else {
        start_wiz = 1;
        get_user("name║name1║byname666║byname666", ob);
    }
}
```

**这是这一节最重要的发现，而且只有读原代码才看得到：**

> **`jiance()` 根本没有验证任何东西。**
> 它把 `str`（刚刚算出来的 crypt 值）当参数收进来，**但一次都没有用到**。
> 只要送出的不是空行，就一律印「版本验证成功」放行。

从线路上看，这是一个「挑战－回应」握手；
从原代码看，它是一个**只检查「你有没有回话」的存活探测**。

这解释了本项目 `src/js/telnetlogin.js` 里那条看起来很随便的规则：

```js
nt7: [
  P(/^ver1\.0[,:]/, 'zjclient', 'challenge', { req: false }),
  ...
]
```

**回 `zjclient` 就过**——不是猜对了密码，是因为**根本没有密码可以猜**。
这条规则在写的时候是实测归纳出来的（🟢），现在有了原代码佐证（🟡），
两份证据互相印证。

**★ 安全揭露：`else` 分支是一个后门。**

送出 `//` 这两个字符，会走进第二个分支：
`start_wiz = 1`，并直接以硬编的凭证
`"name║name1║byname666║byname666"` 调用 `get_user()`——
**跳过帐号密码，以一个固定帐号登录，且带着 `start_wiz` 旗标**
（该旗标在 `logind.c` 里有 11 处引用，用来略过各种登录检查）。

这段代码在上游是公开的，本节只是把它的行为说清楚。
**任何要用这份 mudlib 开服的人，第一件事应该是删掉这个分支。**
本项目的 WASM 展示站不受影响——每个访客拿到的是一份跑在自己分页里、
重整就消失的世界（§032），没有可以被入侵的对象。
项目的其他凭证与外送问题记在仓库根目录的 `SECURITY_NOTES.md`。

### ④ `get_user()` — 帐密字段

```c
private void get_user(string arg, object ob)
{
    // arg = 账号║密码║密文║email
```

**四个字段，用 `║`（U+2551）分隔**——这正是本书 §008 从线路上量到的格式，
现在有了它的出处与字段名。

**解决的痛点**：把 §008 的每一个「观察到的行为」升级成「知道它为什么」：

| §008 的观察（🟢 实机） | §044 的解释（🟡 原代码） |
|---------------------|----------------------|
| 连上后先收到一行 `ver1.0:…` | `logon()` 里的 `write()` |
| 那串值每次连接都一样 | `crypt()` 的两个参数都是常数 |
| 回什么都能过 | `jiance()` 没有比对 `str` |
| 之后送 `账号║密码║密文║email` | `get_user()` 的参数格式 |
| 端口 5001 是 UTF-8、5003 是 GBK | `master::connect()` 的 `if (port == 5003)` |

**这张表就是「证据等级」这条规矩的价值示范**：
五条断言全部先由实机封包确立（🟢，可以直接拿来写客户端），
再由原代码补上原因（🟡，让你知道它在什么情况下会变）。
**两者都需要——只有 🟢 你不知道边界，只有 🟡 你不知道它有没有被实际运行。**

**踩过的坑**：`input_to()` 的提示**没有换行**。
`get_user` 这一路还好（zjmud 客户端有自己的登录窗口），
但 §045 那些传统 telnet lib 会印「请输入您的英文名字：」然后就停在那里等，
**行尾没有 `\n`**。一个逐行分帧的读取器会把它一直留在缓冲里，
于是客户端「什么提示都没看到」。
本项目的处理是**提示行冲洗**：服务器静默一小段时间（300 ms）后，
把分行器里未断行的残余当成一行交出去（`telnet.js` 的 `flushPartial`）。

**优点 / 罩门**：优点是这个登录流程完全用 `input_to` 串成，
**可读性极高**——一个函数一个步骤，顺序就是程序顺序。
罩门是它**没有状态机**：每一步用「下一行输入交给谁」隐式表达，
所以任何一步忘了调用 `input_to`，连接就会安静地卡在那里，
既不报错也不断线。本项目的 `boot-test.mjs` 因此必须自带逾时。

**效益**：这一节把本书第二篇的握手规格从「照做就能连上」
升级成「知道哪些部分可以变、哪些不会变」。
具体地说：**挑战值是常数所以可以硬编，但验证逻辑是可改的，
所以客户端不该假设「随便回都过」永远成立**——
本项目的 `telnetlogin.js` 因此把它写成一条**可以被覆写的 profile 规则**，
而不是写死在连接流程里。

> 💡 君之一席话
> **一个看起来像挑战－回应的握手，可能只是在确认你还活着**——从线路上你分不出这两者，只有读到实作那一行才知道；这正是为什么「实机封包」要排在最前面，而「原代码」不能被省略。

> 🔍 老手视角──真正的门道
> `jiance()` 这种「收了参数却没用」的验证，在逆向工作里出现的频率高得惊人，而且有一个共同的成因：**它曾经是真的**。有人一开始写了比对，后来为了调试或兼容旧客户端把它拿掉，却留下了整个外观——函数名、参数、印出来的「验证成功」。老手看到一个验证逻辑时，会先找**它的失败路径**：没有 else、没有错误消息、没有断线处理的验证，通常根本不验。这个判准比读懂验证算法本身快得多，而且在只有反编译的情况下也适用——**看它有没有处理失败，比看它怎么判断成功更能说明问题**。可落地的做法：逆向一个握手时，优先做的实验不是「送对的值」，是**送一个明显错的值**；对面的反应会在一秒内告诉你这个验证是真是假，而读懂算法可能要一天。

## 045　让 zjmud 客户端玩不是 zjmud 的 mud — 会话层代打

**标签**：`#兼容层` `#会话层` `#profile` `#取舍` `#边界`
**证据等级**：🟢 本项目实测（`src/js/telnetlogin.js`，每条规则出自对应 lib 的 logind 原代码）

**起源**：`mudlibs.fluffos.info` 是 FluffOS 社群做的中文 MUD 博物馆——
**199 个 1990 年代以降的中文 LPC mudlib，全部用 WebAssembly 跑在浏览器里，
其中 193 个标为可玩**。本项目的 `libs/` 布局就是参考它的 `fluffos/mudlibs` 仓库来的。

于是一个很自然的念头：既然 driver 一样、加载方式一样，
**能不能用 zjmud 客户端去玩那 193 个？**

答案是：**连得上、看得到招牌、进不去。**

**技术内核**：问题出在会话层，而不是传输层或协议层。

```
传输层   TCP／WASM 字节管道            ✅ 一样
telnet   IAC 协商                        ✅ 一样（driver 都送）
分帧     \n 逐行                         ✅ 一样
─────────────────────────────────────────────────────
会话层   登录对话                        ❌ 完全不同
协议层   ESC + opcode                    ❌ 对方没有
```

zjmud 客户端的登录窗口收到帐密后，送的是 `账号║密码║密文║email`（§044）。
传统 telnet lib 看到的是一行含有 `║` 的怪字符串——它想要的是
「请输入您的英文名字：」的答案。

**解法：让客户端按提示把这段对话演完。**

登录对话（招呼 → 帐号 → 密码 → 确认 → 建角）是一段
**与游戏内容无关的固定剧本**。既然如此，客户端可以代替用户一行一行回答：
服务器每印一行，接应器比对这一行像哪一步，把对应的输入送回去。

```js
const P = (match, send, note = '', opts = {}) => ({ ... });

export const PROFILES = {
  dongfanggushi2: [
    P(/您的英文名字：/,                 '{id}',   'name'),
    P(/新的人物.*\(y\/n\)|您确定吗\(y\/n\)/, 'y',  'confirm'),
    P(/请再输入一次您的密码/,           '{pw}',   'pw-confirm'),
    P(/请设定您的密码：/,               '{pw}',   'pw'),
    P(/电子邮件地址：/,                 'a@b.c',  'email'),
    P(/你的选择：/,                     'human',  'race'),
    P(/男性\(m\)的角色或女性\(f\)/,      'm',      'gender'),
    P(/您的中文名字：/,                 '秦风',   'cname'),
  ],
  // …其他家族，以及 generic-cn 退路
};
```

四个设计决定，每一个都有代价：

| 决定 | 理由 | 代价 |
|------|------|------|
| **规则由上往下比对，一行最多触发一条** | 提示字符串会互相包含（「请再输入一次您的密码」含「密码」） | 顺序变成隐性契约，改动要小心 |
| **`once` 语意（触发过就不再触发）** | 服务器重印提示时不要重复送 | 需要一个 `seen` 集合 |
| **帐密来自登录窗口，其余（email／种族／中文名）用固定值** | 那些字段用户不在乎，也没有 UI 可问 | 所有用这条路径建的角色 email 都一样 |
| **`generic-cn` 退路，字眼取自多个家族 logind 的交集** | 193 个 lib 不可能一个一个写 profile | 交集规则比专属 profile 脆 |

**整层都在客户端**——mudlib 一个字节都不动，driver 也不用改。

**踩过的坑（每一条都是实测，不是预防性猜测）：**

| 坑 | 症状 | 真因 |
|----|------|------|
| 性别答错不能重来 | 建角时 runtime error 直接断 | `dongfanggushi2` 的 logind 在性别 retry 分支有 bug——**必须一次答对** |
| 中文名被拒 | 卡在「请您用中文取名字」 | 该 lib 的 `is_chinese()` 逐字节判断（§032）；所以 profile 直接送一个已知合法的中文名 |
| 提示看不到 | 接应器一条规则都没触发 | `input_to` 的提示**没有换行**（§044），逐行读取器把它留在缓冲里 → 需要 `flushPartial` |
| nt7 卡在第一行 | 收到 `ver1.0:` 就没下文 | 那是 zjmud 握手壳 + telnet 交互登录的混血；补一条「看到挑战行就随便回」的规则（§044 解释了为什么随便回就过） |

**★ 这一层的边界，必须说清楚。**

接应器**只做到第一层：登录 → 进世界 → 纯文本可玩**。
房间面板、血条、动作列那些需要**结构化数据**的 GUI 一律没有——
因为对方根本没有送 opcode。

要更进一步只有两条路，而且都不便宜：

| 路线 | 做法 | 代价 |
|------|------|------|
| **A：客户端剖析文本** | 用规则从「大厅 - 你站在一个宽敞的大厅里。出口有：north east」剖出房间名与出口 | **脆**。每个 lib 的排版不一样，改版就坏；本质上是在重蹈本书 §004 说的「没有跳脱的分隔符」老路 |
| **B：改 mudlib 加 opcode** | 在对方的 mudlib 里加上 `ESC003` 之类的输出 | 要动别人的 mudlib，等于替 193 个 lib 各做一次移植 |

本项目选了**两条都不走**，只交付第一层，并把边界写在文件的顶端注解里。
取舍的完整讨论在 `docs/zjmud_migration_SOP.md` §5。

**优点 / 罩门**：优点是**一份客户端服务两个世界**——
zjmud 方言的 mud 走完整 GUI，传统 telnet 的 mud 走纯文本，
用户只感觉到「有些 mud 没有面板」。
罩门是 profile 表是**规则的集合而不是状态机**：
它不知道自己现在在登录流程的第几步，只知道「这一行像什么」。
所以一个提示字符串出现在意料之外的位置，它就会答错。
这是刻意的取舍——状态机要为 193 个 lib 各写一份，规则表可以共用。

**效益**：`mudlibs.fluffos.info` 那 199 个 lib 有 193 个标为可玩，
本项目收录 17 个并且 17 个都可玩。
两者的差别不在 driver（同一份），而在**客户端要不要理解对方的方言**——
博物馆用的是通用 telnet 终端机（xterm.js），
本项目用的是一个懂 ZJMUD 方言的 GUI 客户端，
所以它必须额外处理「对方不讲这个方言」的情况。
**这一节就是那笔额外费用的帐单。**

> 💡 君之一席话
> **兼容层最重要的不是它做到了什么，是它明确地不做什么**——一个诚实标好边界的半套方案可以长期维护，一个假装自己完整的方案会在每个新案例上被打脸。

> 🔍 老手视角──真正的门道
> 这一节的取舍有一个很通用的形状：**面对 N 个不一致的对端，你可以写 N 个精确的适配器，或一个模糊的通用规则，或什么都不做只交第一层。** 多数团队会不自觉地选第一个，因为每一个适配器单独看都很合理——结果三年后有 40 个适配器、没有人敢删、每次上游改版都要全部重测。本项目选的是「几个精确 profile + 一个通用退路 + 明确的功能边界」，关键在最后一项：**功能边界压低了，适配器就不需要精确**。登录对话只有五六个步骤，猜错了用户重试一次就好；如果目标是完整 GUI，每个 profile 就得处理几十种输出格式，那才是真正会失控的地方。可落地的判准：在写第三个适配器之前先停下来问——**「如果我把功能范围砍一半，还需要几个适配器？」**答案常常是「一个都不用」。

## 046　一个字节的全程 — 从 LPC 的 `write()` 到浏览器的 DOM

**标签**：`#全链路` `#分层` `#收束` `#端到端验证`
**证据等级**：🟢 本项目实测（`verify-fullstack.mjs` 每次建置都跑）

**起源**：这本书写到这里，两端都摊开了。最后把它们接起来——
**追一个字节，从它在 LPC 里被写出来，到它变成画面上的一个房间标题。**

**技术内核**：WASM 版的完整路径，十一站，全部在同一个分页里：

```
① LPC        write(ZJTITLE + "大厅" + "\n")
                └─ ZJTITLE 在编译期已是字符串 "\x1b002"（§043）
                          ↓  write() efun
② VM         F_ 指令运行，svalue 进出双堆栈（§037）
                          ↓
③ comm.cc    用户输出缓冲（每个平台同一份 code）
                          ↓
④ telnet.cc  telnet 编码（0xFF 跳脱成 0xFF 0xFF）
                          ↓
⑤ Transport  WasmConsoleTransport::write()（§040）
                          ↓
⑥ JS         Module.fluffos.onOutput(id, bytes)
                          ↓
⑦ telnet.js  剥除 IAC、产生「一律拒绝」的回复、逐行切分（§附录 B）
                          ↓
⑧ protocol.js 取行首 4 字符 → "\x1b002" → opcode 002 → { kind:'title', … }（§005）
                          ↓
⑨ ansi.js    字段文本里的样式方言 → span 描述（§007）
                          ↓
⑩ store.js   reducer 更新状态；opcode 002 的副作用连带清空出口／对象／标题按钮（§005）
                          ↓
⑪ ui.js      DOM 更新 → 玩家看到房间标题变成「大厅」
```

**这条链上的每一站，本书都有一节在讲**，而它们的分工可以用一句话概括：

| 站 | 谁的责任 | 这本书的哪一篇 |
|----|---------|--------------|
| ①② | mudlib 作者 + LPC VM | 第八篇（§037、§043） |
| ③④⑤ | driver，跨平台共用 | 第八篇（§040） |
| ⑥ | 移植接缝 | 第八篇（§042） |
| ⑦ | 传输层清理 | 第二篇（§006） |
| ⑧⑨ | **纯函数**，可单元测试 | 第二、三、六篇 |
| ⑩ | 状态容器 + reducer | 第四、六篇（§022、§023） |
| ⑪ | DOM 组件 | 第六篇（§024） |

**三个观察，是把两端接起来之后才看得出来的：**

**其一：桥接版与 WASM 版的差别只有一站。**

```
桥接版：  ⑤ SocketTransport → TCP → bridge/server.mjs → WebSocket → ⑥
WASM 版： ⑤ WasmConsoleTransport ─────── 函数调用 ───────────────→ ⑥
```

第 ⑥ 站之后**完全相同**，第 ⑤ 站之前也**完全相同**。
这是本书第四篇那个「双形态」架构的最终验收：
**Transport 抽象在客户端与 driver 两侧各有一份，而且它们的分界线画在同一个位置。**
这不是巧合——两边面对的是同一个问题（「字节从哪来」与「字节往哪去」），
所以收敛到同一个形状。

**其二：协议层（⑧⑨）两端都不知道对方存在。**

driver（③④⑤）不知道 opcode（§043）；
`protocol.js`（⑧）不知道 driver（它只吃字符串数组）。
**这条链上最内核的那个知识，两端都不持有**——
它只存在于 mudlib 的 header 与客户端的解析器里，隔着八站遥相呼应。
本书第一篇之所以能只靠「一份 header + 一个 APK + 53 行封包」还原整套协议，
正是因为协议知识被压缩在这两个点上。

**其三：静默失败集中在特定几站。**

| 站 | 出错时的表现 |
|----|------------|
| ① mudlib apply 名字打错 | **静默**（§036） |
| ① preload 对象加载失败 | **静默**（§038、§041） |
| ⑤⑥ 重入／connId 未赋值 | **静默**（§042） |
| ⑦ 没剥 IAC | 解码炸掉——**会叫** |
| ⑧ opcode 不认得 | 当成一般消息印出来——**看得到** |
| ⑩⑪ reducer／DOM | 例外——**会叫** |

**会叫的都在客户端，静默的都在服务器侧与接缝上。**
这解释了本项目为什么把验证重心放在端到端：
前半段没有任何东西会替你报错。

**效益**：这条链最后被固化成一条指令：

```bash
node webclient/tools/verify-fullstack.mjs
```

真 DOM、真 wasm driver、真 HTTP——
选 mud → driver 开机 → 连接 → 登录 → 建角 → 进世界 → 换另一台 mud。
**十一站全部走一遍，每次建置都跑。**

本书开头那句内核命题，到这里可以收尾了：

> 逆向工程的尽头，不是「我看懂了」，而是「我能证明它，而且我的实作经得起真机打脸」。

第八篇补上的，是这句话的另一半——
**「真机」是什么，你也得看懂**。
一个 1989 年设计的虚拟机、一次 1992 年的分家、一份 2026 年编出来的 WebAssembly，
以及一套 driver 从头到尾都不知道自己在传的协议。
**知道对面是什么，你才知道哪些观察是稳定的，哪些只是这次刚好。**

> 💡 君之一席话
> **把一条链的两端都摊开之后，才看得出知识集中在哪两个点上**——而那两个点，就是逆向该用力的地方，也是文档该写厚的地方。

> 🔍 老手视角──真正的门道
> 这一节做的事叫「**全链路走查**」，它的价值不在发现 bug，在**发现责任的空隙**。把十一站列出来之后，三个原本说不清楚的问题自己有了答案：桥接版与 WASM 版差在哪（一站）、协议知识住在哪（两个端点）、为什么测试要做成端到端（前半段全部静默）。这些结论没有一个需要新的信息——它们一直都在，只是分散在八个章节里，没有被排成一列。老手在接手一个系统时，很早就会做这件事：**挑一个最典型的输入，从它进入系统的第一奈秒追到它离开的最后一刻，把每一站列出来，标上「谁负责」与「出错时会不会叫」**。这张表通常一个下午就能做完，而它回答的问题比读三天原代码还多。可落地的做法：把这张表放进 README 或 onboarding 文档的第一页——新人问的前十个问题，有八个能在上面直接找到答案。
