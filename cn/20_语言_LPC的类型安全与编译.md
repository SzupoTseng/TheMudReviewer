## 058　一个可以关掉的类型系统

**标签**：`#LPC` `#类型系统` `#编译期` `#strict_types` `#技术债`
**证据等级**：🟡 上游 `docs/lpc/types/general.md` ＋ 🟢 本项目实测（§032）

**起源**：读中文 mudlib 时会看到很多这种东西：

```c
mixed query(string prop, int raw);
object connect(int port);
void logon(object ob);
```

看起来类型齐全。但官方文档对这件事的说法非常直白：

> **Normally, the type information is completely ignored, and can be regarded
> purely as documentation.**

**类型缺省是注解。**

**技术内核**：LPC 的类型检查有三个关键性质，缺一不可地解释了后面所有的坑。

### ① 缺省不检查，`#pragma strict_types` 才检查

类型可以出现在四个位置（全域变量、函数回传值、参数、区域变量），
但除非开了 `strict_types`，编译器只拿它做**优化提示**——
例如 `x` 声明成 `int` 时可以把 `x + 0` 化简掉，声明成 `string` 时就不行。

开了 `strict_types` 之后三件事同时成立：
- 函数**必须**声明回传类型；
- 所有参数**必须**有类型；
- 调用尚未定义的函数**必须**先有原型（`string func(int arg);`）。

### ② ★ 类型检查**只在编译期**，运行期完全不检查

> **The strict type checking is only used by the compiler, not at runtime.
> So, it is actually possible to store a number in a string variable
> even when strict type checking is enabled.**

**这一句就是 §032 那个 `is_killing(ob)` 的完整解释**：
一个声明收 `string` 的函数，被传进一个 object。

```
旧 MudOS：编译期检查较宽松 → 放行 → 运行期不检查 → 跑了很多年没事
FluffOS：编译期检查收紧     → 挡下 → 建角流程当场失败
```

**注意「跑了很多年没事」不是因为它是对的**，
是因为**没有任何一层会抓它**：编译期放行、运行期不看。
本书 §036 说过的那句话在这里有了机制上的解释——
**「它在原机上跑得好好的」不构成它是对的证据。**

### ③ `call_other()` 回传未知类型

```c
(string)call_other(ob, "short");   // 或
(string)ob->short();
```

编译器无法知道 `ob` 是什么、`short()` 回传什么，
所以 `call_other` 的回传类型是 unknown。
若 driver 编了 `CAST_CALL_OTHERS`，这个值**必须**转型；
否则缺省当成 `mixed`。

**这是 LPC 类型系统最大的破口**：mudlib 里跨对象调用（`->`）到处都是，
而**每一个 `->` 都是类型信息的断点**。
§036 提过 simul_efun 有一个相对的好处——
它的原型在编译期已知，**所以回传值不必转型，即使开了 `strict_types`**。

### 基本类型

| 类型 | 说明 | 传递方式 |
|------|------|---------|
| `int` | 32 比特整数（FluffOS 运行期为 64 比特） | **传值** |
| `float` | 浮点数 | **传值** |
| `string` | 不限长度（**不允许 `\0`**） | **传值** |
| `object` | 对象指针 | **传址** |
| `mapping` | 关联数组——§052 那棵属性树的载体 | **传址** |
| `function` | 函数指针（`(: :)`） | **传址** |
| 数组 `type *` | `int *arr;`；嵌套用 `mixed *` | **传址** |
| `void` | 只能用于函数回传 | — |
| `mixed` | 任何情境都合法——**「不好的实务，除非变量真的会装不同类型」** | — |

**传值／传址的分界有一个很容易踩的后果：**

```c
({ 1 }) == ({ 1 })      // → false
```

因为 `({ … })` **每次都产生一个新数组**，而数组的 `==` 比的是「是不是同一个」。
`int` / `string` / `float` 比值，其余比身分。

**另外一条**：改数组元素会影响所有指向它的变量，
但**改数组大小一定会配置一个新的**——所以「改内容」与「改长度」的可见性不同。

**解决的痛点**：可关掉的类型系统解的是 1989 年的实际问题——
**mudlib 是给业余作者写的**。强制类型会让入门门槛上升，
而 LPMud 的整个价值主张就是「让不会 C 的人也能盖世界」（§033）。

**踩过的坑**：这个决定的帐单，本项目付了两次：

| 症状 | 根因 |
|------|------|
| `is_killing(ob)` 声明 `string` 却传 object（§032） | 编译期检查宽松 + 运行期不检查 |
| 一堆 mudlib 文件**没有** `#pragma strict_types` | 三十年前不开，今天也不敢补——补了会炸出上百个既有错误 |

第二列是关键：**类型检查是可以事后打开的，但没有人敢打开。**
一份跑了二十年的 mudlib，补一行 `#pragma strict_types` 会得到几百个编译错误，
其中绝大多数是「一直都错但没事」。
**这正是「缺省宽松」这个决定真正的成本——它不是一次性的，是不可逆的。**

**优点 / 罩门**：优点是入门极低、改动极快。
罩门是**错误的发现时机被推迟到不确定的未来**：
一个类型错误可能潜伏二十年，直到换一台 driver 才爆——
而那时原作者早就不在了。

**设计对照**：

| 语言 | 类型检查 | 事后补救的可能性 |
|------|---------|----------------|
| **LPC** | **缺省关，可用 pragma 开（逐档）** | 理论上可以，实务上不敢 |
| Python | 运行期；类型注解可选 + mypy | 逐模块渐进补（`# type: ignore` 当逃生口） |
| TypeScript | 编译期；`any` 是逃生口 | **设计上就支持渐进**（`strict` 分项开） |
| Rust / Java | 强制 | 没有这个问题 |

第三列是现代生态的答案：**渐进式类型化必须是设计目标，不能是事后的补救**。
TypeScript 之所以能被大规模采用，很大程度是因为它把「一半有类型」当成一等公民；
LPC 的 `#pragma strict_types` 虽然也是逐档的，
但它缺了逃生口（`any` 之于 TS、`mixed` 只能用在类型位置而非「不检查这一段」），
所以实务上是全有或全无。

**效益**：对读 mudlib 的人，这一节给的是一条判读规则：

> **看到类型声明，不要当成保证，当成注解——而且是可能过期的注解。**

本项目在还原协议时对 LPC 函数签名的态度就是这样：
签名说收 `string`，实际传什么要看调用点。

> 💡 君之一席话
> **一个缺省关闭的类型系统，收的不是类型的成本，是「发现错误的时机」的成本**——而这笔帐会在你最没有能力处理的时候寄来：换引擎、原作者消失、二十年后。

> 🔍 老手视角──真正的门道
> 「类型信息被当成注解」这件事有一个很少被说破的连锁效应：**它让类型声明本身失去了维护动力**。既然写错也不会有人告诉你，那么随着代码演化，签名与实际用法就会慢慢分岔——`is_killing(string)` 收 object 这种事不是有人故意写错，是**某次改动把传进去的东西换了，而没有人去改签名，因为改不改都一样**。这个现象在所有「文档与代码分离」的地方都会发生：注解、README、API 文档、`@param` 标注。老手判断一份类型／文档可不可信，看的不是它写得多完整，而是**「它错了会不会有人痛」**：CI 会失败的，可信；只是好看的，一律当成写作当下的快照。可落地的做法：**任何你希望长期正确的声明，都要想办法让它有一个会失败的验证**——类型检查、doctest、契约测试、schema 验证都行，没有的话，那份声明的保鲜期大约是下一次重构。

## 059　修饰词 — 一个关键字承载两个语意的三十年后果

**标签**：`#修饰词` `#static` `#nosave` `#兼容性` `#语意分裂`
**证据等级**：🟡 上游 `docs/lpc/types/general.md`（特殊类型）＋ 🟢 本项目实测（§032 首条修正）

**起源**：§032 那八条兼容性修正的**第一条**，是 17 份 mudlib 全部撞到的：

```
master.c syntax error
```

原因是 FluffOS 移除了 `static` 这个修饰词。
当时的处理是「补一行 `#define static` 不够，要照上游用 `__SENSIBLE_MODIFIERS__` **互斥**分岔」。
这一节解释**为什么补一行不够**。

**技术内核**：LPC 的「特殊类型」（修饰词）可以叠加在基本类型之前。

| 修饰词 | 对**函数** | 对**变量** |
|--------|-----------|-----------|
| `private` | 不能被 `call_other()` 调用，**继承者也拿不到** | 同上 |
| `public` | **一定**可访问，即使用了 private inherit | — |
| `static` | **≈ private**（不能被 `call_other()` 调用） | **不会被 `save_object()` 存、也不会被 `restore_object()` 还原** |
| `nomask` | **不能被继承覆写，也不能被 `shadow()` 盖掉** | 不能被覆写 |
| `varargs` | 可变参数个数（否则个数会被检查） | — |

**★ 问题全部出在 `static` 那一列：它对函数与变量是两个完全不相关的语意。**

```
static int foo() { … }     →  意思是「private」          （可见性）
static int counter;        →  意思是「不要存进存盘」       （持久性）
```

**一个关键字，两个正交的概念。**
在 1992 年这只是个小怪癖（C 的 `static` 本来就一词多义）；
到了三十年后要维护的时候，它变成一个无法自动迁移的问题。

FluffOS 的处理是**把它拆成两个意思明确的关键字**：

| 旧 | 新 | 意思 |
|----|----|------|
| `static`（函数） | **`protected`** | 可见性 |
| `static`（变量） | **`nosave`** | 持久性 |

并提供 `__SENSIBLE_MODIFIERS__` 让 mudlib 知道自己跑在哪一套语意上。

**于是「补一行 `#define static`」为什么不够就很清楚了：**

```c
#define static protected     // 变量会变成「protected 变量」→ 存盘语意全错
#define static nosave        // 函数会变成「nosave 函数」  → 可见性全错
```

**没有任何一个单一替换是对的**，因为原本那个关键字在两种位置有两种意思。
唯一正确的做法是**互斥分岔**——依 `__SENSIBLE_MODIFIERS__` 决定用哪一套，
而不是无条件重新定义。

**解决的痛点**：这一节解的是一类很具体的移植问题——
**当上游把一个关键字拆成两个，下游不可能用宏自动迁移。**

判准是：**拆分是不是信息无损的？**
- `static`（函数）→ `protected`：无损，机械替换即可；
- `static`（变量）→ `nosave`：无损；
- **但「哪一个是哪一个」需要语法上下文**，而 `#define` 没有上下文。

**所以这类迁移只能靠三种手段之一**：
① 上游提供兼容宏（FluffOS 走这条）；
② 写一支会解析语法的迁移工具；
③ 人工逐处改。

**踩过的坑**：本项目一开始走的是「补一行」，因为那是最省事的假设。
症状是**修好一个档又坏另一个档**——因为两种位置的错误会交替出现。
真正的教训不是「要看清楚语意」，而是：

> **当一个修正「修好 A 就坏 B」，通常代表你在用一个维度的手段
> 解一个两个维度的问题。**

**`#pragma` 全表**（同样是逐档生效，从指令处到档尾）：

| pragma | 作用 |
|--------|------|
| **`strict_types`** | 强制类型检查（§058）——**新代码强烈建议开** |
| `warnings` / `no_warnings` | 开关警告 |
| **`save_types`** | **编译后保留类型信息**，让继承它的对象能对它做类型检查 |
| `optimize` | 对这个档做额外的树优化 |
| `show_error_context` | 旧旗标（缺省开），已被 clang 风格诊断取代 |

`save_types` 值得注意：**类型信息缺省在编译后就丢掉了**，
所以继承者无法对父程序做类型检查——除非父档开了这个 pragma。
**这是 §058 那个「类型是注解」在继承链上的延伸**：
不只运行期没有类型，连编译期都只在**单一文件的范围内**有。

**`nomask` 的双重防护**值得单独记一句：它同时挡住继承覆写**与** `shadow()`。
这是 mudlib 保护关键函数（例如安全检查、金钱计算）的标准手段——
§062 会看到 shadow 有多容易被滥用。

**优点 / 罩门**：优点是修饰词极少（五个），心智负担低。
罩门就是本节的主题：**极少的关键字必然意味着一词多义**，
而一词多义在跨版本迁移时是最贵的一种债。

**效益**：对移植老 mudlib 的人，这一节给的是一条检查清单：
遇到「上游移除了某个关键字」时，先问**它原本有几个意思**；
答案大于一，就不要试图用宏解决。

> 💡 君之一席话
> **一个关键字承载两个概念，在写的时候省下的是一个名字，在迁移的时候付出的是一支语法解析器。**

> 🔍 老手视角──真正的门道
> 这件事最值得学的是 FluffOS 的**处理方式**而不是问题本身：它没有默默改语意（那会让旧 code 安静地跑错），也没有永远保留旧关键字（那会让债永远不还），而是**添加两个明确的关键字 + 一个让 mudlib 自我判断的宏**（`__SENSIBLE_MODIFIERS__`）。这个模式在生态演化里有个通用名字：**可侦测的破坏性变更**——破坏是真的，但下游有办法在编译期知道自己站在哪一边，因此可以写出同时支持两边的代码。相对地，最糟的做法是「同名不同义」：关键字还在、语意悄悄变了，下游没有任何办法侦测。老手在做破坏性变更时的顺序是：**能不能不破坏 → 破坏的话能不能让对方侦测到 → 侦测不到的话能不能让它编译失败**；三个都做不到，才考虑默认值改变。可落地的做法：任何要改语意的地方，**同时提供一个可以在编译期／启动期查找的版本旗标**——它的成本是一行，而它让下游有机会写出跨版本的代码。

## 060　继承的真相 — 程序与数据是分开存的

**标签**：`#继承` `#热重载` `#内存模型` `#幽灵bug` `#多重继承`
**证据等级**：🟡 上游 `docs/lpc/constructs/inherit.md`

**起源**：§051 把 mudlib 的对象模型讲成「特征组合」，
但没有回答一个更底层的问题：**多个对象 inherit 同一个文件时，内存长什么样？**

这个问题的答案，正好是 §038 那个「热重载的幽灵 bug」的根因。

**技术内核**：driver **把编译后的程序与全域数据分开存**。

> Because the FluffOS driver internally stores global data and compiled code
> separately, many different objects can use inheritance to share the same
> piece of compiled code. **Each of these objects will have its own local copy
> of any global variables defined by the object.**

```
      /feature/dbase.c  ──编译一次──▶  program（字节码，共用一份）
                                            ▲        ▲        ▲
                                            │        │        │
   inherit F_DBASE 的对象：            角色A     物品B     房间C
                                       各自一份 dbase 变量（数据不共用）
```

**一份程序、N 份变量。** 这正是 §038 说「一万把剑的成本是一万份变量，
不是一万份程序」的机制。

**★ 三条会咬人的规则，全部来自这个分离：**

### ① 重编子对象，不会重编父程序

> Recompiling either of A or B will not cause C to be recompiled.

合理，而且是性能上必要的。

### ② 但重编 A **会让 A 那一份「C 提供的全域变量」归零**

> **However, it will cause any global variables provided by C to lose
> whatever data they had.**

而且**只影响 A**——B 的那份不受影响。
**这就是 §038 那句「跑着新程序、带着旧数据」的另一半**：
不只是数据可能旧，**数据也可能整个消失，而且只消失一部分对象的**。

### ③ ★ 重编父程序，子对象**继续用旧版**，直到子对象也被重编

> **Note: if object B is recompiled, object A will continue to use the old
> version of object B until object A is also recompiled.**

**这一条就是 §038 热重载相依图的全部理由。**
改了 `/std/base.c` 之后，只重载它自己：

```
/std/base.c        ← 重编，新版
  ├─ /d/city/inn   ← 还链接着旧版 base，行为完全没变
  ├─ /d/city/shop  ← 同上
  └─ …             ← 同上
```

**没有错误、没有警告、没有任何征兆。**
你改了程序、存了档、下了 `update`，然后行为没变——
而多数人的第一反应是「我是不是改错地方了」。

FluffOS 给的解法（§038）是两个编译期 master apply
（`inherit_program` / `include_file`）让 mudlib 自己建相依图，
**因为 driver 不会替你做这件事**。

### 多重继承与名称冲突

§051 说 `F_*` 是 mixin，而 mixin 一定会撞名。LPC 的解法是**显式限定**：

```c
inherit "/std/weapon";
inherit "/std/armor";

string query_long() {
    return is_equipped() ? armor::query_long() : weapon::query_long();
}
```

`父文件名::函数名()` 直接指定要哪一份。
`inherit_list()` 回报的是**真实文件名**（含扩展名）。

**路径解析规则**：无扩展名的路径优先加载 `pathname.lpc`，
没有才退回 `pathname.c`——**这解释了 §050 那两个家族的扩展名差异**
（家族 A 用 `.lpc`、家族 B 用 `.c`），两者在同一台 driver 上都能跑。

**解决的痛点**：程序／数据分离解的是内存问题，
而且解得非常漂亮——这是 LPMud 能在 1990 年代的机器上跑几千个对象的原因。

**踩过的坑**：代价是**版本一致性从此不是自动的**。
一个对象在任何时刻都是「某个版本的程序 + 某个时刻的数据」的组合，
而这两者**可以独立地过期**：

| 情况 | 程序 | 数据 | 症状 |
|------|------|------|------|
| 改了父档，只重载父档 | **旧** | 旧 | **完全没有变化**（规则 ③） |
| 重载子对象 | 新 | **部分归零** | 玩家的某些属性不见了（规则 ②） |
| 重载一部分子对象 | 新旧**并存** | 各自不同 | **同一种对象行为不一致** |

第三列是最难查的：**世界上同时存在两个版本的同一种剑**，
一个走新逻辑、一个走旧逻辑，而它们的文件名一模一样。

**优点 / 罩门**：优点是热重载可以很快、很细粒度。
罩门是**它把「版本」这个概念从系统里拿掉了**——
LPC 对象没有版本号，你无法问一个对象「你是用哪一版程序编的」
（除非 mudlib 自己记）。

**效益**：对接手 mudlib 的人，这一节提供三条实务规则：

1. 改了被继承的文件，**要重载的是所有继承者，不是它自己**；
2. 重载会让该对象那一份「父档提供的全域变量」归零——**存盘前先想清楚**；
3. 症状是「改了但没反应」时，**先确认你重载的是不是该重载的那个**。

> 💡 君之一席话
> **当程序与数据可以各自独立地过期，「这个对象是什么版本」就变成一个没有答案的问题**——而所有最难查的 bug，都住在没有答案的问题里。

> 🔍 老手视角──真正的门道
> 「重编父程序，子对象继续用旧版」这个行为，在今天的生态里有一个完全对应的东西：**编译期绑定 vs 运行期解析**。C 的静态链接、Java 的 `final static` 常数内联、Rust 的泛型单态化、C++ 的 header-only inline——全部都有「改了上游、下游没重编就没生效」的性质，而且全部都会产生同一种困惑。LPC 特别的地方在于它同时是**热重载系统**，所以这个性质从「重编一次就好」变成「在线随时可能有两个版本并存」。老手处理这类问题的标准手段是**让版本可见**：给程序一个编译时间戳或哈希，并让运行期可以查找——不是为了防止版本分岔（那挡不住），而是为了在分岔发生时**五秒内看得出来**。可落地的做法：任何有热重载／热更新的系统，**第一天就给每个可重载单元一个版本标记，并在日志与调试指令里印出来**。没有它，「为什么这台机器行为不一样」会变成一个要靠猜的问题。

## 061　uid / euid — 从 Unix 借来的安全模型，以及它的两个相反缺省

**标签**：`#安全模型` `#uid` `#euid` `#fail-open` `#fail-closed` `#授权`
**证据等级**：🟡 上游 apply 文档 ＋ 🟢 本项目实测（`adm/single/master.c` 逐行）

**起源**：§032 那条「建角时 `Denied write permission`」是本项目最难查的兼容性问题之一，
因为它的症状出现在一个和权限毫无关系的地方（创建角色）。
根因在这一节。

**技术内核**：LPC 的安全模型直接照抄 Unix 的 **uid / euid**。

| 概念 | 意思 |
|------|------|
| **uid** | 这个对象「是谁造的」——`getuid()`，通常是巫师名或领域名 |
| **euid** | 这个对象「现在以谁的身分行事」——`geteuid()` |
| `seteuid(x)` | 切换有效身分（要经过 master 的 `valid_seteuid()` 同意） |
| `export_uid(ob)` | 把自己的 uid 给另一个对象 |

**没有 euid 的对象几乎什么都不能做**——
这是 LPC 里一个很常见的初始化样板的由来：

```c
void create() {
    seteuid(ROOT_UID);      // 先把身分拿到手
    …
}
```

而 driver 对每一次文件访问都会问 master：

```c
int valid_write(string file, mixed user, string func);
int valid_read (string file, mixed user, string func);
```

三个参数：**哪个档、谁要动、通过哪个函数**。
回传非零就放行。

**★ 本项目的 master 实作，以及那个致命的不对称：**

```c
int valid_write(string file, mixed user, string func)
{
    object ob;
    if (ob = find_object(SECURITY_D))
        return (int)ob->valid_write(file, user, func);
    return 0;                    // ← 找不到 SECURITY_D：拒绝（fail-closed）
}

int valid_read(string file, mixed user, string func)
{
    object ob;
    if (ob = find_object(SECURITY_D))
        return (int)ob->valid_read(file, user, func);
    return 1;                    // ← 找不到 SECURITY_D：放行（fail-open）
}
```

**同一个文件里，两个相反的缺省。**

单看每一个都很合理：
- **写**失败只是不能写，**写错了会坏数据** → 保守 → fail-closed；
- **读**失败会让一堆东西看不到，**读了也不会坏东西** → 宽松 → fail-open。

**问题出在「SECURITY_D 找不到」这个条件何时成立。**

它成立的时机不是「安全模块坏了」，而是——**它还没被加载**。
而 mudlib 的建角流程（`logind` → 创建玩家对象 → 写入存盘）
在某些启动顺序下**正好发生在 SECURITY_D 加载之前**。

```
启动 → preload → …（SECURITY_D 还没到）
   └─ 有人连进来 → 建角 → 写存盘
        → valid_write → find_object(SECURITY_D) 失败 → return 0
        → Denied write permission
```

**这不是安全策略在起作用，是初始化顺序的竞态。**

> **fail-closed 是对的策略，但它假设了「失败 = 异常」。
> 当失败的真正原因是「还没准备好」，同一个策略就从保护变成了故障。**

**解决的痛点**：uid/euid 解的是 LPMud 最原始的问题——
**mudlib 是给不受信任的巫师写的**（§037 讲 eval cost 时的同一个情境）。
一个巫师写的对象不该能删别人的档、不该能改玩家存盘。
把 Unix 那套搬过来是最省事、也最容易被理解的做法。

**14 个 `valid_*` apply 构成完整的授权面**（附录 E.3.2）：

| 分类 | apply |
|------|-------|
| 文件 | `valid_read` `valid_write` `valid_link` `valid_save_binary` |
| 对象 | `valid_object` `valid_shadow` `valid_override` `valid_hide` |
| 身分 | `valid_seteuid` |
| 对外 | `valid_socket` `valid_bind` `valid_database` `valid_ffi` |

**每一个都是「driver 要做一件危险的事之前，先问 mudlib」。**
这个设计把安全策略完全交给了 mudlib——
**driver 不决定什么是安全的，它只保证会问。**

**踩过的坑（本项目）**：除了上面那个顺序问题，还有一个环境层面的：
**WASM 版是无 uid 的运行环境**。
§032 提过有 lib 的「安全模型与无 uid 的运行环境相冲」，
指的就是这件事——一个假设有完整 uid 体系的 mudlib，
在一个没有用户概念的分页里跑，很多检查会落进没有预期到的分支。

**优点 / 罩门**：优点是**策略与机制彻底分离**——
driver 提供 hook，mudlib 写策略，换一套安全观不必动 driver。
罩门有两个：其一，**策略散在 14 个 apply 里**，
没有一处看得到全貌（和 §053 的三分法是同一种病）；
其二，**默认值的选择需要考虑「失败发生在什么阶段」**，
而那是最容易被忽略的维度。

**设计对照：fail-open 与 fail-closed 该怎么选**

| 情境 | 该选 | 理由 |
|------|------|------|
| 授权检查（正常运转中） | **fail-closed** | 检查不了就别做 |
| 唯读查找（正常运转中） | 视情况 | 读失败多半只是体验变差 |
| **启动／初始化阶段** | **两者都不对** | **正解是「还没准备好」要能被表达**——回一个第三种状态，让调用方等待或重试 |

第三列才是本节真正的结论：**布尔值的授权接口没有办法表达「我还不知道」**，
于是设计者只能在「先放行」与「先拒绝」之间二选一，而两个都会在某种情况下错。

**效益**：对接手 mudlib 的人，这一节给一条调试捷径：
**看到权限错误出现在不该有权限问题的地方，先确认安全模块加载了没有。**
在 LPC 里，「权限不足」与「安全模块还没起来」是同一个回传值。

> 💡 君之一席话
> **fail-closed 假设「失败代表异常」——当失败的真正原因是「还没准备好」，最保守的策略就变成了最难查的故障。**

> 🔍 老手视角──真正的门道
> 这一节的通用教训不是「小心 fail-open/closed」，而是**一个布尔回传值不足以表达授权决策**。真实世界的授权至少有四种结果：**允许、拒绝、我不知道（还没准备好／查不到）、我拒绝但这是暂时的**。把它们压成一个 int，就等于强迫调用方把「不知道」当成「拒绝」或「允许」——而这个转换的正确答案取决于调用发生在哪个阶段，**那是被调用方不知道的信息**。现代的授权系统（OPA、IAM、各种 policy engine）都会把 `INDETERMINATE` 或 `NOT_APPLICABLE` 当成一等结果，原因就在这里。老手设计任何决策接口时会问：**「不知道」要怎么表达？**——答不出来的接口，迟早会有人把「不知道」误译成一个决定。可落地的做法：授权与健康检查类的接口，**回传三态而不是布尔**（允许／拒绝／未就绪），调用方就能对「未就绪」做重试或延后，而不是当场失败。

## 062　三个「无中生有」的机制 — virtual object、shadow 与编译管线

**标签**：`#virtual对象` `#shadow` `#编译管线` `#hook` `#save_binary`
**证据等级**：🟡 上游 `docs/apply/master/compile_object.md`、`docs/driver/parse_tree.md`、`call_into_vm.md`

**起源**：§047 那张「MudOS 能力面」的表里，有三项只列了名字没有解释：
**virtual object、shadow、save_binary**。
这一节补上它们——而补的过程会发现，**它们是同一个设计形状的三个实例**。

**技术内核**：

### ① virtual object — 「这个文件不存在」变成一个 hook

当 mudlib 要加载一个**不存在的文件**时，driver 不直接报错，
而是问 master：

```c
object compile_object(string pathname);
```

> The driver calls `compile_object()` in the event that the mudlib instructs
> the driver to load a file that **does not exist**. […] After an association
> is made between an object and a filename, then it will be **as if the file
> did exist** (to the driver).

**回传 0 = 真的不存在；回传一个对象 = 从此那个路径就有东西了。**

这一招在中文 mudlib 里用得极凶——本项目两个家族都有 `virtuald`（§050）。
典型用途：

| 用途 | 做法 |
|------|------|
| 迷宫 | `/d/maze/room_12_35` → 从座标算出房间，不必存一万个档 |
| 副本 | `/fuben/<玩家id>/room1` → 每个玩家一份独立的世界 |
| 进程生成 | 路径就是参数 |

**架构上的意义**：它把「文件系统的查找失败」变成一个可被 mudlib 接管的扩充点。
**路径从一个地址变成了一个函数调用的参数。**

### ② shadow — 在既有对象外面挂一层拦截

`shadow()` 让一个对象挂在另一个对象前面，**拦截对它的函数调用**。
被 shadow 的对象完全不知情。

| 典型用途 | 为什么要用 shadow 而不是改原对象 |
|---------|--------------------------------|
| 状态效果（中毒、失明、变身） | 效果是**暂时**的，结束就把 shadow 拿掉 |
| 临时惩罚／禁言 | 不必污染角色本体的逻辑 |
| 调试拦截 | 不动在线代码 |

**防护**：`nomask` 的函数**不能被 shadow**（§059）。
这是 mudlib 保护金钱、权限、存盘这类关键函数的标准做法。

**罩门很明显**：shadow 是**隐形的**。
一个函数的行为被改掉了，而原代码里完全没有痕迹——
§036 说过的那条调试路径（对象 → `F_*` → simul_efun → efun）
其实还漏了一层，完整版是：

```
shadow（如果有的话，而你看不到它）
  → 对象自己的 .c
    → inherit 的 F_* 清单
      → simul_efun
        → driver 的 efun
```

**LPC 有 `query_shadowing()` 可以问，但你得先想到要问。**

### ③ 编译管线 — 从 `.c` 到字节码

```
LPC 原代码
   │  ① 预处理器（内置，不是 cpp）：#include / #define / #pragma
   ▼
   │  ② 语法分析 → parse tree
   │     节点类型：NODE_IF / NODE_LOOP / NODE_FOREACH / NODE_CALL /
   │              NODE_EFUN / NODE_BINARY_OP / NODE_TERNARY_OP /
   │              NODE_CONTROL_JUMP / NODE_LVALUE_EFUN …
   ▼
   │  ③ 产生字节码（§037 的 F_* 指令）
   ▼
program（可被多个对象共用，§060）
   │
   └─ ④ 选用：save_binary → binaries/ 落地
```

第 ④ 步的证据在本项目的封存里：
`dongfanggushi2` 带着整个 `binaries/` 目录（`.b` 档），
`91shujian` 等家族 B 的 lib 也有 `#pragma save_binary` 的痕迹。
**它解决的是启动时间**——一万个文件的编译不是零成本的。

**★ 运行期的错误处理：LPC 错误 = C++ 例外。**

> LPC VM use C++ Exception to handle **any** error encountered during
> LPC execution.

而 driver 的非 VM 代码（网络层那半）要调用 LPC 时，必须做完整的仪式：

```
push 参数 → 记住 num_arg → save_context(&econ)
  → try { call_function_pointer(…) }
    catch { restore_context(&econ); pop_n_elems(num_arg); }
  → pop_context(&econ)
```

多数地方用包好的 `safe_apply()` / `safe_call_function_pointer()`；
少数不能用的地方（`apply()`、`call_direct()`、`call_program()`）
就必须自己走完上面那套。

**这解释了 §037 那个 `F_CATCH` 为什么要 `setjmp` 加递归求值器**——
LPC 的 `catch()` 与 driver 的错误处理是同一套机制的两端。

**★ 三个机制的共同形状。**

把三者并排，会看到同一个设计反复出现：

| 机制 | 「查不到／做不到」的那一刻 | 变成了什么 |
|------|--------------------------|-----------|
| **virtual object** | 文件不存在 | 一个 master apply（`compile_object`） |
| **shadow** | 函数不该由本体处理 | 一个可插入的拦截层 |
| **错误处理** | 运行失败 | 一个可被 LPC 接住的例外（`catch()`） |
| （§038 的热重载） | 需要相依图 | 两个既有安全 apply 的**参数** |
| （§061 的安全） | 要做危险的事 | 14 个 `valid_*` apply |

**LPMud 家族的内核设计哲学可以浓缩成一句：
「driver 遇到任何需要做决定的时刻，就去问 mudlib。」**

driver 几乎不持有政策——文件存不存在、能不能写、要不要继承、
错误怎么处理、危险操作准不准，**全部外包给上层**。
这就是 §033 那次分家在三十七年后最完整的样子。

**优点 / 罩门**：优点是**极高的可塑性**——
mudlib 可以在不碰 C 的情况下改变几乎任何行为。
罩门是**可诊断性持续下降**：每多一个 hook，
「这个行为是谁造成的」就多一个要查的地方。
本节列的五个 hook 加上 §036 的三个调用方向，
合起来就是为什么读 mudlib 比读一般代码慢。

**效益**：对逆向工作，这一节补完了那条搜索路径的最后一块。
**完整版是六层**：

```
① shadow（先 query_shadowing() 确认有没有）
② 对象自己的 .c
③ inherit 的 F_* 清单（含 `父::函数` 显式调用）
④ simul_efun 有没有盖掉
⑤ driver 的 efun
⑥ 这个路径是不是 virtual object（文件根本不存在）
```

第 ⑥ 层特别容易忘记：**你在文件系统里找不到那个档，
不代表那个对象不存在。**

> 💡 君之一席话
> **「查不到」是一个设计机会**——LPMud 把每一次失败（文件不存在、权限未知、运行出错）都变成一个问上层的 hook，于是引擎三十七年没有政策，也就三十七年不必改。

> 🔍 老手视角──真正的门道
> 「把失败变成 hook」这一招威力很大，但它有一个必须配套的东西，而 LPMud 没有做——**可观测性**。当文件不存在会变成一个 virtual object、当函数调用可能被 shadow 拦走、当权限检查外包给 14 个 apply，系统的实际行为就不再能从原代码推导出来，只能从运行期观察。现代系统面对同样的扩充性（middleware、拦截器、AOP、service mesh）都学到了同一课：**扩充点必须配一个「谁在这里插了东西」的查找接口**。Express 有 middleware stack、Spring 有 AOP proxy 查看、Envoy 有 config dump。LPC 有 `query_shadowing()`、`inherit_list()`、`function_exists()`，但它们是零散的 efun，不是一个统一的「这个调用实际会走哪条路」的视图。老手在设计高度可扩充的系统时会刻意加一个**「解释这次调用」的调试模式**——把实际经过的每一层印出来。它的成本是几天，而它把「为什么会这样」从一个调查变成一次查找。
