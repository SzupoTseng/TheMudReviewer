## 054　客户端简史 — 三十年没变过的四件套

**标签**：`#MUD客户端` `#trigger` `#架构史` `#耦合` `#文本接口`
**证据等级**：🟡 公开的客户端沿革 ＋ 🟢 本项目对协议面的实测

**起源**：§053 最后留下一句话——**客户端只拿得到状态与文本，拿不到规则。**
这一节从客户端这一侧看同一件事：**在只有文本的前提下，客户端能做什么？**

答案三十年没变过，而且所有客户端都收敛到同一个形状。

**技术内核**：MUD 客户端的沿革与它们共同的架构。

| 年代 | 客户端 | 平台 | 带进来的东西 |
|------|--------|------|-------------|
| 1980s 末 | **TinyFugue** | Unix | 宏语言 + 完整的触发系统；早期主要服务 TinyMUD 系 |
| **1992-04** | **TINTIN**（Peter Unold） | Unix | 易学的脚本语言；为 DikuMUD 而生 |
| 1992-10 | TINTIN III | Unix | 该线的最后一版 |
| **1993-07** | **TinTin++ 1.0**（Bill Reiss） | Unix | 开源、无授权限制——**后来 GGMud／MudMaster／Pueblo 都以它为基础** |
| **1995-12** | **zMUD 1.0**（Mike Potter） | Windows | 把 TinTin++ 的能力搬上图形接口：可自订按钮、地图；1996-09 起转共享软件 |
| — | MUSHclient | Windows | 开源；alias／macro／trigger／脚本／记录，**内置 MXP 与 MCCP** |
| — | Mudlet | 跨平台 | 开源；强脚本引擎与高速显示 |

**三十年、六代、两种操作系统，架构是同一个：**

```
      服务器文本流
           │
           ▼
   ┌───────────────┐
   │  trigger 引擎  │ ← 对每一行做模式比对
   └───────┬───────┘
           │ 命中
           ▼
   ┌───────────────┐   ┌──────────┐   ┌──────────┐
   │  alias 展开    │   │  macro   │   │  script  │
   │（输入端缩写）   │   │（按键）   │   │（脚本引擎）│
   └───────┬───────┘   └────┬─────┘   └────┬─────┘
           └────────────────┴──────────────┘
                            ▼
                      送回服务器 / 改变显示
```

**四件套：trigger（输出端模式比对）、alias（输入端展开）、
macro（按键绑定）、script（把前三者串起来的编程语言）。**

**为什么是这四件套？**因为在「服务器只吐文本」这个前提下，
客户端能施力的地方只有两个：**进来的文本**与**出去的文本**。
trigger 处理前者、alias／macro 处理后者、script 让两者可以有状态。
**这不是设计选择，是前提的必然结果。**

**解决的痛点**：这四件套解的是一个很真实的痛——
**MUD 的操作密度远高于人的打字速度**。
战斗每回合要下指令、补血要盯数字、走路要记路径。
trigger 让「看到血低于三成就喝药」变成一条规则，而不是一次反应。

**★ 但它有一个结构性的罩门，而且这个罩门定义了后面三十年的协议史：**

> **trigger 耦合的是「输出的排版」，不是「游戏的状态」。**

```
服务器送：  你的气血：[####------] 137/450
规则写成：  比对 /气血：.*(\d+)\/(\d+)/ → 取第一个数字
                      ↑
        服务器某天把方括号改成圆括号、或在数字间加一个空格
                      ↓
              整套规则静默失效
```

玩家的脚本绑在**服务器的排版**上，而排版是服务器最常改的东西。
更糟的是失效方式：**规则不会报错，只是不再命中**——
又一次静默失败，而这次连 log 都没有。

**这就是本书第二篇那套协议存在的全部理由。**
ZJMUD 在文本流上叠 opcode，做的事本质上是：

> **把「客户端从排版里猜状态」换成「服务器直接说出状态」。**

换句话说，第二篇解剖的那 116 个 opcode，
是对 §054 这个罩门的一次回答——而它不是唯一的回答，
也不是第一个（§056 会看到另外三代）。

**设计对照：同一个问题的两种解**

| | **客户端猜**（trigger） | **服务器说**（结构化协议） |
|---|---------------------|------------------------|
| 知识在哪 | 玩家的脚本里 | 服务器与客户端之间 |
| 谁维护 | **每一个玩家各自维护** | 服务器作者 |
| 服务器改排版 | **全体玩家的脚本一起坏** | 没有影响 |
| 换一台 mud | 脚本全部重写 | 只要对方讲同一套协议 |
| 上手成本 | 高（要学脚本语言） | 零（客户端内置） |
| 服务器要做什么 | **什么都不用做** | 要多送数据 |

最后一列是 trigger 三十年不死的原因：**它不需要服务器配合**。
任何一台 MUD、任何一个年代，trigger 都能用。
而结构化协议永远需要两边都同意——这件事有多难，§056 会看到。

**优点 / 罩门**：四件套的优点是**普适**——
它对所有 MUD 都有效，包括那些作者早已消失的。
本项目 §045 那个「会话层代打」（`telnetlogin.js`）本质上就是一组 trigger，
而它之所以是这个形状，正是因为对面的 193 份 mudlib 不可能配合修改。
罩门就是上面那条：**耦合在排版上，且失效是静默的。**

**效益**：对写客户端的人，这一节给的是一个定位问题：
**你要做的是第几种客户端？**
做 trigger 型的，要投资脚本引擎与规则管理；
做协议型的，要投资方言解析与兼容性。
本项目是后者，而它的代价与收获在 §057 结算。

> 💡 君之一席话
> **当客户端只能从排版里猜状态，服务器的每一次美化都是一次破坏性变更**——三十年的 MUD 协议史，本质上是在把这句话里的「猜」字拿掉。

> 🔍 老手视角──真正的门道
> trigger 这个架构有一个很值得学的地方：**它把扩充点开在「数据流」上，而不是开在「程序」上。** 客户端不需要插件 API、不需要重编译、不需要作者同意，任何人都能在文本流上挂规则——这是它能适配所有 MUD 的原因，也是它三十年不死的原因。同样的形状在别的地方也很常见：Unix 的管道、浏览器的 userscript、log 分析、封包过滤器。它们共同的优点是**零协调成本**，共同的缺点也一样：**上游一改格式，下游全体静默失效**。老手在依赖这类扩充点时会做一件事——**替自己的规则加一个「应该要命中」的健康检查**：如果一条本来每分钟都会命中的规则，五分钟没命中，那不是安静，那是坏了。可落地的做法：任何基于模式比对的自动化（log 告警、爬虫、trigger、监控规则），都要有一条「规则本身还活着吗」的反向监控——**没有这一条，你的规则会在某个你不知道的时刻停止工作，而系统看起来一切正常。**

## 055　telnet 选项层 — 协商的架构，与 6 组实测字节

**标签**：`#telnet` `#选项协商` `#能力协商` `#IAC` `#实测`
**证据等级**：🟢 实机封包（本项目）＋ 🟡 上游 `src/net/telnet.cc` 的协商立场表

**起源**：本书 §006 记过一次惊险——连接第一毫秒收到的那串字节，
差点让一个严格 UTF-8 解码器当场死掉。
当时的处理是**全部剥除、一律拒绝**，这个策略至今没变。

这一节补上它的**架构**：那些字节到底在谈什么，以及为什么「一律拒绝」是安全的。

**技术内核**：telnet 选项协商是一个**对称的能力协商框架**。

```
IAC WILL <opt>    我想要激活 <opt>（我这边做）
IAC WONT <opt>    我不做 <opt>
IAC DO   <opt>    请你激活 <opt>（你那边做）
IAC DONT <opt>    请你不要做 <opt>
IAC SB <opt> …数据… IAC SE    子协商：<opt> 激活后的实际数据信道
```

四个内核性质：

| 性质 | 说明 |
|------|------|
| **对称** | 两边都能发起，两边都能拒绝 |
| **双向独立** | 「我做」与「你做」是两件事——`WILL` 与 `DO` 各谈各的 |
| **缺省关闭** | 没谈成的选项就是不激活 |
| **拒绝是合法且无副作用的** | 回 `DONT`／`WONT` 是协议的正常路径，不是错误 |

**第四条就是「一律拒绝」为什么安全的全部理由。**
拒绝所有选项＝退回最基本的 NVT telnet，
而 MUD 的内核功能（送文本、收文本）**完全不依赖任何选项**。
本项目因此可以用不到一百行处理掉整个协商层。

**FluffOS 这一侧的协商立场**（`src/net/telnet.cc` 的 `my_telopts`）——
driver 对每个选项预先声明自己的态度：

| 选项 | 编号 | 用途 | driver 立场 |
|------|------|------|------------|
| BINARY | 0 | 8-bit 透传 | WILL / DO |
| ECHO | 1 | **回显控制（密码屏蔽靠它）** | WILL / DO |
| SGA | 3 | Suppress Go Ahead——**字符模式的信号** | WILL / DO |
| TM | 6 | Timing Mark | WILL / DO |
| **TTYPE** | **24** | 终端机类型（`xterm-256color`） | WONT / **DO** |
| **NAWS** | **31** | **窗口大小**，改变时重报 | WILL / DO |
| LINEMODE | 34 | 行模式 | WONT / DO |
| **NEW-ENVIRON** | **39** | 环境变量 | WONT / **DO** |
| **CHARSET** | **42** | 字集协商 | WILL / DO |
| MSDP | 69 | 频外结构化数据（§056） | WILL / DO |
| **MSSP** | **70** | MUD 服务器状态（给爬虫用） | WILL / DO |
| **COMPRESS2** | **86** | **MCCP2 压缩** | WILL / DO |
| **MSP** | **90** | 音效（§056） | WILL / DO |
| MXP | 91 | 行内标记（§056） | WILL / DO |
| ZMP | 93 | Zenith MUD Protocol（§056） | WILL / DO |
| GMCP | 201 | 频外 JSON（§056） | WILL / DO |

注意 TTYPE / NEW-ENVIRON 那两列是 **`WONT` / `DO`**——
**driver 不提供，但要求客户端提供**。这是信息流方向的声明：
终端机类型与环境是客户端的知识，服务器只负责问。

**★ 本项目实测：WASM driver 的首包，逐组解码。**

```
ff fd 18   IAC DO   24    → 请客户端报终端机类型（TTYPE）
ff fd 1f   IAC DO   31    → 请客户端报窗口大小（NAWS）
ff fd 27   IAC DO   39    → 请客户端报环境变量（NEW-ENVIRON）
ff fb 46   IAC WILL 70    → 我可以提供服务器状态（MSSP）
ff fb 2a   IAC WILL 42    → 我可以谈字集（CHARSET）
ff fb 5a   IAC WILL 90    → 我可以送音效（MSP）
```

**六组，18 个字节**，之后才是 `ver1.0:…` 那一行（§044）。

而本书 §006 记录的**原生版**首包多了一组：

```
ff fb 56   IAC WILL 86    → 我可以做 MCCP2 压缩
```

**这一组在 WASM 版消失了**——因为 zlib 被移除、compress 套件关闭（§041）。
**§041 那张套件矩阵，在线路的第 10 个字节上就看得见。**

这是一个很干净的闭环：从 driver 的 CMake 选项，
到 C++ 的协商表，到线路上的三个字节，到客户端要不要处理压缩——
**同一个决定，四层都看得到。**

**★ 还有第二个闭环：`config` 的默认值也在这 18 个字节里。**

FluffOS 的设置档有一组协议开关，各有默认值：

| 设置 | 缺省 | 选项 | **实测首包里有吗** |
|------|-----:|-----:|------------------|
| `enable mssp` | **1** | 70 | ✅ `ff fb 46` |
| `enable msp` | **1** | 90 | ✅ `ff fb 5a` |
| `enable mxp` | 0 | 91 | ❌ |
| `enable gmcp` | 0 | 201 | ❌ |
| `enable zmp` | 0 | 93 | ❌ |
| `enable msdp` | 0 | 69 | ❌ |

**两个缺省为 1 的都出现了，四个缺省为 0 的一个都没有。**

这条对照有一个很实际的用途：**看首包就能反推对方的设置**。
本项目没有读过那 17 份 lib 的协议开关设置，
但从协商字节就能断定它们全部没有开 GMCP／MXP——
**这也再一次印证 §056 的结论：中文 MUD 生态停在第 0 代，
不是因为 driver 不支持，是因为没有人去打开它。**
FluffOS 早就准备好了，开关就在那里，缺省是关的。

**解决的痛点**：telnet 选项层解的是一个 1983 年就存在、
而且至今每个协议都要面对的问题：
**如何在一条已经在用的连接上，让两边逐步协商出共同的能力？**

它的答案有三个很现代的性质：
**逐项协商**（不是全有全无）、**可拒绝**（拒绝是正常路径）、
**可延后**（连接中途才激活某个选项也合法）。

把它和本篇前面两节对照：

| 层级 | 能力声明的方式 | 何时 | 可否拒绝 |
|------|--------------|------|---------|
| **driver 套件**（§048） | 编译期 `#define` | 编译 driver 时 | — |
| **mudlib intermud**（§049） | `support_*()` 回传 1/0 | 运行期，被问时 | — |
| **telnet 选项**（本节） | `WILL`／`DO` 协商 | **连接期，双向** | ✅ |

**三层在解同一个问题，而只有最上面这一层做对了。**
telnet 这套在 1983 年定下的框架，
比它上面两层晚了十年才被 MUD 世界用起来，
却是三者里唯一能处理「两边能力不对等」的。

**踩过的坑**：本项目在这一层踩过的坑在 §006——
**不是协商逻辑错，是根本没想到有这一层**。
一个用严格 UTF-8 解码的读取器，
碰到 `0xFF` 开头的字节串行会直接抛例外，
而那是连接的第一毫秒。

教训是**分层要从最外层开始验证**：
本项目的验收顺序后来固定成「字节 → 分帧 → opcode → 样式 → 状态 → DOM」（§046），
而 IAC 剥除是第一站。

**优点 / 罩门**：优点是**极高的向下兼容**——
四十多年来加了几十个选项，而一个 1983 年写的 telnet 客户端今天还连得上，
因为所有新东西都在「谈不成就不激活」的框架里。
罩门是**它把复杂度推给了每一个实作者**：
任何客户端都必须先写一个状态机来剥 IAC，才能看到第一个字。
这对本项目是 138 行 JavaScript 加 162 行 Rust（§附录 B）——
**在能看到任何有意义的内容之前，先要付的入场费。**

**效益**：对本项目的具体效益是**两份实作的等价性可以被钉死**。
那 42 个实机字节同时当成 Rust 测试与 JS 测试的输入（§028.6），
于是「桌面版与浏览器版对协商的处理是否一致」这件事，
变成一条会失败的测试，而不是一个假设。

> 💡 君之一席话
> **一个能力协商框架的价值，不在它能谈成什么，而在它谈不成的时候会不会坏**——telnet 选项四十年不倒，靠的正是「拒绝」是一条正常路径。

> 🔍 老手视角──真正的门道
> telnet 选项协商有一个常被忽略的设计细节：**`WILL/WONT` 与 `DO/DONT` 是两组独立的协商，而不是一问一答。** 这看起来只是形式上的对称，实际上是它能撑四十年的关键——因为它承认了「我能做的」与「我想要你做的」是两件不同的事。多数自制的握手协议会把这两件事压成一次「能力交换」（我把我支持的清单给你，你把你的给我，取交集），那在双方角色对称时没问题，但一旦出现「我不提供但我需要你提供」这种不对称需求（本例的 TTYPE、NAWS），交集模型就表达不出来。老手设计能力协商时会先问：**这个能力是对称的吗？**——对称的用交集，不对称的就必须把方向写进协议里。可落地的做法：任何 capability negotiation，**把「提供」与「需求」分成两个字段**，即使一开始所有能力都是对称的；等你发现需要方向的那天，协议已经没办法改了。

## 056　频外数据的四代 — 语意的定义权一路往上搬

**标签**：`#GMCP` `#MSDP` `#MXP` `#ATCP` `#频外数据` `#协议演化`
**证据等级**：🟡 上游协商表与公开规格 ＋ 🟢 本项目对 ZJMUD 的实测定位

**起源**：§054 的罩门是「客户端只能从排版猜状态」。
过去三十年，MUD 世界对这个问题给过**四代**答案。
这一节把它们排成一列——不是为了列规格，
是因为**它们的演化方向非常一致，而 ZJMUD 刚好落在起点**。

**技术内核**：四代的架构差异。

| 代 | 代表 | 载体 | 数据格式 | 语意由谁定义 | 纯 telnet 看得到吗 |
|---|------|------|---------|------------|------------------|
| **第 0 代** | **ANSI 色码、mudlib 行内标记、ZJMUD** | **就在文本流里** | 自订字符串标记 | **每个 mudlib 自己** | ✅ 看得到（有点乱） |
| **第 1 代** | **MXP**(91)、**MSP**(90) | 文本流内，但先用选项谈过 | 类 HTML 标签 / 命令行式 | 协议规格 | ⚠️ 看得到标签 |
| **第 2 代** | **ATCP**(200)、**ZMP**(93) | **telnet 子协商** | 自订字符串 / 命令＋参数 | 半规格半自订 | ❌ 看不到 |
| **第 3 代** | **GMCP**(201)、**MSDP**(69) | telnet 子协商 | **JSON** / 类型化 KV | 有社群共识的命名空间 | ❌ 看不到 |

**四代的方向只有一个，但它很值得说清楚：**

```
第 0 代   语意住在 mudlib 里         → 每台 mud 一套，撞号（§043）
第 1 代   语意住在协议规格里          → 但数据还混在文本流中
第 2 代   数据搬出文本流（子协商）     → 语意仍各家自订
第 3 代   数据搬出文本流 + 语意标准化  → 客户端可以「通用地」理解
```

**两件事被逐步分开：数据的信道，与数据的语意。**
第 0 代两者都在 mudlib 手上；第 3 代两者都被擡到了协议层。

各代的架构特征（high level）：

- **第 0 代**是**行内标记**。优点是零基础设施——
  服务器多印几个字符就好，driver 完全不必知情（§043）。
  代价是三件：撞号、没有跳脱机制（§004）、不认识的客户端会看到乱码。
- **第 1 代**开始用 telnet 选项**谈过再用**，
  所以不认识的客户端不会被打扰。MXP 走「类 HTML 标签」的路
  ——可点击的链接、可展开的区块；MSP 专门处理音效触发。
  它们仍然把数据放在文本流里，所以**排版与数据还是绑在一起**。
- **第 2 代**是分水岭：**数据离开文本流，走子协商信道**。
  从此「给人看的」与「给程序看的」在物理上分开，
  排版怎么改都不会影响数据。
- **第 3 代**把最后一块补上：**格式标准化**（GMCP 用 JSON），
  并形成命名空间惯例，让客户端可以对「没见过的 mud」也做出合理的缺省行为。

**★ ZJMUD 落在第 0 代——而且它是第 0 代里做得很彻底的一个。**

用本篇的框架重新定位本书第二篇：

| 面向 | ZJMUD 的做法 | 属于哪一代的性质 |
|------|-------------|----------------|
| 载体 | 行首 `ESC` + 三码，就在文本流里 | 第 0 代 |
| 数据格式 | `$zj#` 分记录、`:` 分字段、`║` 分属性 | 第 0 代（自订字符串标记） |
| 语意定义 | `include/zjmud.h`，**每个 mudlib 自己一份** | 第 0 代 |
| 数据完整性 | **状态明确送出**（房间、出口、属性、血条各有专属码） | **接近第 3 代的野心** |
| 向下兼容 | 旧 telnet 客户端看得到，只是难看 | 第 0 代（刻意保留，§004） |

**它用第 0 代的机制，做了第 3 代想做的事。**
这既是它的成就，也是它所有问题的来源——
116 个 opcode、三个世代方言、4 个撞号（第三篇），
全部是「语意的定义权留在 mudlib 手上」的直接后果。

**那为什么中文 MUD 没有走向 GMCP？** 三个原因，都不是技术上的：

1. **时间轴不对**。中文 MUD 的高峰在 1996–2005 年；
   ATCP／GMCP 这一系成形要晚得多。
   **当一个生态的内核期已经过去，新标准就进不去了**——
   不是不能，是没有人有动机再改一份跑了十年的 mudlib。
2. **需要 driver 配合**。第 2、3 代都走 telnet 子协商，
   而子协商是 driver 的地盘（§036 那张 apply 表：
   `gmcp`／`msdp`／`mxp_tag`／`zmp` 都是 driver 提供的 apply）。
   第 0 代不需要任何人配合——**这正是 §043 说的「组织成本」**。
3. **没有中央权威**（§043）。要形成共通语意，得有人来定命名；
   而中文 MUD 圈从来没有这样一个角色，
   于是每一份 mudlib 各自加码，撞号成为必然。

**这三条加起来就是一个很普遍的现象：技术上更好的方案输给了组织成本更低的方案。**

**解决的痛点**：这一节解的不是实作问题，是**定位问题**。
本书前七篇解剖 ZJMUD 时，一直缺一个座标系——
「这套协议算好还是不好」没有基准可比。
放进四代的框架之后，评价可以精确得多：

> ZJMUD 在「数据完整性」上做得比多数第 0 代方案好得多
> （它真的把状态明讲了，而不是只做颜色与换行）；
> 在「语意的定义权」上则完全停在第 0 代，
> 而那正是它撞号与难以互通的原因。

**踩过的坑**：本项目一开始把「支持哪些 opcode」当成客户端的内核指针，
后来发现这个指针会误导——**因为 opcode 数量反映的是方言的分裂程度，
不是协议的能力**。
三个世代方言合计 116 个码，其中 89 个是扩充码、4 个撞号（§010）；
而真正撑起完整接口的是那 **27 个内核码**（§005）——
**最大公因数才是能力，总数只是熵。**

**优点 / 罩门**：第 0 代的优点在 §043 说过了：**一个人就能完成**。
罩门是它把成本从「开发时」推迟到「互通时」——
本项目要同时支持三个方言、隔离 4 个撞号、
再为不讲 ZJMUD 的 193 份 mudlib 做会话层代打（§045），
**全部都是那笔延迟付款的利息。**

**效益**：对要设计自订协议的人，这四代提供的是一张**演化路线图**：
你现在在第几代、下一代要付什么代价、哪一步需要别人配合。
知道这件事，至少可以在第 0 代就把编号分区留好——
**撞号是可以预防的，只要你知道自己终究会走到那一步。**

> 💡 君之一席话
> **协议的演化方向，是把「语意的定义权」一路往上搬**——从每个实作各说各话，到规格说了算；每往上一阶，互通性上升一级，而所需的协调成本也上升一级。

> 🔍 老手视角──真正的门道
> 第 2 代那个「数据离开文本流」的转折，是这四代里唯一真正的架构突破，值得单独记住：**它把「给人看的」与「给程序看的」在物理上分开了。** 在此之前，排版就是数据，改排版就是改 API；在此之后，两者可以各自演化。这个转折在别的领域反复出现——网页从 table 排版走到语意标签再走到前后端分离的 API、CLI 工具加上 `--json` 输出、log 从人类可读走到结构化 log。它们的共同教训是：**只要人类可读的输出同时是机器读取的接口，你的排版就是公开 API，而且是一个没有版本、没有弃用期、改了就有人坏掉的公开 API。** 老手看到任何「我们的输出格式下游有人在剖析」的情况，第一个动作是给下游一条专用信道（`--json`、结构化事件、频外信道），哪怕一开始只有一个用户。可落地的判准：**当你开始因为「怕下游剖析坏掉」而不敢改排版时，你已经欠了一笔技术债了**——那一刻就是该开专用信道的时候。

## 057　知识该放在哪一层 — 三种客户端架构与它们的寿命

**标签**：`#架构决策` `#耦合` `#寿命` `#取舍` `#收束`
**证据等级**：🟢 本项目实测（三种架构本项目各实作过一部分）

**起源**：§054 是「客户端猜」，§056 是「服务器说」。
但这两者之间其实有三种可落地的架构，而本项目**三种都碰过**。
这一节把它们并排结算——也是本书最后一个架构问题。

**技术内核**：**协议知识住在哪一层？**

```
架构 A：知识在「用户的脚本」里
        服务器 ──文本──▶ 客户端 ──▶ 玩家写的 trigger 规则 ──▶ 行为
        代表：TinTin++／zMUD／MUSHclient／Mudlet 的一般用法
        本项目的实例：telnetlogin.js 的 profile 表（§045）

架构 B：知识在「客户端的代码」里
        服务器 ──ESC+opcode──▶ 客户端内置的方言解析器 ──▶ UI
        代表：ZJMUD 客户端（本书第二～六篇）

架构 C：知识在「协议规格」里
        服务器 ──GMCP/MSDP──▶ 任何懂该规格的客户端 ──▶ UI
        代表：GMCP／MSDP 生态（§056 第 3 代）
```

**六个面向的并排比较：**

| | **A：用户脚本** | **B：内置方言解析** | **C：标准频外协议** |
|---|---------------|-----------------|------------------|
| 谁维护那份知识 | **每个玩家各自** | 客户端作者 | 规格 + 两边实作者 |
| 服务器要配合吗 | **不用** | 要（得送 opcode） | 要（driver + mudlib 都要） |
| 服务器改排版 | **全体脚本坏** | 没影响 | 没影响 |
| 服务器改协议 | 没影响（本来就在猜） | **客户端要跟着改** | 规格挡着，不常改 |
| 换一台 mud | 脚本重写 | **要嘛同方言，要嘛做兼容层** | ✅ 直接可用 |
| 新玩家上手 | 高（要学脚本） | **零** | 零 |
| 能做到多深的 GUI | 浅（猜得到的才做得到） | **深**（服务器明讲） | 深 |

**本项目为什么选 B？** 因为前提决定了：
目标是重写**一个特定 mud 的客户端**，而那个 mud 已经在用一套私有方言。
选 A 等于放弃它已经送出来的结构化数据；
选 C 等于要求一份原作者已经不在的 mudlib 改用 GMCP。
**B 是唯一与现实兼容的选项。**

**★ 但 B 的代价，这本书从头到尾都在付：**

| B 的代价 | 本书的哪一部分 |
|---------|--------------|
| 协议知识没有规格书，得自己还原 | 第一、二篇（整个逆向工程） |
| 一个方言不够，要支持三个 | 第三篇（三个世代、4 个撞号） |
| 知识进了代码，就必须有边界 | 第四篇（纯函数、`protocol.js` 不碰 DOM） |
| 没有规格挡着，只能靠测试钉住 | 第五篇（177 条测试、53 行实机封包固化成回归测试） |
| 换一台不同方言的 mud 就不通 | §045（会话层代打，且只做得到第一层） |

**换句话说：这整本书，就是架构 B 的帐单。**

而本项目最后**同时用了 A 和 B**——
对讲 ZJMUD 的 mud 用 B（完整 GUI），
对不讲的用 A（`telnetlogin.js` 的 profile 表，只做到纯文本可玩）。
§045 那句「兼容层最重要的不是它做到了什么，是它明确地不做什么」，
现在可以说得更精确：**A 与 B 的能力天花板不同，所以它们该交付的东西也不同。**

**踩过的坑**：本项目一度想把 A 往上推——
用规则从文本里剖出房间名与出口，让不讲 ZJMUD 的 mud 也有面板（§045 的路线 A）。
最后没做，判断是：**那等于在 193 份排版各异的 mudlib 上重建 §054 那个罩门**，
而且是替用户重建的——他们不会知道规则什么时候失效。

**这个判断的通则是：不要用架构 A 去仿真架构 B 的能力。**
A 的天花板由「猜得准不准」决定，而猜的准确率会随着对端数量增加而崩溃。

**优点 / 罩门**：三种架构没有优劣，只有**适用前提**：

- **A 适用于：对端不可能配合**（老 mud、别人的服务器、第三方服务）；
- **B 适用于：对端已经在送结构化数据，但那套数据是私有的**；
- **C 适用于：你能同时影响两端，或生态已经有标准**。

罩门也各自对应：A 的知识分散在用户手上、B 的知识锁在你的代码里、
C 需要一个你可能没有的社群共识。

**效益**：这一节其实是本书第四篇「架构」那条线的终点。
第四篇问的是「怎么让协议知识不污染 UI」——那是**同一层之内**的边界问题；
这一节问的是「协议知识该不该在我这一层」——那是**跨层**的归属问题。

两个问题的答案指向同一个习惯：

> **先问这份知识属于谁，再问它该放在哪个文件。**

而本书开头那句内核命题，到这里有了它最后一层意思：

> 逆向工程的尽头，不是「我看懂了」，而是「我能证明它，而且我的实作经得起真机打脸」。

**当协议知识住在你的代码里（架构 B），「真机打脸」就是你唯一的规格书。**
没有标准可以援引、没有第三方实作可以对照、没有规格委员会可以申诉——
只有那 53 行实机封包，和它们固化成的回归测试。

**这就是为什么这本书从第一页就在讲证据等级。**

> 💡 君之一席话
> **选架构，本质上是在选「将来坏掉的时候，谁要负责修」**——A 是用户、B 是你、C 是规格；三个都不是免费的，但只有把它想清楚的人，才不会在坏掉的那天感到意外。

> 🔍 老手视角──真正的门道
> 这三种架构有一个共同的隐藏维度：**知识的更新速度必须配得上它所在那一层的发版速度。** 架构 A 把知识放在用户手上，用户可以在五分钟内改一条规则——所以它能适配变动最快的对端；架构 B 把知识放在客户端代码里，更新要走发版流程——所以它只适合对端相对稳定的情况；架构 C 把知识放在规格里，改一次要动整个生态——所以它只适合几乎不变的东西。多数架构失误不是选错了层，是**把变动快的知识放进了发版慢的层**：把业务规则编进客户端、把费率写进行动 App、把对端的怪癖硬编进要跑五年的固件里。老手在放置任何一块知识时会问两个问题：**这东西多久会变一次？我修好它要多久才能送到用户手上？**第二个数字大于第一个，就放错层了。可落地的做法：把系统里的知识按「变动周期」列一张表，对照每一层的「发版周期」——**两张表对不上的地方，就是未来的紧急发版**。
