## 050　17 个 mud，其实是 2 份 mudlib — 用文件名集合量血缘

**标签**：`#血缘鉴定` `#可重复量测` `#Jaccard` `#封存` `#方法论`
**证据等级**：🟢 本项目实测（17 份映像的文件索引，可重跑）

**起源**：本项目收了 17 个中文 mud。表面上它们是 17 款不同的游戏——
不同的名字、不同的世界、不同的武功。
但把它们一个一个修到能开机的过程中，出现了一个很难忽视的现象：
**同一个修正，往往一次修好好几个。**

那不是巧合。**它们大多是同一份 mudlib 的分身。**

问题是：怎么证明？口述历史（「听说某某是从某某改的」）在本书里不算证据。
所以本项目用了一个**可重复、可量测**的方法。

**技术内核**：**把每份 mudlib 化约成一个文件路径集合，量它们的交集。**

每份 mudlib 在本项目里都是一份映像 + 一张索引（`mudlib.json`），
索引里就有完整的路径清单——不必解开、不必读任何一行 LPC。
两份 mudlib 的相似度用 Jaccard 系数：

```
J(A, B) = |A ∩ B| / |A ∪ B|
```

结果非常干净：

| 相似度区间 | 对数 | 解读 |
|-----------|------|------|
| 0.70 – 0.90 | 20 对 | **近亲**——彼此是直接的分支 |
| 0.44 – 0.69 | 30 余对 | **同族**——共同祖先较远 |
| **0.012** | dongfanggushi2 对**所有**其他 lib | **完全不同的血脉** |

最高的一对是 `shuiyuzhengfeng ↔ zhijianxing`，**0.90**——
**九成的文件路径一模一样**。

而 `dongfanggushi2`（东方故事Ⅱ）对其他 16 份的最高相似度只有 **0.012**。
不是低，是**几乎没有交集**。

**于是 17 份 mudlib 分成两族，而且从目录形状就看得出来：**

| | 家族 A（1 份：dongfanggushi2） | 家族 B（16 份） |
|---|---|---|
| 扩展名 | **`.lpc`** | **`.c`** |
| 对象基底 | `std/` | **`inherit/`** |
| 守护进程 | `daemon/` | `adm/daemons/` |
| 武功系统 | 无独立目录 | **`kungfu/`**（141 – 3,469 档） |
| 特征模块 | 无 | **`feature/`**（43 个 `F_*`） |
| 设置档 | `config.ES2` | `config.ini` / `config.xajh` / … |
| 其他痕迹 | `binaries/`（`save_binary`）、`adm/tmp/swapfile.*`（swapping） | `clone/`、`grant/`、`fuben/`（副本） |

家族 A 是经典的 LPMud／TMI 风格布局；
家族 B 是**中文武侠 mudlib 的标准骨架**——
`inherit/` + `kungfu/` + `feature/` 这三件套，是它的指纹。

**★ 但两族共享 ~170 个档。**

去掉扩展名之后比对，`dongfanggushi2` 与家族 B 各成员之间，
**有 142 – 182 个同名文件**，而且全部集中在同一批位置：

```
adm/daemons/           aliasd channeld chard chinesed combatd emoted
                       fingerd itemd logind natured securityd virtuald …
adm/daemons/network/   dns_master + services/ 那整组 _q/_a（§049）
adm/simul_efun/        atoi chinese file gender message object path wizard
adm/etc/               config motd preload welcome wizlist
```

**这就是 §049 那批 TMI-2 的文件。**
两个看起来毫无关系的中文 mudlib 家族，
共享的正是 1993 年那份 MudOS 参考 mudlib 的**守护进程层与仿真函数层**。

所以完整的血缘图是：

```
TMI-2 mudlib（1993, MudOS 参考实作）
   │
   ├──→ 家族 A：东方故事系（保留 std/ + daemon/ 布局，改写游戏层）
   │
   └──→ 家族 B：中文武侠系（保留 daemon 层，**整个对象层重写**
                            成 inherit/ + feature/ + kungfu/）
                 └─→ 16 份分身，彼此 0.44 – 0.90
```

**解决的痛点**：这个量测回答了三个原本只能靠猜的问题：

1. **「修一个能修几个？」**——0.9 的近亲，修正几乎必然通用。
   §032 那八条「通用修正」之所以通用，就是因为它们打在共享的骨架上。
2. **「这份封存缺了什么？」**——把它和近亲的文件集合相减。
   `nt7` 缺整个玩家层与世界（`clone/user/` 空、没有 `d/`），
   就是这样看出来的；补件也是拿 0.78 的近亲 `nitan7` 来对（§032）。
3. **「这是一款新游戏还是一次换皮？」**——0.90 的两份，
   差的是内容不是架构。

**踩过的坑**：这个方法有一个明显的失效模式，必须说清楚——
**它量的是「文件路径」，不是「代码」。**

一份 mudlib 可以：路径全同但内容全改（换皮的反面），
或路径全改但内容照抄（重命名）。
本方法对前者会高估、对后者会低估。

本项目接受这个误差，理由是**成本**：路径比对读一张 JSON 就好，
内容比对要解开 17 × 一万个档。
而且对「这批东西是不是同源」这个问题，路径的鉴别力已经足够——
**0.90 与 0.012 之间没有模糊地带**。

真要提高精度，下一步是对共享路径的文件做内容哈希比对；
本项目没做，因为现有结论没有一条会因此改变。
**知道自己的量测误差在哪、且判断它不影响结论，比追求精度重要。**

**★ 后记：量测做完之后，才去查史料。**

本节的分析全部做完、结论全部写下之后，本项目才回头去查中文 MUD 的公开记载。
**三条独立的线对上了：**

| 史料说 | 本节量到 | 文件里写着 |
|--------|---------|-----------|
| 1993 年底《东方故事》采用 **MudOS ＋ TMI Mudlib**，并改造 MudOS 使其能处理中文；**舍弃 TMI 的游戏内容自行创作** | 15/17 份共用 ~170 个档，**全部集中在 daemon／network／simul_efun** —— 正是「保留框架、换掉内容」的形状 | `Creator : Grendel@Tmi-2` `93-08-15` |
| 1995 年底《侠客行》**在《东方故事2》基础上**开发 | `dongfanggushi2` 自成一族（对其他 16 份仅 **0.012**） | `config.ES2`；名录里有 `es2.muds.net 4000` |
| **1996-05 侠客行代码外流**，据此诞生大量改编版本 | 家族 B 那 **16 份彼此 0.44–0.90** —— 同一份 code 的分身 | `Creator : ken@XAJH`（侠客行对网络层的扩充）、`config.xajh`、`d/…/xkxnpc/` |

**完整血缘图与这三条线的对照，收在附录 D.3。**

这件事对方法论的意义比对历史的意义更大：**量测是在不知道答案的情况下做的**，
所以它不可能是「照着史料找证据」。当一个独立量测与一份独立史料收敛到同一张图时，
**两者互为验证**——这正是本书第一篇那条规矩要求的形状。

**优点 / 罩门**：优点是**便宜、可重跑、不需要领域知识**——
不必懂 LPC、不必懂武侠，一支三十行的脚本就能把 17 份封存的关系画出来。
罩门是它只能告诉你**结构**上的亲疏，说不出**谁先谁后**。
方向是靠别的证据补的：TMI-2 档头的日期（`93-08-15`）、
家族 A 保留而家族 B 改写的部分（**改写的一方通常是后来者**），
以及上面那份史料。

**效益**：对接手一批来历不明的封存，这个方法提供的是**第一天的地图**：
哪些是同源、哪些是孤儿、修正该打在哪、缺件该去哪里借。
本项目 17 份 lib 的导入之所以能收敛，很大程度靠这张图
把「17 个独立问题」压缩成「2 个家族的问题」。

> 💡 君之一席话
> **考据不必靠传说**——当你手上有一批来历不明的东西，先找一个便宜、可重跑的量测把它们的关系量出来；量得出来的结构，比任何人的回忆都可靠。

> 🔍 老手视角──真正的门道
> 这一节的方法在软件考古之外也很通用：**当你面对 N 个「据说有关系」的东西，先找一个可以自动计算的相似度，把 N 个问题压成 k 个群的问题。** 文件路径集合只是其中一种特征；相依清单、API 调用集合、字符串常数集合、错误消息集合都可以拿来当指纹，而且各有各的鉴别力（字符串常数对「换皮」特别敏感，相依清单对「同一个框架的项目」特别敏感）。老手做这件事的顺序是：**先挑最便宜的特征试一次，看分布有没有明显的断层**——本例的 0.90 与 0.012 之间那个大洞，就是「这个特征有效」的信号。如果分布是连续的、没有断层，那通常代表你挑错特征了，换一个，而不是硬套一个门槛值。可落地的做法：任何「这几份东西是不是同一个来源」的问题，**先画分布再定门槛**；先定门槛再看数据，得到的永远是你想看到的答案。

## 051　特征组合，不是继承树 — mudlib 的对象模型

**标签**：`#对象模型` `#mixin` `#多重继承` `#组合` `#架构`
**证据等级**：🟢 本项目实测（`feature/` 43 个模块、`inherit/char/char.c` 继承 18 个）

**起源**：家族 B 的对象层有一个很鲜明的形状，
而且它和多数人对「面向对象」的直觉不一样。

打开一个角色的基底类别，看到的不是一条继承链，而是**一张清单**：

```c
inherit F_ACTION;      inherit F_ALIAS;       inherit F_APPRENTICE;
inherit F_ATTACK;      inherit F_ATTRIBUTE;   inherit F_COMMAND;
inherit F_CONDITION;   inherit F_DAMAGE;      inherit F_DBASE;
inherit F_EDIT;        inherit F_FINANCE;     inherit F_MESSAGE;
inherit F_MORE;        inherit F_MOVE;        inherit F_NAME;
inherit F_SKILL;       inherit F_TEAM;        inherit F_SUIT;
```

**18 个**。整个 mudlib 提供 **43 个** 这样的 `F_*` 模块。

**技术内核**：这不是继承，是**组合**——LPC 的多重 `inherit` 被当成 mixin 用。

```
                 ┌─ F_DBASE     数据：属性树（§052）
                 ├─ F_MOVE      能被搬动、有 environment
   一个「角色」 = ├─ F_ATTACK    能打架
                 ├─ F_SKILL     有技能
                 ├─ F_CONDITION 有状态效果
                 ├─ F_TEAM      能组队
                 └─ …（共 18 个）

   一个「物品」 = F_DBASE + F_MOVE + F_CLEAN_UP + …
   一个「房间」 = F_DBASE + F_CLEAN_UP + …（不含 F_MOVE：房间不会被搬走）
```

**判准很单纯：一个 `F_*` 就是一种「能力」，对象要哪些能力就 inherit 哪些。**

这个模型的三个性质：

| 性质 | 说明 |
|------|------|
| **正交** | `F_MOVE`（能被搬）与 `F_ATTACK`（能打架）互不相关，可以任意组合 |
| **扁平** | 没有深继承链——`char.c` 直接列 18 个，不是 `char → living → object` 叠三层 |
| **可加不可减** | 要添加能力就多 inherit 一个；**但没有办法「不要某个能力」** |

第三条是罩门的来源，稍后说。

**解决的痛点**：MUD 的对象天生**不适合单一继承**。
「一把会说话的剑」既是武器又是 NPC；
「一间会移动的房间」（船舱）既是房间又能被搬动；
「一个可以被拿起来的 NPC」（小动物）既是生物又是物品。

单一继承要处理这些，只能靠深继承链加大量覆写，
或者拷贝粘贴。**组合模型让这些混种变成加法**：
要哪几种能力就列哪几个。

**设计对照：同一个问题的四种答案**

| 模型 | 代表 | 组合方式 | 诊断难度 |
|------|------|---------|---------|
| **单一继承树** | Java、C# | `extends` 一个 | 低（链是线性的） |
| **多重继承／mixin** | **LPC 的 `F_*`**、Python、Ruby module | `inherit` 多个 | **中高**（要知道方法从哪来） |
| **trait / interface + 缺省实作** | Rust trait、Scala、Go 嵌入 | 声明 + 实作分离 | 中（有类型检查帮忙） |
| **ECS（实体－组件－系统）** | 现代游戏引擎 | 挂组件，行为在系统 | 中（数据与行为彻底分离） |

LPC 的 `F_*` 在 1990 年代就落在第二列，
而它处理的问题（游戏对象的能力组合）今天的主流答案是第四列。
**两者的共同直觉是一样的：对象的能力应该是可组合的清单，不是可继承的分类。**
差别在 ECS 把数据与行为也拆开了，而 `F_*` 没有——
`F_SKILL` 同时带着技能的数据访问与技能的逻辑。

**踩过的坑**：组合模型的代价，本项目在移植时全部尝过一轮：

| 问题 | 具体形状 |
|------|---------|
| **方法从哪来？** | 看到 `query_skill()` 要先知道它在 `F_SKILL` 里——没有类型系统会告诉你 |
| **名称冲突** | 两个 `F_*` 都定义同名函数时，**顺序决定谁赢**，而顺序是 `inherit` 的书写顺序 |
| **不能减** | 某个 `F_*` 的行为不合用时，只能覆写或用 shadow 盖掉，**不能把它拿掉** |
| **`create()` 的链** | 每个 `F_*` 可能都有初始化，谁先谁后不明显——§038 那类「跑着新程序带着旧数据」的幽灵 bug 常出在这 |

第二列在 §032 的兼容性修正里出现过一次变体：
`is_killing(ob)` 类型不符（声明 `string` 却传 object）之所以能潜伏多年，
部分原因就是**组合模型让「这个函数的正确签名是什么」没有单一答案可查**。

**优点 / 罩门**：优点是**世界观可以很自由**——
中文武侠 mudlib 那些奇形怪状的对象（可携带的坐骑、会打架的房间机关、
既是装备又是技能载体的内功心法）都能用加法表达出来。
罩门是**可诊断性**：一个对象为什么有这个行为，答案分散在 18 个文件里，
而且没有工具会替你合并。

**效益**：对逆向工作，这个模型给的是**一条固定的搜索路径**。
要找「某个行为是谁做的」，顺序是：

```
对象自己的 .c
  → 它 inherit 的 F_* 清单（逐一）
    → simul_efun 有没有盖掉（§036）
      → 才轮到 driver 的 efun
```

本项目追 ZJMUD opcode 的发送点时走的就是这条路，
而下一节会看到一个很有意思的结果：**有些 opcode 根本不在 UI 层送出，
它藏在最底层的那个 `F_DBASE` 里。**

> 💡 君之一席话
> **当对象的分类方式超过一种，继承树就会开始说谎**——把「是什么」换成「有哪些能力」，架构才不会被世界观绑架。

> 🔍 老手视角──真正的门道
> mixin 这个模型有一个长期成本很容易被低估：**它把「这个东西是什么」这个问题从代码里删掉了。** 单一继承有一个线性的链，你可以回答「这是一个 Living，Living 是一个 Object」；组合模型的答案是「这东西有 18 种能力」，没有名字、没有阶层、没有可以印在文档上的分类。这在小系统里是解放，在大系统里是负担——因为**沟通需要名字**。老手用组合模型时通常会补一层命名惯例当作补偿：把常用的能力组合固化成几个有名字的基底（本例的 `char.c` / `npc.c` / `room.c` / `item.c` 就是），让 90% 的对象从有名字的东西开始，只有真正的混种才手动组合。可落地的做法：**用组合当机制，用命名的缺省组合当接口**——直接把 mixin 清单暴露给所有用户，等于把架构的复杂度转嫁给每一个新人。

## 052　属性树 — 一个 mapping 撑起整个游戏状态

**标签**：`#数据模型` `#无schema` `#路径访问` `#耦合` `#副作用`
**证据等级**：🟢 本项目实测（`feature/dbase.c` 与全 mudlib 的使用形式）

**起源**：§051 那 43 个 `F_*` 里，有一个是所有对象都会 inherit 的：**`F_DBASE`**。
它是整个 mudlib 的数据层——而它的实作内核只有一个东西：

**一个 mapping。**

**技术内核**：所有游戏状态都住在对象的 `dbase` 这个 mapping 里，
用一对函数访问，键可以是**路径**：

```c
set("name", "王小二");
set("attribute/str", 25);          // ← 斜线 = 嵌套
query("attribute/str");            // → 25
query("family/family_name");       // → 门派名
query("skill/dodge/level");        // → 技能等级
```

`set`／`query` 看到键里有 `/` 就把它拆开，
在 mapping 里逐层往下走（这件事由另一个模块 `F_TREEMAP` 负责）。

**于是整个游戏的数据模型是一棵无 schema 的树：**

```
对象的 dbase
├── name, id, short, long          基本识别
├── attribute/ str con dex int per  五围
├── combat_exp, level, skill_point  成长（§053）
├── skill/<技能名>/level            技能
├── family/family_name              门派
├── equipped, armor_prop, …         装备状态
├── exits/<方向>                     房间出口
└── …（任何人想加的任何东西）
```

**这个设计的三个性质，决定了它上面所有东西的形状：**

| 性质 | 好处 | 代价 |
|------|------|------|
| **无 schema** | 加一个属性零成本——`set("我的新字段", x)` 就有了 | 没有任何东西知道「合法的字段有哪些」 |
| **路径访问** | 嵌套结构不需要声明类型 | 打错字 = 一个新字段，**静默** |
| **统一接口** | 存盘、读档、串行化、调试都只要处理一种结构 | 性能不佳（每次访问都要解析路径） |

**第二列是关键：`query("atribute/str")` 拼错不会报错，会回 0。**
这是 mudlib 最经典的一类 bug，而它是数据模型的直接后果，不是谁粗心。

**★ 这一节最重要的发现：协议被塞进了数据层。**

本项目在追 ZJMUD opcode 的发送点时，
在 `F_DBASE` 的 `set()` 里找到这样一段逻辑：

```
set("exits/north", 某房间)
   → 侦测到键的第一段是 "exits"
   → 取出目标房间的短描述
   → 立刻对本房间广播一行 ZJEXIT（ESC003）
```

也就是说——**「设置一个出口」这个数据操作，
会直接产生一个协议封包。**

这件事有几个很不小的后果：

1. **协议发送点不只在 UI 层**。本书 §005 用「grep 宏名找发送点」的方法
   统计 opcode 使用频率，这个方法会漏掉这一类——
   **它的触发点是数据写入，不是接口调用。**
2. **对客户端而言，`ESC003` 是一个「数据变更通知」，不是「请画出口」**。
   这解释了本书 §005 观察到的一个现象：出口更新有时会在
   看起来毫无关联的时机出现——因为那一刻有人动了 `exits/` 底下的数据。
3. **这是数据层与表现层的直接耦合**，而且是最紧的那种。
   换一套协议，要改的不是输出模块，是**数据访问的内核函数**。

从架构的角度，这是一个明确的越界：
**`F_DBASE` 的职责是存数据，它不应该知道 ZJMUD 协议存在。**
但从实务的角度，它也很好理解——
**这是「保证不漏送」最省事的做法**：
把通知绑在数据变更上，就不可能有人改了数据忘了通知。

**这个取舍在现代有一个名字：反应式数据（reactive data）。**
Vue 的 `ref`、MobX 的 observable、各种 ORM 的 change hook，
做的是同一件事——**把「数据变了」自动变成「通知出去」**。
差别只在现代做法把通知的**目标**抽象掉了（订阅者自己注册），
而 `F_DBASE` 直接写死了「送一个 `ESC003` 给这个房间里的人」。

**解决的痛点**：无 schema 的属性树解的是一个很现实的问题——
**mudlib 是给几十个业余作者共同编辑的**。
要求每个人加属性前先改 schema、跑 migration，这件事在 1995 年的 MUD 巫师群里不可能发生。
**零成本的扩充是这个社群能运转的前提。**

**踩过的坑**：本项目在移植时撞到的是它的另一面——
**没有 schema 就没有办法验证封存的完整性**。

`nt7` 那份缺件的封存（§032），少的是整个玩家层与世界。
如果数据有 schema，缺一整类东西应该在加载时就报错；
但属性树的哲学是「没有的字段就是 0」，
所以**缺件表现成「进去之后什么都没有」，而不是一个错误**。

这再一次回到本书反复出现的主题：**静默失败**。
无 schema 的数据模型，本质上是把所有「缺数据」的错误都变成静默的。

**优点 / 罩门**：优点是**极高的可塑性与极低的协作成本**——
17 份 mudlib 各自往这棵树上加了几百个自己的字段，彼此不冲突。
罩门三个：打错字静默、缺数据静默、以及上面那个**协议耦合进数据层**。

**效益**：对逆向工作，这一节提供了一条很具体的教训：
**找协议发送点时，不要只找「输出」相关的代码，也要找「数据写入」的内核路径。**
本项目的 opcode 使用频率统计（§005）因此有一个已知的偏差——
数据驱动的那几个码会被低估。这件事在规格书里标了，
是本书「证据等级」规矩的一次实际应用：
**知道自己的量测方法会漏掉什么，比量得准更重要。**

> 💡 君之一席话
> **把通知绑在数据变更上，就不可能有人忘记通知——代价是数据层从此知道了协议的存在**；这笔交易在小系统里划算，在要换协议的那一天会一次结清。

> 🔍 老手视角──真正的门道
> 无 schema 的数据模型有一个很有意思的长期轨迹：**它一开始省下的是「定义」的成本，最后付出的是「发现」的成本。** 前三年，加字段零成本、没有 migration、没有版本冲突，所有人都觉得赚到了；第五年，没有人知道这棵树上到底有哪些字段、哪些还在用、哪些是十年前某个巫师加了之后就没动过的。这条轨迹在 NoSQL、在 JSON 设置档、在「先用 map 装着以后再说」的每一个决定里都会重演。老手的缓解手段通常不是「回头加 schema」（那时已经来不及），而是**加一支能把实际使用的键扫出来的工具**——从数据里反推 schema，而不是从文档里查 schema。本项目做同一件事的形式是扫 mudlib 原代码里所有 `set(`／`query(` 的字面字符串，得到一份「这份 lib 真的用到哪些属性」的清单。可落地的做法：任何无 schema 的数据层，**第一天就写那支反推工具**——它的价值会随着数据长大而上升，而写它的成本永远是那半天。

## 053　升级、门派、装备 — 三个机制共用的同一种架构

**标签**：`#游戏机制` `#数据模型` `#三分法` `#守护进程` `#逆向可见性`
**证据等级**：🟢 本项目实测（`feature/` 与 `kungfu/` 的结构与规模）

**起源**：§051 讲了对象模型、§052 讲了数据模型。
这一节看**游戏机制**——但重点不是「这个 mud 怎么玩」，
而是**这些机制在架构上长什么样，以及那个形状对客户端意味着什么**。

因为它们的形状出乎意料地一致。

**技术内核：三分法。**

中文武侠 mudlib 的每一个游戏机制，都被切成同样的三块：

```
    数据  ──→  在 dbase 属性树里（§052）        「这个角色现在是什么状态」
    行为  ──→  在 feature/ 的某个 F_* 里（§051） 「这个状态能做什么」
    规则  ──→  在 adm/daemons/ 的某个 daemon 里  「全世界共通的算式与表格」
```

四个代表性机制，套进这个三分法：

| 机制 | 数据（dbase） | 行为（`F_*`） | 规则（daemon） |
|------|-------------|-------------|--------------|
| **成长 / 升级** | `combat_exp`、`level`、`skill_point`、`tianfu_point` | `F_LEVEL`、`F_ATTRIBUTE` | 升级曲线与上限 |
| **技能 / 武功** | `skill/<名>/level`、`skill_type`、`meridian/*` | `F_SKILL`（746 行，最大的一个） | `combatd` + `kungfu/` 底下的技能对象 |
| **装备** | `equipped`、`armor_type`、`armor_prop`、`weapon_prop` | `F_EQUIP`、`F_SUIT`（套装） | `itemd` |
| **门派 / 师承** | `family/family_name`、师徒关系 | `F_APPRENTICE` | `familyd` |

**这个三分法就是整份 mudlib 的架构**，
所有机制都是它的实例。理解了它，读任何一个机制都是同一套动作。

**四个机制各自的架构要点（high level）：**

### 成长：属性是五围，成长是两条轨

角色的基本属性是 **`str` / `con` / `dex` / `int` / `per`** 五项——
这组字段名在家族 B 的 16 份 lib 里完全一致，是这一族的另一个指纹。

成长走**两条互不相同的轨**：
- **`combat_exp`（实战经验）**——打架累积，决定「等级」；
- **`skill_point` / `tianfu_point`（点数）**——用来换技能等级。

架构上的意义是：**「变强」不是单一数值**。
等级由经验决定、能力由技能决定、技能由点数决定，
三者用不同的速率成长。这让数值设计有多个独立的旋钮，
代价是**状态面变大**——而状态面变大，正是后面协议设计的压力来源。

### 技能：技能是对象，不是数值

这是家族 B 最有特色的架构决定，也是它 `kungfu/` 目录动辄
**1,200 – 3,469 个文件**的原因。

一项武功不是 dbase 里的一个数字，而是：

```
dbase 里：  skill/<技能名>/level     ← 这个角色练到几级（状态）
kungfu/ 里： 一个 LPC 对象            ← 这门武功「是什么」（行为）
             ├─ class/      门派功夫
             ├─ skill/      基础技能
             ├─ special/    特殊技能
             └─ condition/  状态类
```

**状态在角色身上，行为在技能对象里。**
角色施展武功时，`F_SKILL` 拿着等级去调用那个技能对象。

这是一个很干净的分离，而且它有一个很实际的好处：
**添加一门武功不需要改任何既有文件**——丢一个新对象进 `kungfu/` 就好。
这正是这个目录能长到三千多个档的原因：**它的扩充成本是常数。**

代价是**规模本身**：3,469 个文件要编译、要加载、要维护，
而其中绝大多数在任何一场游戏里都不会被碰到。

### 装备：槽位是类型，套装是规则

装备系统的架构是**槽位化**——`inherit/armor/` 底下一个槽位一个基底类别：

```
head  neck  cloth  surcoat  wrists  hands  finger
waist  pants  boots  shield  shou  …（13 个槽位）
```

一件装备 inherit 哪个基底，就决定了它戴在哪。
**槽位不是一个字段，是一个类型**——
这让「这件东西能不能戴在头上」变成编译期就决定的事，
而不是运行期的字符串比对。

在这之上还有 `F_SUIT`（套装）：**跨对象的规则**。
它的架构位置很有意思——套装效果不属于任何一件装备，
而是「同时穿了某几件」这个**组合**的性质，
所以它必须住在角色身上（`char.c` inherit 了 `F_SUIT`），
不能住在装备上。

**「属性属于个体、效果属于组合」——这是所有套装／羁绊系统的共同结构问题**，
而这份 mudlib 的答案是把它上提到角色层。

### 门派：组织是 daemon，关系是属性

门派（`family`）的架构是最典型的三分法：
- 角色身上只存 `family/family_name` 一个字符串（**数据**）；
- 拜师、逐出、师承查找在 `F_APPRENTICE`（**行为**）；
- 门派有哪些、各自的功夫、入门条件在 `familyd`（**规则**）。

**组织实体本身不是对象，是 daemon 里的一张表。**
这个决定让「加一个门派」变成改一张表，
而不是创建一套新的对象关系。

**★ 这一切对客户端与协议的意义。**

这才是本书关心的部分。三分法造成一个很具体的后果：

| 三分法的哪一块 | 客户端**看得到**吗 | 为什么 |
|--------------|------------------|--------|
| **数据**（dbase） | ✅ 看得到 | 属性条、血条、经验值都是 opcode 送过来的（`ESC012`、`ESC022`） |
| **行为**（`F_*`） | ⚠️ 只看得到结果 | 客户端收到的是「你受了 30 点伤」，不是伤害公式 |
| **规则**（daemon） | ❌ 完全看不到 | 升级曲线、套装效果、门派条件从来不上线路 |

**所以任何 MUD 客户端都不可能「懂」游戏——它只能显示状态。**

这解释了本书 §005 那个 opcode 家族分布为什么长那样：
27 个内核码里，**状态类**（属性条、血条、快捷钮）和**内容类**
（房间、对象、详情、动作列）占了绝大多数，
**没有任何一个 opcode 在传输规则**。

而这一条，正是下一章要谈的整个 MUD 客户端史的起点：
**客户端只拿得到状态与文本，拿不到规则——
所以它三十年来一直在做同一件事：从文本里把状态猜回来。**

**优点 / 罩门**：三分法的优点是**每一块的扩充成本都是常数**——
加武功丢一个档、加门派改一张表、加属性 `set` 一个新键。
这是一个给几十个业余作者长期共同编辑的系统该有的性质。
罩门是**没有任何一处看得到全貌**：
一个「为什么我打不赢这个 NPC」的问题，答案分散在角色的 dbase、
`F_ATTACK` 与 `F_SKILL` 的逻辑、`combatd` 的公式、以及两个技能对象里。

**效益**：对逆向工作，三分法给的是**一张定位表**：
看到一个现象，先判断它属于数据、行为还是规则，
就知道该去哪一层找，也知道**它会不会出现在线路上**。
本项目在还原协议时，凡是判断为「规则」的东西，
一律不去线路上找——**因为那里不会有**。

> 💡 君之一席话
> **客户端永远只看得到状态，看不到规则**——这不是实作的限制，是分层的必然；认清这一点，才不会在协议里找一个永远不会出现的东西。

> 🔍 老手视角──真正的门道
> 「数据／行为／规则」这个三分法值得从架构的角度多看一眼，因为它切的位置很特别：它不是按**领域**切（战斗、社交、经济），而是按**变更频率与作用范围**切——数据每秒都在变且属于个体，行为偶尔改且属于类别，规则很少改且属于全世界。这正好呼应了本书 §033 那句「频率相同的东西放在一起」。它带来的实际好处是：改一条全域规则不需要碰任何一个对象（改 daemon 就好），而加一个个体属性不需要碰任何规则（`set` 一下就好）。老手在看一个长期演化的系统时，会刻意去找它**有没有这种按频率切开的层**；有的，通常还在健康地长大，因为每种改动都有一个明确且便宜的落点；没有的，往往是「改一个小需求要动七个文件」的那种系统。可落地的做法：设计任何要活很久的模块时，先把「每天会变的」「每季会变的」「几乎不变的」三种东西分开放——**分层的依据是时间，不是名词**。
