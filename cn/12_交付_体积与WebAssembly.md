# 第七篇　交付

## 029　4 GB 的中间档 — Rust 的体积从哪里来

**标签**：`#Rust` `#建置产物` `#交付` `#磁盘` `#AI辅助开发`
**证据等级**：🟢 本项目实测

**起源**：项目要交给别人用，先量一下有多大。

```
webclient/          3.7 GB
├── src-tauri/      3.6 GB   ← 几乎全部在这
│   └── target/
│       ├── debug/    2.5 GB
│       └── release/  1.2 GB
├── node_modules/    40 MB
└── src/            172 KB   ← 这才是我们写的东西
```

**我们亲手写的前端 172 KB，建置中间档 3.6 GB——比例是 1 : 21,000。**

`cargo clean` 的回报更直白：

```
Removed 8417 files, 4.0GiB total
```

同一份功能如果用 C 写，`.o` 档加运行档大概几 MB。差距不是倍数，是量级。

**技术内核**：体积来自四个机制，而且它们会相乘。

| 机制 | C 的做法 | Rust 的做法 | 后果 |
|------|---------|------------|------|
| **依赖处理** | 链接系统既有的 `.so` / `.dll` | 把每个 crate 的**原代码抓下来、在你的机器上从头编成静态库** | 一个 Tauri 项目动辄编译数百个 crate |
| **多版本共存** | 一个系统一份库 | 依赖树里若有 `tokio 1.x` 与 `tokio 0.2`，**两份都编** | 体积直接加倍 |
| **调试符号** | `-g` 产生的符号相对精简 | debug profile 缺省 `debug = 2`（完整），为了精准 backtrace | 几十 KB 的 C 运行档，在 Rust debug 下轻松破 50 MB |
| **增量编译缓存** | 没有等价物 | `target/debug/incremental/` 随修改次数线性增长 | 改越多次、越肥 |

**踩过的坑：AI 辅助开发是这件事的放大器。**

本项目整段开发都在 AI 代理的协助下进行，而代理的行为模式**刚好踩满四个机制**：

1. **高频编译**。代理每改一次就想确认「还编得过吗」，于是 `cargo check` / `cargo build` 跑得比人类频繁得多，增量缓存快速堆积。
2. **倾向引入现成 crate**。C 里要手写的东西，Rust 生态多半有现成的；代理为了快速完成任务会直接引入，而一个 crate 背后常牵出数十个间接依赖。
3. **测试会各自产生运行档**。Rust 的 `#[test]` 每个测试单元编出独立的二进位，是隐形的空间杀手。
4. **debug 与 release 并存**。开发用 `tauri dev`（debug），交付用 `tauri build`（release），两份都留着——本项目就是 2.5 GB + 1.2 GB。

> 这一节的因果要讲清楚：**Rust 不是「写出来的程序很肥」，是「编出来的过程很肥」**。
> 本项目交付的 release 运行档只有 **3.2 MB**——比那 4 GB 中间档小了 1,250 倍。
> 混淆这两件事，会得出「Rust 产物很大」这种完全错误的结论。

**效益**：知道体积来自「过程」而非「产物」，清理策略就很明确——**清过程，留产物**。

## 030　交付前的清理 — 清过程，留产物

**标签**：`#交付` `#cargo-clean` `#gitignore` `#工程卫生`
**证据等级**：🟢 本项目实测（3.9 GB → 335 MB）

**起源**：「我要给其他人用。」

**技术内核**：依交付对象分两种做法。

### 交付「原代码」——给要自己编译的人

```bash
cargo clean
```

**直接删掉整个 `target/`**，项目回到只剩 `.rs` 与 `Cargo.toml` 的状态。
用 `cargo clean` 而不是手动 `rm -rf target/`，是因为它认得 workspace 布局与
`CACHEDIR.TAG`，也会回报实际删了什么——手动删只会得到一片沉默。

### 交付「运行档」——给要直接跑的人

**顺序很重要，而且很容易做错：**

```bash
cargo build --release        # ① 一定要 release，绝不交付 debug 版
cp target/release/<name>.exe  <项目目录之外>   # ② 先把产物移出去
cargo clean                  # ③ 再清（clean 会把 exe 一起删掉）
```

**②③ 的顺序是本节唯一的重点。** `cargo clean` 不会替你保留运行档，
先清再找就来不及了——本项目的做法是先备份 exe、`cargo clean`、再放回
`target/release/`，因为启动脚本检查的就是那个路径。

> ⚠️ 清完务必**实际运行一次**那颗 exe。
> 「文件还在」不等于「还能跑」——这正是本书第五篇七次事故的共同教训：
> 编译成功 ≠ 能用，文件存在 ≠ 能运行。

### 让它从一开始就不要肥

三个层次，由轻到重：

**① `.gitignore`**——最低限度，至少别让 4 GB 进版控：

```gitignore
webclient/src-tauri/target/
!webclient/src-tauri/target/release/zjmud-client.exe   # 保留交付物
node_modules/
```

**② `Cargo.toml` 减肥设置**：

```toml
[profile.dev]
debug = 1                       # 缺省 2（完整符号）→ 1（仅行号）

[profile.dev.package."*"]
opt-level = 3                   # 第三方套件直接用优化模式编，减少中间产物

[profile.release]
opt-level = "z"                 # 以体积为最优先
lto = true                      # 链接期优化，移除未使用的代码
codegen-units = 1               # 优化做得更彻底
panic = "abort"                 # 不产生 backtrace 相关信息
strip = true                    # 移除调试符号
```

> **证据等级 🔴 推论**：上面这组 `[profile.release]` 设置**本项目尚未实测**。
> 本项目目前的 release exe 是 3.2 MB（未套用任何减肥设置）。
> 一般说法是可以缩到数百 KB，但**在你自己的项目上量过之前，不要引用那个数字**——
> 实际效果高度依赖依赖树大小，而 Tauri 项目内嵌了整个 WebView 绑定，未必缩得那么多。
> 验证方式很简单：加上设置 → `cargo build --release` → 比对前后 exe 大小。

**③ 把 `target/` 移出项目目录**——治本：

```toml
# .cargo/config.toml
[build]
target-dir = "C:\\Users\\<你>\\AppData\\Local\\Temp\\rust-target"
```

这样不管背景编译多频繁，**项目目录永远是轻的**，要打包时也不必先 `cargo clean`。
代价是换机器／清系统暂存后要全部重编一次。

### 与 AI 代理协作时的节流时机

什么时候可以要求代理停止高频编译？三个判准：

| 时机 | 判准 | 指令 |
|------|------|------|
| **语法定型** | 类型、生命周期、所有权错误都清完，`cargo check` 过得去，接下来只调算法与命名 | 「接下来专注逻辑重构，不要运行 `cargo build`／`cargo check`，等我要求再统一验证」 |
| **写文档阶段** | 功能完成，在补注解／README／重命名 | 同上 |
| **微调测试** | 只在改测试的输入输出数值 | 「只跑 `cargo test -- <测试名>`，不要全量 build」 |

`cargo check` 比 `cargo build` 轻非常多（不做代码产生），**在「只想知道语法对不对」的
阶段应该是默认值**。本项目后期验证 Rust 改动时用的就是 `cargo check`，1.18 秒完成。

**踩过的坑**：清理不是只有 Rust。本项目清完 `target/` 之后才发现，
服务器的 `debug.log` 有 **8.6 MB、51,574 行，其中 51,253 行是自己造成的重连风暴警告**
（见 §015 第七次事故）。清理的范围要涵盖「**你的程序在别人系统上留下的东西**」，
不只是「你的建置目录」。

**效益**：3.9 GB → 335 MB，可运行档保留、测试 177 条全过、书籍网页照常开。

## 031　WebAssembly 的边界 — 能搬什么，不能搬什么

**标签**：`#WebAssembly` `#浏览器沙箱` `#代码共用` `#架构边界`
**证据等级**：🟡 依原代码相依性分析（尚未实际编译验证）

**起源**：一个很自然的问题——**既然桌面版的内核是 Rust，浏览器版能不能也用同一份 Rust，编成 WebAssembly 就好？**

这个问题的答案不是「可以」或「不可以」，而是**逐个模块看它碰不碰得到 I/O**。

**技术内核**：把 Rust 端两个模块摊开看依赖。

| 模块 | `use` 声明 | 能上浏览器 WASM？ |
|------|-----------|-----------------|
| `telnet.rs`（162 行） | **一个都没有** | ✅ 可以，而且几乎不用改 |
| `mud.rs`（200 行） | `tokio::net::TcpStream`、`tokio::io`、`tauri::AppHandle` | ❌ 不可能 |

判准只有一条：**纯计算可以搬，I/O 不行。**

`telnet.rs` 的签名是 `filter(buf: &[u8]) -> Filtered { data, reply }`——
输入字节、输出字节，没有 socket、没有时间、没有文件、没有全域状态。
这种形状的代码是 WASM 的甜蜜点。

`mud.rs` 则是**架构上不可能**：浏览器沙箱没有 raw TCP socket API，
这是浏览器的限制而**不是 Rust 或 WASM 的限制**。把 `mud.rs` 编成 WASM 在技术上会失败
（wasm32 目标下 `tokio::net` 不可用），就算勉强编过，运行时也没有 socket 可以开。

> **所以本书第四篇的 WebSocket 桥接不是临时方案，是架构必然。**
> 无论前端用 JS、WASM 还是任何未来技术，只要协议是原生 TCP、
> 而运行环境是浏览器，**中间就一定要有一个能开 socket 的进程**。
> 这一点不会因为换技术而改变。

**那搬 `telnet.rs` 有什么好处？** 有一个很具体的：**消除重复实作**。

目前 IAC 剥除逻辑存在**两份**：

```
src-tauri/src/telnet.rs   162 行   Rust，桌面版用
bridge/telnet.mjs          63 行   JavaScript，浏览器版用
```

两份必须行为完全一致，否则同一个服务器在两个版本会表现不同。
本书 §028.6 因此把那 42 个实机字节同时当成 Rust 测试与 JS 测试的输入——
**用测试来钉住两份实作的等价性**。若 `telnet.rs` 编成 WASM 给桥接用，
这份重复与它的等价性负担就一起消失了。

**踩过的坑（诚实揭露）**：这一节是**依相依性静态分析得出的结论，尚未实际编译验证**。
要升级到 🟢 需要：

```bash
rustup target add wasm32-unknown-unknown
cargo build --target wasm32-unknown-unknown   # telnet.rs 要先拆成独立 crate
```

在那之前，本节对 `telnet.rs` 的判断应视为**高信心推论**，不是实测结果。
本书的规矩是证据等级要标清楚——**没量过就不能标 🟢**，即使推论看起来再稳。

**成本评估（决定要不要做的关键）**：省下的是 63 行 JavaScript 与一份等价性负担；
付出的是 wasm32 工具链、一个额外的 crate 边界、桥接的 WASM 加载流程，
以及让「纯 HTML 无建置步骤」的前端原则出现第一个例外。
**以本项目 63 行的规模，这笔帐不划算**——记录它是为了说清楚边界在哪里，
而不是建议照做。若 `telnet.rs` 有 1,600 行而非 162 行，结论会相反。

> 💡 君之一席话
> **「能不能编成 WebAssembly」从来不是语言问题，是 I/O 问题——纯计算搬得走，碰硬件与网络的搬不走；先看 `use` 清单，再谈可行性。**

> 🔍 老手视角──真正的门道
> 这一篇两个主题看似无关（磁盘体积、WASM 可行性），其实共用同一种思考习惯：**先量，再谈**。谈体积时，「Rust 项目很肥」是没有信息量的抱怨；「产物 3.2 MB、过程 4.0 GB、比例 1:1250」才能导出正确的行动（清过程、留产物）。谈 WASM 时，「Rust 可以编 WASM」是正确但无用的事实；「`telnet.rs` 零依赖所以可以、`mud.rs` 用了 `tokio::net` 所以不行」才是能拿来做决策的答案。老手在面对「这个能不能做」的问题时，第一个动作几乎都不是回答，而是**把问题换成一个可量测的形式**——体积换成「哪个目录多大」，可行性换成「相依清单里有没有 I/O」。可落地的做法：任何技术可行性评估，先写下你要量什么、以及什么结果会让你改变答案；量不出来的可行性评估，本质上是猜测换了一个比较体面的说法。

## 032　前提被拿掉的那一天 — 服务器搬进分页

**标签**：`#WebAssembly` `#架构前提` `#重入` `#竞态` `#闭环验证`
**证据等级**：🟢 实测（收藏中 17 个 mudlib 全部打包并实跑，17 个都走完注册→建角→进世界）

**起源**：§031 的结论写得斩钉截铁——

> 只要协议是原生 TCP、而运行环境是浏览器，中间就一定要有一个能开 socket 的进程。

三个月后，FluffOS 官方发了 WebAssembly build。**那句话没有错，但它的前提被拿掉了。**

**技术内核**：§031 的推理链是「浏览器没有 raw socket → 所以要有代理」。
成立的隐含前提是**服务器在远程**。WASM 版把整台 driver 搬进分页之后：

```
桥接版   浏览器 ── WebSocket ──> bridge/server.mjs ── TCP ──> driver.exe
WASM 版  浏览器 ── 函数调用 ──> driver（同一个分页、同一份内存）
```

**没有网络，所以不需要能开 socket 的进程。** 接口只有五个导出函数与两个回呼：

| 导出 | 作用 |
|------|------|
| `fluffos_boot(config)` | 启动（mudlib 已在 MEMFS 里） |
| `fluffos_tick(now)` | 心跳。原生版由 libevent 驱动，这里由页面 `setInterval` 手动泵 |
| `fluffos_connect()` | 开一条虚拟连接，回传 id |
| `fluffos_input(id, bytes)` | client → server |
| `Module.fluffos.onOutput(id, bytes)` | server → client |

**而 `mud.rs` 依然编不成 wasm32**（`tokio::net` 在该 target 不存在）——§031 对它的判断没有变。
变的是**它不再需要存在**：它的位置被 driver 自己的 `src/wasm/comm_wasm.cc` 占走了。

**踩过的坑：三个只有「服务器在分页里」才会出现的失效模式。**

三个症状完全相同——**送出去的东西服务器毫无反应**——但成因一个比一个难看见。

| # | 症状 | 真因 | 怎么找到的 |
|---|------|------|-----------|
| 1 | 收到握手行后回复，服务器没反应 | 在 `onOutput` 回呼里直接调用 `fluffos_input`，等于在 driver 的输出路径中途重入它 | 官方参考前端的注解写着 “sends must be queued” |
| 2 | 排队之后**还是**没反应 | 误判成时序问题，先加了「拨号后 grace 期」，再加了「输出静置窗」——**两个都无效** | 加了才发现无效，这两层后来留着当纵深防御，但不是解 |
| 3 | 排队、延迟都试过还是没反应 | `send()` 用 `connId === null` 判断「还没连上」。而 `fluffos_connect()` **会在自己回传之前**就同步回呼 logon 的输出——此时 `connId = ccall(...)` 那行赋值还没发生，`connId` 仍是 null，于是整包被静默丢弃 | 在 `rawSend` 印一行追踪，发现**它一次都没被调用** |

第 3 个是真因，而前两次的修法都创建在「一定是时间问题」这个错误假设上。

**分辨这两者的方法只有一个：不要猜东西为什么没送到，先确认它到底有没有被送出。**
`rawSend` 的调用次数是 0 还是 1，这件事不需要推理，加一行 `console.error` 就有答案；
而在拿到那个答案之前，任何关于「延迟多久才对」的讨论都是在错误的问题上做优化。

> 本书 §015 的七次事故里，第 1 次（`scrollTo` 不存在打断 `mount()`）与这次是同一种：
> **静默失败**。差别在于当时花了四次交付才发现，这次花了三次尝试——
> 因为这次一开始就有一个能自己跑完的验证回路（下一段）。

**解决的痛点**：能不能上线不再是「感觉应该可以」。

打包管线的每一个 mud 都会被 `tools/boot-test.mjs` 真的跑一次：

```
拨号 → 等 ver1.0: 握手 → 送帐号密码 → 收 ESC000 0008（要求建角）
     → 送 性别║头像║暱称 → 收 ESC000 0007 → 送 look → 统计收到哪些 opcode
```

走完才给 `playable`，只开得起来给 `limited`，连握手都没有给 `noboot`。
**分级是量出来的，不是标上去的**，所以清单不会随时间变成谎言——
driver 升版或 mudlib 改坏，下一次建置就会自己降级。

跑完整批、把每一次失败都追到真因之后：**17 个收录，17 个都 playable**
（这个数字曾经停在 14，最后三个的收尾见下方）。
而它们不是「本来就能跑」——每一个都是被下面这些**通用**修正救回来的，
每一条修正都对应一次实测失败，而不是预防性猜测：

| 修正 | 症状 | 真因 |
|------|------|------|
| 设置文件名 | `boot exit(-1)` | 文件名从 `config.ini` 到 `config.hell` 都有，得从启动批量档反推 |
| `#define static` | master.c syntax error | FluffOS 移除了 `static` 修饰词；补一行不够，要照上游用 `__SENSIBLE_MODIFIERS__` **互斥**分岔 |
| `external_port_1` | 连上但编码分支跑错 | wasm 用第一个 external_port 当来源端口 |
| `is_chinese()` | 建角卡在「请您用中文取名字」 | 逐字节的中文判断（GBK `%2`、UTF-8 `%3`）在码点索引下全数失效 |
| 日志子目录 | `fluffos_connect` 回 -1 | `log_file("static/logon")` 找不到目录 → logon 失败 → driver 踢掉连接 |
| config 绝对路径 | `Bad mudlib directory: 'c:\hell'` | 设置里写着原营运者机器上的路径 |
| `is_killing(ob)` | 登录后生不出身体 | 声明 `string` 却传 object；旧 MudOS 放行、FluffOS 不放行 |
| `valid_write` | 建角时 `Denied write permission` | 找不到 SECURITY_D 就一律拒绝，而建角正好发生在它加载之前（同档的 `valid_read` 是 fail-open——**同一个文件里两个相反的缺省**） |

**最后 3 个是另一类问题，值得单独说**：它们不是兼容性坏了，是**封存本身不完整**——
nt 家族的来源快照少了 simul_efun 缺件，其中 `nt7` 甚至整个玩家层与世界都不在
（`clone/user/` 是空目录、没有 `d/`）。这种缺口硬修等于替别人重写 mudlib。
最后的解法不是修，是**补件**：用同一款游戏的**另一份快照**把缺的部分接上去
（kungfu 文件名 99.7% 同名，可以逐档比对；补件明细记在 `libs/nt7/mud.json`）。

> **「修不好」与「数据不全」是两种完全不同的失败**，混在一起会让人一直在错的方向上加班。
> 分辨的方法很直接：**看缺的是行为还是文件**。行为不对是兼容性问题，
> 文件不在是封存问题——后者再怎么读原代码也读不出来。

**最贵的一次错误不在上表**：把说明写成 config 的**行尾注解**，而 FluffOS 的设置档
没有行尾注解——值取的是冒号后整行。三个原本已经修好的 lib 因此变回 `noboot`，
而且修正脚本每重跑一次就再叠一层注解。**自动修正工具本身必须是幂等的**，
否则它会变成另一种损坏来源。

**优点 / 罩门**：优点是整条交付链没有任何服务器端代码，静态托管即可，
而且每个访客拿到的是一份全新的世界，没有滥用面。
罩门三个，而且都不是 bug 是**本质**：没有多人（同分页可多开连接，跨用户不行）、
重整即失（MEMFS 不落地）、每个 mud 要下载 20–60 MB。
**它是展示品与教材，不是正式服**——把这件事写在显眼处，比事后解释便宜。

> 💡 君之一席话
> **一个结论的寿命，取决于它的前提而不是它的推理**——推理再严密，前提被换掉那天它就过期了；所以写下结论时，把前提一起写下来，比把推理写得更漂亮更有价值。

> 🔍 老手视角──真正的门道
> §031 那句话当时是对的，今天依然对，只是**不再适用**。老手与新手在这里的差别不是谁预见了 WASM driver 的出现——没有人预见得到——而是结论被写成什么形状：写成「浏览器版一定要有桥接」的人，会在新前提出现时整段推翻重来，而且很可能不服气；写成「协议是远程 TCP 时一定要有桥接」的人，只要把前提一比对就知道该换路了。可落地的做法：任何架构结论都加一句「这个结论在什么情况下会失效」。写得出来，代表你真的理解为什么；写不出来，那句结论其实是一个信念。**而信念不会因为证据改变，只会因为挫折改变——那通常太晚了。**
