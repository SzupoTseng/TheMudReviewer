# 第一篇　逆向工程

## 001　选对标的 — 三个 APK 里，只有一个值得拆

**标签**：`#逆向` `#APK` `#multidex` `#选型` `#成本控制`
**证据等级**：🟢 实机（文件本身）
**工具**：apktool 2.7.0、jadx 1.5.1

**起源**：手上有三个安装档，文件名看不出差别：`UTF-8版客户端_sign.apk`（1.1 MB）、`newzjclient.apk`（4.3 MB）、`zjmudclient.apk`（4.5 MB）。直觉会想「拆最大的，功能最完整」。这个直觉会让你多花一整天。

**技术内核**：判断标的优劣，不需要先反编译，**看 dex 结构就够了**。

```
UTF-8版客户端_sign.apk   classes.dex 195 KB          132 个文件
newzjclient.apk          classes.dex ~ classes26.dex  277 个文件
zjmudclient.apk          classes.dex ~ classes26.dex  294 个文件
```

单一 dex 对上 **26+ 个 multidex**。Android 的 dex 有 65,536 个方法引用的上限，一旦超过就得拆成 multidex。一个纯粹的 MUD 文本客户端**不可能**写到需要 26 个 dex——那些额外的体积几乎必然是广告 SDK、推播、统计、热更新框架，或是加固壳。

拆开后印证了这个判断：那份 1.1 MB 的版本只有 **130 个 smali 类别**，全部在 `com.zwyouto.*` 一个命名空间下，四个 Activity 加一个 Application 类。**没有一行是无关的。**

**解决的痛点**：逆向的成本几乎全花在「读懂无关的东西」。选错标的，你会在广告 SDK 的混淆代码里耗掉两天，才发现真正的协议逻辑只有三百行。

**踩过的坑**：本地备好的 jadx 是 **GUI 专用的 exe**，没有 CLI，无法批量反编译。改从 GitHub 抓 CLI 版时，第一次下载在 94 MB 处逾时中断——因为预期它「应该只有 40 MB」，一度怀疑抓错文件。实际用 `curl -sIL` 查 `content-length` 才确认：**这个版本本来就是 116 MB**。

> 凭感觉判断「文件应该多大」，比不上一行 HEAD 请求。

**优点 / 罩门**：apktool 给出可读的资源与 layout XML，是 UI 规格的最佳来源；jadx 给出接近原代码的 Java，是逻辑的最佳来源。**两个都要用，缺一不可**——apktool 不还原逻辑，jadx 不还原资源。罩门是两者都会在混淆过的代码上失效，而这正是为什么「选一个没混淆的标的」如此关键。

**工具对照**：

| 对手 | 定位 | 相对优势 | 相对劣势 |
|------|------|---------|---------|
| apktool | 资源与 smali 还原 | layout/values/manifest 完整可读，是 UI 规格圣经 | 只给 smali，逻辑难读 |
| jadx | dex → Java 反编译 | 输出接近原代码，控制流清楚 | 不还原资源；遇混淆会产生大量 `a.b.c` |
| Ghidra | 通用逆向平台 | 支持 DEX/Dalvik，能做交叉引用分析 | 对纯 Java 项目杀鸡用牛刀 |

**效益**：正确的标的选择，让整个协议还原工作从「预估两三天」压缩到半天。

> 💡 君之一席话
> **逆向工程的第一个技术决策，发生在你打开反编译器之前——选错标的，之后每一分钟都在替别人的广告 SDK 加班。**

> 🔍 老手视角──真正的门道
> 老手拿到多个版本的 APK，会先做三件不花钱的事：比 dex 数量、比 `AndroidManifest.xml` 的权限清单、比 `assets/` 的文件名。本项目那份干净版申请了 **27 项权限**（相机、定位、通话、开机自启…），对一个文本游戏来说绝大多数用不到——这既是「原作者习惯性拷贝权限模板」的证据，也提醒你：**权限清单是最快看穿一个 App 真实企图的地方**。真正的门道在于，逆向的目标不是「还原全部」，而是「还原到够写出可互通的实作为止」——分得清这条线，项目才会收敛。

## 002　字符串常数 — 三十分钟看穿一套协议的骨架

**标签**：`#逆向` `#字符串分析` `#协议发现` `#smali` `#快速侦察`
**证据等级**：🟠 客户端反编译

**起源**：反编译完成后，最快理解一个未知协议的方法不是逐行读逻辑，而是**把所有字符串常数倒出来排序**。代码会骗人（死码、废弃分支），字符串不会——它们是协议在二进位里留下的指纹。

**技术内核**：一行指令从 130 个 smali 档抽出 431 个唯一字符串：

```bash
grep -rhoP 'const-string[^,]*, "\K[^"]{2,}' smali/ | sort -u
```

其中三组立刻让整套协议的形状浮现：

**第一组——行级 opcode。** 三十几个 `` 开头、后接三位数字的字符串：

```
000  001  002 … 024
045  100  900  903  905  913
997  998  999
```

看到这组的瞬间就知道：这不是纯 telnet 终端机，而是**在文本串流上叠了一层行级指令**。而且编号有规律——`9xx` 明显是 `0xx` 的反向操作（`903` 删出口对 `003` 建出口，`905` 删对象对 `005` 建对象）。

**第二组——字段标记。** `$zj#`、`$z2#`、`$br#`、`$dh#`、`$sock#`、`$N`、`$obj#`、`$exp#`、`$god#`、`$txt#`。

这组告诉你 payload 不是自由文本，而是**有结构的记录**，用字符串当分隔符而不是二进位长度前缀——典型的「从 telnet 时代长出来」的设计。

**第三组——ANSI 扩充。** 除了标准的 `[0m`、`[31m`、`[1;33m`，还混着 `[f#`、`[b#`、`[s`、`[u`、`[9m`、`[2J`。

前两个是自订前景／背景色，后面几个更有趣：`[s` 和 `[u` **以 `]` 收尾而不是 `m`**——那是这套方言自己加的东西，也是后来咬人最狠的一个细节。

**解决的痛点**：面对未知协议时，「从哪里开始读」本身就是最大的成本。字符串常数把搜索空间从「130 个类别、上万行代码」压缩到「431 行文本」。

**踩过的坑**：字符串倾印会同时捞出一批**假线索**——HTTP 端点写着 `http://127.0.0.1/mobi/login.php`（占位值，不是真实服务器）、一个八字符的签章 salt 直接明文躺在里面、还有 `https://baidu.com` 这种显然是占位的语音下载网址。**别急着把它们写进规格**，先确认它们在 `.c` 或实机上真的出现过。

**优点 / 罩门**：字符串分析的优点是快、几乎零成本、能一眼看出协议家族。罩门是它**只给你名词，不给你文法**——你知道有 `$zj#` 这个分隔符，但不知道哪个 opcode 用它、切几层。那要靠下一步。

**方法对照**：

| 方法 | 适用阶段 | 产出 | 局限 |
|------|---------|------|------|
| 字符串常数倾印 | 侦察 | 协议词汇表、opcode 清单 | 没有文法与语意 |
| 分派器反编译 | 解剖 | opcode → 行为的完整对应 | 需要读懂控制流 |
| 实机抓包 | 验证 | 真实 payload 样本 | 只涵盖触发到的功能 |

**效益**：三十分钟内置立起整套协议的心智模型，让后续每一次阅读原代码都有地图可循。

> 💡 君之一席话
> **代码会有死码，字符串不会说谎——当你不知道从哪里下手，就先把所有字面量倒出来排序，协议的骨架常常就浮在那里。**

> 🔍 老手视角──真正的门道
> 这一步真正的价值不在「找到 opcode」，而在**创建分类直觉**。看到 `903` 对 `003`、`905` 对 `005`，老手立刻会问：「那 `913` 对什么？」——答案是「清空全部出口」，一个没有对应正向操作的码。这种**编号空隙**往往指向两件事之一：某个功能被移除了，或某个功能还没实作。本项目后来在另一份 header 里发现 `1085` 这个**四字符 opcode**，正是因为早就对「编号应该长什么样」有了预期，才会在它出现时立刻警觉。可落地的提醒：逆向时**把编号表画出来，盯着空格看**，空格比填满的格子信息量更大。

## 003　三方交叉验证 — 这个项目能收敛的唯一原因

**标签**：`#方法论` `#交叉验证` `#证据等级` `#净室` `#规格书`
**证据等级**：🟢🟡🟠 三方并用

**起源**：协议还原做到一半，出现一个典型困境：客户端反编译说 A，但没有任何东西能证明服务器真的送 A。这时候有两条路——赌下去，或者去找第二个证据源。

**技术内核**：本项目最终创建了**三个独立的证据源**，并明确定义它们的优先级：

```
🟢 实机封包        真的连上服务器抓到的字节
     ↑ 推翻
🟡 服务器原代码    LPC 的 #define 与 .c 的实际发送点
     ↑ 推翻
🟠 客户端反编译    APK 还原出的 Java
     ↑ 推翻
🔴 推论            由结构相似性推得
```

**三者互补的方式很清楚**：

- 反编译告诉你**客户端会怎么解读**（含客户端自己的主动行为，这是另外两者看不到的）
- 服务器原代码告诉你**服务器会怎么送**（含中文注解说明意图，信息密度最高）
- 实机封包告诉你**线路上到底跑什么**（唯一能推翻其他两者的裁判）

**解决的痛点**：单一证据源的逆向，错误会安静地潜伏。你不会知道自己错了，直到某个用户在半年后回报一个无法重现的 bug。

**踩过的坑**：这套方法**当场抓到两个已经写进规格书的错误**——

**第一个：`[u` 少了一个冒号。**
反编译里的取值是 `substring(3, indexOf("]"))`。我当时读成「跳过 `[`、`u`，再跳一个字符」，写成 `[u<url>]`。服务器原代码一翻，宏写得清清楚楚：

```c
#define ZJURL(w)   ESA + "[u:" + w + "]"
```

**是 `[u:` 有冒号**，索引 3 正好跳过 `[`、`u`、`:` 三个字符。我的实作会把 URL 解成 `:cmds:look`，**所有可点击链接全部失效**——而且不会报错，只是点了没反应。

**第二个：`$N` 根本不属于那个 opcode。**
我把 `ESC001`（文本输入面板）的指令样板写成用 `$N` 替换数量。服务器原代码里 147 处 `INPUTTXT` 用例，**全部使用 `$txt#`**：

```c
INPUTTXT("请输入想设定的【中文名字 英文名字】：", "name $txt#")
```

而且输入是**自由文本**（服务器拿它接角色名、四项属性数列、聊天内容），不是数字。我不只用错了占位符，连输入框的类型都做错了。

`$N` 确实存在，但它属于**另一个** opcode（`ESC010` 对话框）。两个机制长得像，但不能混用。

**优点 / 罩门**：三方交叉的优点是**错误会自己浮出来**，而且能标出可信度。罩门是成本——你得同时有 APK、服务器原代码和一台能跑的服务器。少一个，方法就降级。

**证据源对照**：

| 证据源 | 看得到 | 看不到 | 典型陷阱 |
|--------|--------|--------|---------|
| 客户端反编译 | 客户端的解读逻辑与主动行为 | 服务器实际送什么 | 死码；索引差一 |
| 服务器原代码 | 发送意图、中文注解、宏定义 | 客户端怎么反应 | **定义了 ≠ 用得到** |
| 实机封包 | 线路上的真实字节 | 没触发到的功能 | 只有一次会话的样本偏差 |

**效益**：规格书从「大概是这样」升级成「每一条都指得出出处」，而且**两个潜伏的致命 bug 在写进代码之前就被拦下**。

> 💡 君之一席话
> **一个证据源给你答案，两个给你怀疑，三个才给你确定——逆向工程里最贵的不是时间，是那个你以为对了却没人反驳的结论。**

> 🔍 老手视角──真正的门道
> 这里最容易被忽略的一点是：**三方冲突时，别急着选一边，先问「为什么会不一致」**。本项目有一处 `ESC003` 出口格式，官方文档写成「出口名字:方向」，而反编译与实机封包都显示是「方向:名字」。答案不是谁错了——是文档作者用「出口名字」这个词去指涉方向关键字，措辞松散而已。如果当时盲从文档把字段对调，八个方向键会全部失效。**不一致本身就是信息**，它常常指向命名习惯、版本演进或文档过期，而不是单纯的对错。可落地的做法：规格书里替每个有争议的字段保留一行「冲突纪录」，写明谁说了什么、你采信谁、为什么——半年后回头看，这行字比结论本身更有价值。
