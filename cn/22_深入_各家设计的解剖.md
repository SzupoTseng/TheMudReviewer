## 066　LDMud 的语言野心 — 把 LISP 放进 LPC

**标签**：`#LDMud` `#closure` `#lambda` `#coroutine` `#lwobject` `#struct`
**证据等级**：🟡 上游 `ldmud/doc/LPC/`（`closures`、`inline-closures`、`coroutines`、`lwobjects`、`structs`、`unions`）

**起源**：§065 那张表里 LDMud 只写了「官方线的连续性」，
那是它的**定位**，不是它的**内容**。

实际打开 `ldmud/doc/LPC/` 会看到一份不太像 1997 年的清单：

```
closures  inline-closures  closure_guide  closures-abstract  closures-example
coroutines  async  await  yield
lwobjects  structs  unions  decltype  references  varargs  modifiers
```

**`async` / `await` / `yield` / `union` / `decltype`。**
这是一支把语言本身当成主战场的 driver。

**技术内核**：四项语言特性，一项比一项激进。

### ① closure — 不是函数指针，是 LISP

MudOS／FluffOS 的 `(: foo :)` 是**函数指针**：指向一个既有的函数。
LDMud 的 closure 是**另一个层级的东西**。

**先是字面量，带命名空间前缀：**

```c
closure f;
f = #'this_player;              // efun closure
f = #'efun::move_object;        // 明确指定 efun（绕过 simul_efun）
f = #'sefun::my_helper;         // simul_efun
f = #'lfun::query_name;         // 本对象的 lfun
f = #'var::hp;                  // ★ 指向一个「全域变量」的 closure
```

`#'var::` 那一行值得停一下：**变量也可以被闭包化**——
你可以把「某个全域变量」当成一个值传来传去。

**然后是 `lambda()`，而这才是它真正的野心：**

```c
f = lambda( ({ 'x }), ({ #'environment, 'x }) );
funcall(f, this_object());      // → environment(this_object())
```

看清楚第二个参数：`({ #'environment, 'x })`——
**这是一个数组，而它就是代码。**
第一个元素是要调用的东西，其余是参数；`'x` 是**符号**（symbol），
在求值时被绑定。

> **LPC 在这里变成了同像性（homoiconic）语言：代码就是数据结构。**
> `lambda()` 几乎是 LISP 的 `lambda` 直译过来——
> 官方文档自己就这样写：*“It is much like the lambda function in LISP.”*

**`funcall()` 与 `apply()` 的差别**也是 LISP 传统：
`apply()` 的**最后一个参数若是数组，会展开成多个参数**。

```c
mixed eval(object ob, string func, mixed *args) {
    return apply(#'call_other, ob, func, args);   // args 展开
}
```

**这意味着什么？** 意味着 mudlib 可以**在运行期组出代码再运行它**。
§062 讲 CD 的 VBFC 时说那是「把函数调用嵌在字符串里」——
LDMud 更进一步：**把代码放在数组里**，类型安全、可组合、可传递。

### ② inline closure — 写在用它的地方

```c
filter(list, function int (mixed x) { return x > 0; });
```

和现代语言的 lambda 一样，而且**可以捕捉上下文变量**。

### ③ coroutine — `async` / `await` / `yield`

这一项在 MUD driver 上出现，坦白说有点超现实。

> Regular LPC functions have a short life span. **They must finish, before a
> new event like a player command can be processed.** Coroutines are a special
> type of functions, **whose execution can be suspended and continued at a
> later time.**

```c
async void fun() { … }

coroutine cr = fun();
```

三个操作：

| 操作 | 语意 |
|------|------|
| `await(cr[, value])` | 调用另一个 coroutine 并**等它 return**；期间本 coroutine 暂停 |
| `yield([value])` | **暂停自己**，把值交给调用者；恢复时 `yield()` 的结果是传进来的值 |
| `yield(value, cr)` | 暂停自己并**直接切换到指定的 coroutine** |
| `return [value]` | 销毁本 coroutine；有人在等就继续它 |

两个实作细节很能说明它的定位：
**coroutine 是传址的**，而且**结束后会退化成整数 0**——
所以「这个 coroutine 还活着吗」就是 `if (cr)`。

**为什么一个 MUD driver 需要这个？**
因为 §037 讲过的那件事：LPC 是**事件驱动、无线程**的，
一次调用必须跑完才能处理下一个事件。
于是所有「跨越多个事件的流程」（多步对话、逐步战斗、
需要等玩家输入的精灵）都得手写状态机——
§044 那条 `input_to` 接力就是一个活生生的例子：
**登录流程被拆成 `logon` → `jiance` → `get_user` 三个函数，
只因为中间要等玩家打字。**

**coroutine 让那条接力可以写成一个函数。**
LDMud 没有加线程（那会毁掉整个模型），
而是加了**可暂停的函数**——在单线程事件循环上得到多步流程的表达力。

### ④ lwobject 与 struct — 补上「轻量数据」这一格

**lightweight object**（概念借自 DGD，§064）：

```c
#pragma lightweight          // 这个档可以被当成轻量对象用（隐含 no_clone）
lwobject lwo = new_lwobject("/obj/foo");
```

> Lightweight objects are **a cross between regular objects and structs**.
> Like regular objects they are built from programs and encapsulate data and
> functions. **Like structs they are automatically destructed, they can be
> copied and saved.**

**struct**：

```c
struct Foo { int one, *two; struct Bar three; };
```

> The name is **resolved when the LPC code is compiled**, making struct member
> access **as fast as array member access**.

**union**（纯编译期，除非开 `#pragma rtt_checks`）：

```c
int|string var;
int|float fun(object|closure f);
<int|string>* arr;              // 数组成员是 int 或 string
int*|string*  arr;              // 「int 数组」或「string 数组」
```

注意最后两行的差别——**LDMud 认真到需要一套角括号语法来消歧义**，
甚至要提醒你 `< <` 之间要有空白，免得被当成 `<<` 操作符。

**解决的痛点**：LDMud 解的是一个很清楚的问题——
**LPC 作为语言，在 1990 年代中期已经落后了。**

对照 §058 那张 MudOS 的类型表：`int` `float` `string` `object`
`mapping` `function` `mixed` 加数组，就这样。
没有结构、没有联集、没有轻量值、没有真正的闭包、没有协程。

**LDMud 的答案是：那就把语言补起来。**

**踩过的坑（生态层面）**：语言补得越好，**离其他分支越远**。
一份用了 closure、struct、coroutine 的 LDMud mudlib，
在 FluffOS 上连编译都过不了——不是兼容性小问题，是**语言不同**。

这解释了一件事：§050 那 17 份中文封存全是 MudOS 系，
**不是因为 LDMud 比较差，是因为两边的 mudlib 从一开始就不能互换。**
语言分歧比 API 分歧更难跨越。

**优点 / 罩门**：优点是**表达力**——用 closure 写的 mudlib，
在抽象程度上可以远超同期的 MudOS mudlib。
罩门有两个：其一，**心智负担**（`lambda()` 那套组出来的代码很难调试）；
其二，**单向锁定**（用了就回不去）。

**效益**：对本书而言，LDMud 提供的是一个很重要的反例——
**§058 说「LPC 的类型是注解」，那是 MudOS 系的事实，不是 LPC 的本质。**
同一个语言家族里，有一支把类型、结构、联集、协程全部做进去了。

> 💡 君之一席话
> **当你发现自己一直在手写状态机，那不是纪律问题，是语言缺了一个特性**——LDMud 的协程与 §044 那条 `input_to` 接力，是同一个问题的两个时代的答案。

> 🔍 老手视角──真正的门道
> `lambda(({'x}), ({#'environment, 'x}))` 这种「用数组表示代码」的设计，威力和危险是同一件事：**它让代码可以被程序产生**，于是你能写出组出查找、组出规则、组出行为的 mudlib；而代价是**堆栈追踪失去意义**——出错时你看到的是一个被组出来的匿名 closure，没有文件名、没有行号、没有作者。这个取舍在现代生态里到处都是：ORM 组出的 SQL、串行化器产生的类别、装饰器包出来的函数、Proxy 拦截出来的对象。它们都能大幅减少样板，也都会在出事时让你面对一段没有出处的代码。老手用这类机制时会加一件事：**让产生出来的东西带着它的来源**——组 SQL 时附注解、产生类别时记下产生器、动态注册时记下注册点。可落地的做法：任何「代码由程序产生」的地方，**在产物里留一个指回产生处的字符串**。它几乎不花成本，而它决定了三个月后那个错误是十分钟还是两天。

## 067　LDMud 的 driver 野心 — 把 efun 的实作交给 mudlib

**标签**：`#driver_hook` `#ERQ` `#compat模式` `#Python` `#权力下放`
**证据等级**：🟡 上游 `ldmud/doc/concepts/`（`hooks`、`erq`、`native`、`python`）与 `doc/hook/`

**起源**：§066 讲的是 LDMud 在语言上的野心。
这一节讲它在 driver 架构上的——而它比语言那一半更激进。

**技术内核**：

### ① driver hook — 把硬编行为搬进 mudlib

> To allow a greater flexibility of the muds, the gamedrivers since 3.2.1
> **moved several once hardcoded 'underground' activities from the driver
> into the mudlib.**

机制是 `set_driver_hook(编号, 值)`（特权 efun），
编号的符号名定义在 `/sys/driverhooks.h`。**30 个以上的 hook**：

| 分类 | hook |
|------|------|
| **★ efun 的实作** | **`H_MOVE_OBJECT0` / `H_MOVE_OBJECT1`——强制性，用来实作 efun `move_object()`** |
| 身分 | `H_LOAD_UIDS` `H_CLONE_UIDS` `H_LWOBJECT_UIDS`（强制） |
| 生命周期 | `H_CREATE_OB` `H_CREATE_CLONE` `H_CREATE_SUPER` `H_CREATE_LWOBJECT`（＋`_COPY` / `_RESTORE`）`H_RESET` `H_CLEAN_UP` |
| 指令处理 | `H_COMMAND` `H_MODIFY_COMMAND` `H_MODIFY_COMMAND_FNAME` `H_NOTIFY_FAIL` `H_SEND_NOTIFY_FAIL` `H_DEFAULT_METHOD` |
| 编译 | `H_INCLUDE_DIRS` `H_AUTO_INCLUDE` `H_AUTO_INCLUDE_BLOCK` `H_AUTO_INCLUDE_EXPRESSION` `H_FILE_ENCODING` `H_REGEXP_PACKAGE` |
| 连接 | `H_TELNET_NEG` `H_NO_ECHO` `H_NO_IPC_SLOT` `H_PRINT_PROMPT` `H_DEFAULT_PROMPT` `H_MSG_DISCARDED` |
| 外部进程 | `H_ERQ_STOP` |

**第一列是重点，而且它很不寻常：**

> `H_MOVE_OBJECT0` / `H_MOVE_OBJECT1` are **mandatory hooks to implement
> the efun `void move_object()`**.

**`move_object()` 是一个 efun，但它的实作在 mudlib 里。**

在 MudOS／FluffOS 的世界观里这不成立——efun 是 driver 的 C++ 函数（§036）。
LDMud 把「把对象从 A 搬到 B」这件事判定为**游戏政策而不是引擎机制**，
于是 driver 只保留名字，行为交给上层。

而且——**hook 的值可以是 unbound lambda closure**（§066）。
**两套机制在这里合流：closure 让 mudlib 可以把「一段行为」当值传给 driver。**

这条路线和 DGD 的「把所有游戏导向功能拿掉」（§064）方向一致，
但手段不同：**DGD 是删掉，LDMud 是留下名字、外包实作。**

### ② ERQ — 一个 driver 外的协处理进程

LPMud 早期用了两个外部程序：`hname`（解析 IP 成主机名）与 `indent`（排版 LPC）。
3.2.1@61 把它们统一成 **ERQ（External Request Demon）**。

| 面向 | 说明 |
|------|------|
| 启动 | driver fork 出 `BINDIR/erq --forked …`，经 AF_UNIX socket 走 stdin/stdout |
| 握手 | erq 启动成功要**写回一个字符 `'1'`** |
| 运行期替换 | `attach_erq_demon(某个交互对象)`——**把连接从那个对象手上夺走**，当成新的 erq 信道 |
| 扩充 | 可挂任意功能（`--execdir` 指定可调用的运行档目录） |

**设计意图很明确：把「会阻塞的事」赶出主行程。**
LPC 是单线程事件循环（§037），一次 DNS 查找就能让整台 mud 卡住。
ERQ 是 1990 年代版本的「工作行程」。

文档里还留了一句很诚实的话：

> **Unfortunately it was never documented by Amylaar, so the information
> presented here had to be reverse engineered from the sources —
> better take it with a grain of salt.**

**官方文档承认自己是逆向出来的。** 这正是本书第一篇在讲的那件事——
连 driver 的维护者都得对自己的前任做逆向工程，
而且他**标了证据等级**（“take it with a grain of salt”）。

### ③ compat / native — driver 有「模式」这个概念

> During the evolution of LPMud there has been a hiatus as **the old driver
> became too restricting**: it did a lot of things the mudlib could do better
> or completely different. Removing these things from the driver weren't a
> problem, **but to keep compatible with the existing mudlibs (namely the
> well-known 2.4.5 lib), it was possible to undo these changes.**

演化路径：

```
运行期选项  →  编译期 compat / native 两种模式
            →  3.2.1 起：差异逐步移进 mudlib（用 driver hook）
            →  3.2.7：native 模式消失，只剩 plain 与 compat
            →  3.2.9：模式可用命令行选项指定
            →  目标：modeless driver
```

**这是一份「如何拆掉兼容性包袱」的实作路线图**，而且它走了十几年。

对照 §035 的 FluffOS：它选择**永久保留**兼容性
（`old range behavior`、`old type behavior` 这些旗标，附录 E.4.5）。
**LDMud 选择把兼容性逐步转移到 mudlib，然后让 driver 恢复无模式。**

**两种都是合理的策略，差别在谁承担转换成本**：
FluffOS 让 driver 永远背着；LDMud 让 mudlib 分阶段接手。

### ④ Python 扩充 — 运行期注册 efun

最新的一项，也是最能说明 LDMud 性格的：

```python
# 启动脚本，在 master 对象加载之前运行
import ldmud
ldmud.register_efun("my_efun", my_python_function)
```

> If the Python function has **type annotations** for its arguments and
> return value, **the type is checked at compile and runtime.**
> Union types can be specified as tuples of types.

**用 Python 写 efun，而且 Python 的类型注解会被 LPC 编译器拿去做类型检查。**

对照 §047：MudOS 的能力面是**编译期**用 `#define` 决定的，
§048 整节在讲那个决定的三十年后果。
**LDMud 的答案是把能力面变成运行期可注册的。**

**解决的痛点**：这四项合起来解的是同一个问题——
**driver 不该替 mudlib 做决定。**

| 曾经硬编在 driver 里的东西 | LDMud 的处置 |
|--------------------------|-------------|
| `move_object` 的行为 | → `H_MOVE_OBJECT0/1` 交给 mudlib |
| uid 怎么决定 | → `H_LOAD_UIDS` 等三个 hook |
| include 路径、文件编码、regexp 引擎 | → hook |
| telnet 协商 | → `H_TELNET_NEG` |
| compat 与 native 的差异 | → 逐步移进 mudlib |
| 有哪些 efun | → **Python 运行期注册** |

**这条线的终点是一个几乎没有政策的 driver**——
和 DGD 的目标一致（§064），只是 DGD 用「重写并删掉」达成，
LDMud 用「留下接口并外包」达成。

**踩过的坑（可推论的）**：把 efun 的实作交给 mudlib 有一个必然代价——
**强制性 hook**。文档明说 `H_MOVE_OBJECT0/1` 与三个 uid hook 是 mandatory：
**没设就不能跑。**
于是 LDMud 的 mudlib 有一个 MudOS 系没有的开机义务：
**在任何东西能动之前，先把 driver 的空缺填满。**

这是「权力下放」的隐藏成本——**下放的不只是权力，还有责任**。

**优点 / 罩门**：优点是弹性极高，且**兼容性可以被逐步偿还**而不是永远背着。
罩门是**入门门槛**：一个新 mudlib 要先实作一堆 hook 才能开机，
而 MudOS 系拿一份现成 lib 就能跑。
§064 说 DGD 的极小内核让「拿一份 mudlib 开站」的人门槛更高——
**LDMud 走同一条路，就付同一种代价。**

**效益**：对本书而言，这一节补完了「driver 该保留多少权力」这条光谱：

```
权力全在 driver ←─────────────────────────────→ 权力全在 mudlib
   （没有这一端）
        MudOS/FluffOS          CD            LDMud        DGD
        能力面极宽，          为单一世界      名字留下，    重写并删掉
        政策靠 apply 外包      量身决定       实作外包      游戏导向功能
```

**四支的位置不同，但方向一致：三十年来，driver 一直在往右移。**

> 💡 君之一席话
> **把权力下放给上层，同时下放的是责任**——一个什么都不决定的引擎，换来的是每个用户都必须先做完一堆决定才能开机。

> 🔍 老手视角──真正的门道
> `H_MOVE_OBJECT0` 这种「efun 的实作在上层」的设计，本质上是**依赖反转**（dependency inversion）用在引擎边界上：driver 定义接口，mudlib 提供实作，driver 调用自己不认识的代码。它的好处人人都懂，而它的代价很少被诚实讨论——**启动顺序变成一个必须被设计的东西**。当引擎在启动时要调用上层提供的实作，「谁先准备好」就成了一个真实的问题，而这正是 §061 那个 `valid_write` 竞态的同一种病（安全检查依赖一个还没加载的模块）。老手在做依赖反转时会同时做两件事：**明确定义「未就绪」的行为**，以及**在启动时检查所有必填的实作是否到齐**——LDMud 把后者做成了「mandatory hook，没设就不能跑」，这是对的。可落地的做法：任何靠上层注入实作的框架，**在启动完成前做一次完整性检查并明确失败**，比在第一次调用时得到 null 好上一个数量级。

## 068　DGD 的实作决断 — 轻量对象其实是一个数组

**标签**：`#DGD` `#kfun` `#轻量对象` `#builtin类型` `#快照迁移`
**证据等级**：🟡 上游 `dworkin/dgd`（`doc/builtin.md`、`README.md`、`src/kfun/`）

**起源**：§064 列了 DGD 的五项创新，但那是**功能清单**。
这一节看它的**实作**——因为 DGD 的实作方式本身就在说明它的世界观。

**技术内核**：

### ① kfun — efun 的另一个名字，与一套极简的定义方式

DGD 不叫 efun，叫 **kfun**（kernel function）。
定义方式是一组宏，同一个文件编译两次（`FUNCDEF` 有无定义）：

```c
# ifdef FUNCDEF
FUNCDEF("new_type", kf_new_type, pt_new_type, 0)
# else
char pt_new_type[] = { C_TYPECHECKED | C_STATIC, 0, 0, 0, 6, T_OBJECT };

int kf_new_type(Frame *f, int n, KFun *kf) { … }
# endif
```

注意 `pt_new_type` 那一行：**函数原型被编码成一个字节数组**——
旗标（是否类型检查、是否 static）、参数个数、各参数类型。

**整个 kfun 表就是 `src/kfun/` 底下几个文件**
（`std.cpp`、`math.cpp`、`file.cpp`、`extra.cpp`、`builtin.cpp`、`table.cpp`）。
对照 FluffOS 的 451 篇 efun 文档（附录 E.2）——**DGD 的内核小了一个数量级**，
这是 §064 那句「把所有游戏导向功能拿掉」的具体长相。

而且 kfun 可以**模块化插件**：

```
modules = ([ "kfun_module" : "module config" ]);
```

JIT 本身就是这样挂上去的（`lpc-ext` 是独立仓库）。
**内核极小 + 可插件 = DGD 的整个策略。**

### ② ★ 轻量对象的真面目：一个带标头的数组

`doc/builtin.md` 揭露了一件很有意思的实作细节：

> Ordinary light-weight objects will have **an object as the first element of
> their array**. For builtin types, the first element must be **an integer,
> the type number**; the second element is reserved and must be initialized
> to `Float` 0.0.

**LWO 的表示就是一个 LPC 数组**，前几格是标头：

```
LWO = ({
   [0]  对象（一般 LWO）或类型编号（builtin 类型）
   [1]  保留：必须是 Float 0.0
   [2]  建议：版本号         ← 给你之后改格式时做转换用
   [3+] 任意 LPC 数据
})
```

**第三格那个「建议放版本号」特别值得记**：
官方文档直接建议你在自订类型里**预留版本字段**，
「以防你之后改变类型的建构方式、想转换旧的实例」。

> **这是一个在数据结构层级就内置了迁移意识的设计。**
> 对照 §052 那棵无 schema 的属性树——那里连「有哪些字段」都没人知道，
> 更不用说版本。两种数据观的距离，大约就是二十年。

### ③ builtin type — 用 LWO 扩充类型系统

因为 LWO 就是带标头的数组，**添加一个「内置类型」就变得很便宜**：
在 `object.h` 保留一个编号、在 `Object::builtinName()` 给它名字，
再写一个产生它的 kfun。名字前缀由 `BIPREFIX` 决定（缺省 `/builtin`）。

编译期它的节点修饰词是 `T_CLASS`，类别字符串由 `builtinName()` 产生——
**所以类型系统看得见它。**

缺省这些类型**没有可从 LPC 调用的函数**、
不能被 `function_object()` 探测、`status()` 也查不到它们的信息；
要有的话得改 `Frame::call()`、`kf_function_object()`、`kf_status()`。

**这段文档本身就是 DGD 的性格**：它不提供一个「扩充类型」的高端 API，
它告诉你去改哪四个函数。**内核极小的代价是扩充要动内核。**

### ④ 快照迁移 = 数据库迁移

§064 说 DGD「整个世界是数据库」。这句话的最强证据在 README 的升级说明：

> DGD 1.7 is backward compatible with snapshots from **DGD 1.5.9 and later,
> only**. To upgrade to DGD 1.7, first upgrade to the latest 1.5.x version,
> **recompile all objects, and create a non-incremental snapshot.**

拆开来看：

| 步骤 | 这在数据库世界叫什么 |
|------|-------------------|
| 先升到最新的 1.5.x | **中继版本升级**（不能跳版） |
| 重编所有对象 | **重建索引／重写数据** |
| 产生一个非增量快照 | **完整备份**（不能用增量链） |
| 然后才升到 1.7 | 目标版本升级 |

**这是一份标准的数据库迁移进程，出现在一个 MUD driver 的 README 里。**

对照 MudOS 系：升级 driver 就是换一个运行档，玩家存盘是一堆 `.o` 文本档，
没有版本、没有迁移、没有兼容性声明（§052 那个「缺件表现成什么都没有」）。

**两种世界观的差别在这里完全暴露：
DGD 把世界当成必须被完整保存的状态，所以升级是一次迁移；
MudOS 把世界当成可以重来的东西，所以升级只是换运行档。**

**解决的痛点**：DGD 解的是「持久性」，而它为此付出的是**内核的复杂度**。
快照、增量快照、跨版本兼容、原子函数的回卷——
这些都是数据库等级的问题，而它把它们放进了一个语言运行环境里。

**踩过的坑（生态层面，可从文献推得）**：
「1.7 只兼容 1.5.9 以后的快照」这句话翻译过来是——
**如果你的 mud 停在 1.5.9 之前，你的世界搬不过来。**
持久化的代价是**你的数据成为一种必须被维护的资产**；
而 MudOS 系的 mud 因为本来就没真的保存世界，反而没有这个问题。

**这是「更好的技术带来新的义务」的典型例子。**

**优点 / 罩门**：优点是 DGD 的每一个设计都彼此咬合——
LWO 是数组，所以 builtin 类型便宜；内核小，所以 kfun 可插件；
世界是数据库，所以有快照与原子函数。**它是一个有整体构思的系统。**
罩门是**它几乎不可能被渐进采用**：你不能「稍微用一点 DGD」，
它的世界观是全有全无的。

**效益**：对本书而言，DGD 提供了一面镜子。
本书从第一篇到第七篇处理的所有问题——
协议没有规格、数据没有 schema、缺件表现成静默、
版本无法辨识、状态随时可能不一致——
**在 DGD 的世界观里，其中一半根本不会发生。**

不是因为 DGD 比较高明，是因为**它从一开始就把「状态是有价值且必须被保存的」
当成前提**，而 MudOS 系（以及长在它上面的整个中文 MUD 生态）没有。

> 💡 君之一席话
> **当升级一个系统需要写一份迁移进程，那代表它真的保存了东西**——没有迁移进程的系统，多半不是兼容性做得好，是根本没有什么值得搬过去。

> 🔍 老手视角──真正的门道
> `doc/builtin.md` 建议在自订类型的第三格放版本号，这件事的份量比它的篇幅大得多：**它是在数据结构诞生的那一刻就替它的未来留位置。** 多数系统的版本字段是事后补的——先有 v1（没有版本字段），发现要改的时候才发现「我没办法区分新旧」，于是只能靠猜（长度、字段存在与否、magic number）。这件事的成本极不对称：**事前留一个字段几乎免费，事后补则需要一套启发式侦测**。本书 §附录 F 那个映像格式（`format: 1`）之所以第一个字段就是版本，用的是同一个道理。老手在设计任何会被写进磁盘、送上网络、或存进数据库的结构时，第一个字段永远是版本——**即使当下只有一个版本，而且你确定不会改**。你不会确定，而那个字段是你唯一的退路。

## 069　CD 的节制 — 以及三份跨越三十四年没改过的文档

**标签**：`#CD` `#节制` `#文献化石` `#单一用户` `#设计自由度`
**证据等级**：🟡 上游 `cotillion/cd-gamedriver`（原代码树、`doc/`）＋ 🟢 与 FluffOS 封存的逐段比对

**起源**：§063 拆了 CD 的四个独特设计。这一节看它的**另一面**——
**它没有做的事**，以及为什么那也是一种设计。

**技术内核**：把 CD 的原代码树摊开，会发现它出奇地小而且**平**。

```
array.c  backend.c  bibopmalloc.c  call_out.c  comm1.c  debug.c  ed.c
func_spec.c  genfkntab.c  hash.c  hname.c  interface.c  interpret.c
json.c  lex.c  main.c  make_table.c  mapping.c  memory.c  mstring.c
mudstat.c  ndesc.c  net.c  nqueue.c  object.c  otable.c  parse.c
port.c  random.c  regexp.c  signals.c  simul_efun.c  simulate.c
siphash.c  sprintf.c  stdmalloc.c  super_snoop.c  tcpsvc.c  telnet.c
udpsvc.c  wildmat.c
```

**四十几个 `.c`，全部在根目录，没有子系统分层。**
对照 FluffOS 的 `src/`：`vm/`、`compiler/`、`net/`、`packages/`、
`base/`、`thirdparty/`、`wasm/`、`tools/`……

**这不是「比较旧」，是「比较小」。**

**四件 CD 没有做、而其他三支都做了的事：**

| 其他人做了 | CD 没做 | 为什么可以不做 |
|-----------|--------|--------------|
| 套件系统（MudOS 十几个 package，§047） | 没有——功能就是编进去或不编 | **只有一个用户，不需要让别人选** |
| 兼容模式（LDMud 的 compat/native，§067） | 没有 | **只有一份 mudlib，不需要兼容任何人** |
| 大量可调参数（FluffOS 的 config，附录 E.4） | 命令行旗标，十个左右 | 同上 |
| 语言扩充（LDMud 的 struct/union/coroutine） | 没有——LPC 大致停在 3.0 的形状 | **Genesis 不需要** |

**「只有一个用户」是 CD 全部设计自由度的来源。**

一个服务单一世界的 driver 可以：
- 直接改行为，不必声明兼容性；
- 不必猜别人要什么，只要问 Genesis 的管理者；
- 不必做设置系统，因为只有一组设置；
- **可以把 intermud 做进 driver**（§063）——因为只有一个 mudlib 需要它。

**这是一种被低估的架构优势**：本书 §043 讲 ZJMUD 的协议为什么停在第 0 代时
说过「技术上更好的方案输给了组织成本更低的方案」；
**CD 是反过来的例子——组织成本趋近于零时，可以做出很干净的决定。**

### ★ 三份跨越分家的文档化石

§065 已经记过一份（`CREDITS`）。把三份放在一起，
会得到一张**用文档画出来的分家图**：

| 文档 | 在 CD | 在 FluffOS | 状态 |
|------|-------|-----------|------|
| **`CREDITS`** | `doc/CREDITS` | `docs/archive/Credits.LPmud` | **共同开头，1991 年后各自往下长**（§065） |
| **`STACKMACHINE`** | `doc/STACKMACHINE` | `docs/driver/stackmachine.md` | **七个章节、内容、顺序完全相同**——只有 Markdown 排版不同 |
| **TMI-2 档头** | —（CD 不用 TMI mudlib） | 🟢 本项目 15/17 份封存带着它 | 只存在于 MudOS 那一支（§049） |

**第二列是新发现，而且它比第一列更说明问题。**

`STACKMACHINE` 那份文档——全大写开头、两个堆栈、frame pointer 图、
`F_FUNCTION` / `F_SSCANF` / `F_CALL_OTHER` / `F_AGGREGATE` / `F_CATCH` / `F_RETURN`
七个章节——**在 1991 年分家的两侧，三十四年后仍然逐段对应**。

FluffOS 那一侧做的唯一改动是把 `1. CALLING LOCAL FUNCTIONS.`
改成 Markdown 的 `## CALLING LOCAL FUNCTIONS.`。

> **这代表什么？** 代表 §037 那台虚拟机——双堆栈、frame pointer 索引、
> 参数自动补齐、`setjmp`/`longjmp` 的 `catch`——
> **不是 FluffOS 的设计，也不是 MudOS 的设计，是 1989 年 Lars 的设计**，
> 而两条在 1991 年分开的血脉，各自演化三十四年，**都没有动它**。

本书 §037 说过「活得最久的设计通常不是最先进的那个，
是最没有东西可以过时的那个」——
**这份文档就是那句话的证据：它连文本都没有需要更新的地方。**

**解决的痛点**：CD 不解通用性问题，它解的是**一个世界的持续营运问题**。
1989 年开的 Genesis 至今还在跑，这件事本身就是它的规格书。

**踩过的坑（结构性的）**：CD 的节制有一个必然后果——
**它几乎没有外部生态**。撰写当下 32 颗星、174 个 commit。
本项目 17 份封存没有一份是 CD 系的（§063），
`mudlibs.fluffos.info` 那 199 份也没有。

**「只有一个用户」是设计自由度的来源，也是生态规模的天花板。**
两者是同一件事的两面，不能只要一边。

**优点 / 罩门**：优点是**没有妥协**——每一个决定都可以为 Genesis 优化。
罩门是**没有备援**：driver 与世界互为存在理由，
任何一边消失，另一边就失去意义。

**效益**：对本书而言，CD 的价值有两层。
技术上它是 §063 那些「相反选择」的来源；
方法论上它示范了**文献比对可以定位分家点**——
不需要任何人的回忆，把两份同源文档并排，
共同前缀的结尾就是分家的那一刻。

> 💡 君之一席话
> **只服务一个用户的系统可以做出所有其他系统做不到的干净决定**——代价是它的价值与那个用户完全绑定，而这通常不是缺点，是一个被诚实接受的前提。

> 🔍 老手视角──真正的门道
> 「一份三十四年没改的设计文档」这件事，比它听起来更值得思考。多数人会把它解释成「这个设计很好」，但更准确的解释是**「这个设计没有需要被重新决定的东西」**——双堆栈机不依赖任何一代硬件、任何一种操作系统、任何一种语言潮流，所以没有任何外部变化能逼它改。这给了一个很实用的判准：**看一个设计会不会过时，不要看它有多先进，看它依赖了多少会变的东西。** 依赖硬件特性的会过时，依赖当代最佳实务的会过时，依赖某个生态的会过时；而只依赖「有一块内存可以当堆栈用」的，不会。可落地的做法：做长期设计时，把它的假设列出来，然后对每一条问「这个假设在十年后还成立吗」——列不出假设的设计，通常假设了很多；假设里有一半是关于当前技术环境的，那它的寿命就是那个环境的寿命。

## 070　四种扩充点 — 一个综合分析

**标签**：`#扩充点` `#设计空间` `#权力分配` `#综合` `#收束`
**证据等级**：🟡 四支上游的交叉比对 ＋ 🟢 本项目对 FluffOS 的实测

**起源**：§066–§069 分别解剖了四支。这一节把它们的**同一个机制**放在一起——
因为四支 driver 都要解决同一个问题：

> **driver 运行到一半，需要上层做一个决定。怎么问？**

四支给了四种答案，而**每一种都反映了它对「权力该在哪」的判断**。

**技术内核**：四种扩充点的机制比较。

| | **MudOS / FluffOS**<br>`apply` | **CD**<br>`hook` | **LDMud**<br>`driver hook` | **DGD**<br>`kfun module` |
|---|---|---|---|---|
| **绑定方式** | 字符串函数名，driver 直接 `apply()` | 名字集中在 `master.n`，编译成 `M_*` 常数 | **运行期 `set_driver_hook(编号, 值)`** | 编译期／设置档加载模块 |
| **值是什么** | mudlib 里的一个函数 | 同左 | **可以是 unbound lambda closure、lfun closure 或字符串** | 一个 C++ 实作的 kfun 表 |
| **名字打错会怎样** | **静默略过**（§036） | driver 端不会错（用常数）；mudlib 端仍是惯例 | **编号错 = 设置失败，可侦测** | 链接失败 |
| **强制性** | 全部可选 | 未定义回传 0 | **部分 mandatory（没设不能跑）** | — |
| **可以在运行期改吗** | ❌（改了要重载对象） | ❌ | **✅ 随时可换** | ❌ |
| **能取代 efun 吗** | ❌ | ❌ | **✅（`H_MOVE_OBJECT0`）** | ✅（模块即 kfun） |
| **数量** | **69 个** | 12 个 | **30+ 个** | 不限（模块） |
| **权力位置** | driver 保留机制，政策外包 | driver 保留较多 | **driver 几乎只保留名字** | **内核极小，其余全插件** |

**四种答案排在同一条轴上：**

```
driver 决定一切  ←────────────────────────────────→  mudlib 决定一切

              CD          MudOS/FluffOS       LDMud        DGD
          （为单一世界      （能力面宽，      （名字留下，   （内核极小，
            量身决定）      政策靠 apply）     实作外包）    其余插件）
```

**三个从这张表读得出来的通则：**

### ① 「静默略过」是 apply 模型的原罪

FluffOS 的 69 个 apply 全部是可选的、靠字符串名绑定、找不到就当没有。
这在 §036 被列为「apply 最需要创建的直觉」，
而它在本书里造成的实际后果不只一次：
§038 的 preload 静默失败、§041 的三个 daemon 不存在、
以及 §046 那张「静默失败集中在哪几站」的表。

**CD 用常数解掉了一半**（driver 端不会拼错），
**LDMud 用「mandatory + 运行期设置」解掉了另一半**（没设就开不了机）。

**同一个问题，两种解法，而 MudOS 系两种都没采用**——
因为它的优先序是兼容性（§035），而收紧 apply 会弄坏既有 mudlib。

### ② 运行期可换 = 扩充点变成了状态

LDMud 的 `set_driver_hook()` 是四者中唯一可以在运行期改的。
**这带来弹性，也带来一个新的问题类别**：
「这台 mud 现在的 `H_MODIFY_COMMAND` 是什么」变成一个**运行期状态**，
而不是原代码里的一个事实。

§060 那个「程序与数据可以独立地过期」的问题，在这里多了一层：
**连 driver 的行为都可以在运行期被换掉。**

**弹性与可诊断性的交换，在这里是一比一的。**

### ③ 扩充点的数量反映的是「driver 想保留多少」

```
CD 12 个 hook   →  driver 保留最多决定权
FluffOS 69 个   →  政策几乎全外包，但机制自己做
LDMud 30+ 且含 efun 实作  →  连机制都可以外包
DGD 模块化 kfun →  内核只留语言与持久化
```

**注意 CD 的 12 个是最少的，但它不是「最不可扩充」——
它是「最不需要扩充」**，因为它只服务一个 mudlib（§069）。

**这一点很容易被误读**：扩充点多寡不是能力指针，
是**「这个系统预期要服务多少种不同需求」的指针**。

**解决的痛点**：这一节解的是选型与设计上的一个常见混淆——
**把「可扩充性」当成一个单一维度的好东西。**

实际上它至少有四个维度，而且彼此冲突：

| 维度 | 提高它的代价 |
|------|------------|
| **扩充点数量** | 每一个都是要维护的接口；上层要学的东西变多 |
| **绑定时机**（编译期→运行期） | 越晚绑越弹性，**也越难诊断** |
| **可取代的深度**（政策→机制→内核） | 越深越强大，**上层的开机义务越重** |
| **失败的可见性** | 提高它会弄坏既有的、靠「静默略过」运作的东西 |

**四支 driver 各自在这四个维度上选了不同的点，而没有一个是全对的。**

**踩过的坑（本项目，回头看）**：本书 §046 那张「静默失败集中在哪几站」的表
现在可以更精确地解释了——
**那些站全部落在 apply 模型的责任范围内**：
mudlib apply 名字打错、preload 对象加载失败、WASM 接缝的重入与状态判断。

**如果本项目的 driver 是 LDMud，第一类与第二类会在开机时就失败**
（mandatory hook、可侦测的设置失败）；
**如果是 DGD，第三类的一部分会被原子函数挡掉**（§064）。

**这不是说本项目选错了 driver**——选 FluffOS 是因为 17 份封存全是 MudOS 系（§050），
而且只有它有 WebAssembly build（§032）。
**这是说：本项目花在「静默失败」上的时间，有一部分是 driver 选型的必然成本，
而不是工程能力问题。**

**知道哪些成本是选型带来的，才知道哪些值得优化、哪些只能接受。**

**优点 / 罩门**：这种横向综合的优点是它把「可扩充性」拆成了可讨论的维度。
罩门是它需要四份一手材料，而多数人只会读一份。

**效益**：本书第八篇到第十一篇的收束——

> 第八篇问：**连接的另一端是什么？**
> 第九篇问：**引擎／mudlib／客户端各自把知识放在哪一层？**
> 第十篇问：**这个设计是本质，还是某人在 1992 年的一个决定？**
> 第十一篇问：**四支给了四种答案，那条轴线本身是什么？**

答案是这一节开头那句话：**driver 该保留多少决定权。**

而四支三十七年的演化方向是一致的——**往外包移**。
MudOS 外包政策、LDMud 外包实作、DGD 外包一切非内核。
**没有任何一支往回走。**

这件事对任何在做平台、引擎、框架的人都有意义：
**你今天保留的每一个决定，都是未来某个用户要绕过的东西。**

> 💡 君之一席话
> **可扩充性不是一个维度，是四个**——扩充点多少、什么时候绑、能取代到多深、失败看不看得见；四个一起看，才知道一个系统是灵活还是失控。

> 🔍 老手视角──真正的门道
> 四支 driver 三十七年一致往「权力外包」移动，这个方向性本身值得警惕地看待——**因为它有一个没有被说出来的终点：一个什么都不决定的引擎，等于把所有决定推给了一群比你更没有时间思考的人。** DGD 与 LDMud 的极小内核路线在技术上很漂亮，但它们的生态规模都远小于 MudOS 系，而原因之一就在这里：**大部分用户要的不是「我可以决定一切」，是「不必决定就能开始」。** 老手在设计平台时会刻意同时提供两层——**一组不需要任何决定就能跑起来的缺省，以及一条可以逐项接管的信道**（Rails 的 convention over configuration、Next.js 的缺省路由、Docker 的官方 image 都是这个形状）。可落地的判准：如果你的系统「必须先做完 N 个决定才能看到第一个结果」，那 N 就是你的入门门槛，而它与你的扩充性同样重要——**扩充性决定天花板，默认值决定有多少人走到天花板底下。**
