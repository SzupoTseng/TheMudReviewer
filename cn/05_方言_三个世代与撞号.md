# 第三篇　方言与兼容性

## 009　定义不等于使用 — 一份 header 骗走你两天

**标签**：`#方言` `#兼容性` `#统计方法` `#优先级` `#死定义`
**证据等级**：🟡 16 份 `zjmud.h` ＋ `.c` 使用统计

**起源**：手上有一个 mudlib 收藏，19 个项目、17 份 `include/zjmud.h`。要判断「客户端该支持多少 opcode」，第一反应是把所有 header 的定义取联集。

那个联集是 **101 个**。

如果照着做，会为了七十几个永远不会出现在线路上的 opcode 写处理器。

**技术内核**：正确的做法是**用 `.c` 的实际使用情形过滤 header 的定义**。一支脚本扫过所有 mudlib，结果是这样：

| mudlib | 定义 | 实际使用 | 落差 |
|--------|------|---------|------|
| nt7 | **102** | **16** | 86 个从未使用 |
| 大梦江湖（新协议） | 101 | **81** | 真正的扩充方言 |
| 谁与争锋、天涯二、四合一…（共 14 个） | 27 | 19–21 | 部分功能未开 |

**`nt7` 是最极端的案例**：它定义了 102 个 opcode，`.c` 里一个扩充码都没用。那份 header 是从别处拷贝过来的，等同一份许愿清单。

同样的现象也出现在 `LPMud-Name` 的 `zjmud.h`——里面有一大段被注解掉的扩充定义，形式完整、注解齐全，但全部处于停用状态。

**最终的真实数字**：

```
全收藏实际使用的不同 opcode：83 个
  ├─ 经典内核 27 个  ← 14 个 mudlib 共用，最大公因数
  └─ 扩充     61 个  ← 只有「大梦江湖」一个 mudlib 在用
```

**解决的痛点**：把「要支持多少」这个问题，从一个猜测变成一个可以数出来的数字。

**踩过的坑**：一开始只扫 header，得到「74 个缺口」的结论，差点就照着实作。是后来多问一句「这些真的有人在用吗」，才发现 nt7 那 86 个是死定义。

**这个检查的成本是一支脚本、十分钟。省下的是好几天。**

**优点 / 罩门**：使用频率统计的优点是**它直接给你实作优先级**。本项目扫出的分布极不均：

```
ZJOBLONG   (详情)      531 次
ZJOBACTS2  (动作列)    448 次
ZJSIZE     (字级)      336 次
ZJMENUF    (版面)      305 次
ZJURL      (链接)      302 次
ZJFORCECMD (代送指令)   98 次
...
ZJYESNO    (对话框)      0 次   ← 定义了但没人用
```

「详情＋动作列」占了绝对多数——那才是玩家 95% 时间看到的东西。而 NPC 对话框在该服务器一次都没用。

罩门是这个统计**只反映当下这批 mudlib**。新的服务器可能激活你判定为「没人用」的码，所以未知 opcode 的降级处理仍不可省。

**判读方法对照**：

| 方法 | 成本 | 准确度 | 风险 |
|------|------|--------|------|
| 只读 header | 最低 | 低 | 为死定义做白工 |
| **header ∩ `.c` 使用** | 低（一支脚本） | 高 | 只涵盖手上这批 mudlib |
| 实机抓包 | 中 | 最高 | 只涵盖触发到的功能 |

**效益**：实作范围从「101 个」收敛到「27 个内核 + 61 个扩充」，且扩充有明确的优先级。

> 💡 君之一席话
> **一份 header 告诉你作者曾经想做什么，一次 grep 告诉你他真正做了什么——中间的落差，就是你省下来的时间。**

> 🔍 老手视角──真正的门道
> 「定义了但没使用」在协议演化里几乎是常态，而不是例外。原因通常是三种：功能被砍、header 被拷贝、或某个分支版本才用得到。老手判断一个协议实作的优先级，永远是**先量频率再排工**——这和读 API 文档的直觉完全相反，文档会把所有端点平等呈现，但真实世界的流量分布几乎都是长尾。可落地的做法：面对任何「规格 vs 实作」的落差，写一支统计脚本比开三次会有效；而且这支脚本应该进版控，因为下次协议更新时，你要的是**差异**，不是重新数一遍。

## 010　撞号 — 为什么不能把所有方言合并成一张表

**标签**：`#方言` `#profile` `#撞号` `#静默错误` `#架构`
**证据等级**：🟡 两份 header 直接对照

**起源**：扩充方言做好之后，又发现第三套——指游 MUD 的 `ZY*` 系列（600–618）。顺手把它加进同一张 opcode 表。

然后一个检查脚本吐出了这个：

```
重复的 opcode： ['602', '603', '604', '605']
```

**技术内核**：这四个码在两个方言里意义**完全不同**：

| opcode | 大梦江湖 | 指游 |
|--------|----------|------|
| 602 | `DMZHUYET` 主页文本 | `ZYCHARHP` NPC 状态 |
| 603 | `DMZHUYETY` 主页文本 2 | `ZYFIGHTBTN` 战斗按钮 |
| 604 | `DMZHUJMQH` 判断界面 | `ZYHANDLERBTN` 操作面板 |
| 605 | `DMZHUJIU` 更改界面 | `ZYCLEARSCREEN` 清空主画面 |

而在 JavaScript 的对象字面量里，**后定义的键会静默覆盖前者**。合并表的那一刻，大梦江湖的四个主页 opcode 就已经坏了——

**不会报错、不会有警告、测试依然全绿。** 画面上的表现是「某些功能莫名其妙变成别的东西」。

**这是本项目架构层面最有价值的一次发现**：它证明了单一合并表在结构上就是错的。

**正确设计是分方言 profile**：

```javascript
export const PROFILES = {
  classic: { label: '经典 zjmud',      ext: {} },
  dmjh:    { label: '大梦江湖（新协议）', ext: DMJH },
  zymud:   { label: '指游 MUD（ZY）',    ext: ZYMUD },
}
```

由**握手字符串决定套用哪一套**（见 008）：

```
ver1.0:  / ver1.0,        → dmjh
version 1.0 key::         → zymud
```

**解决的痛点**：让同一个客户端安全地支持多个互相冲突的协议世代。

**踩过的坑**：发现撞号**纯属意外**——写了一个「列出所有 profile 中意义不同的 opcode」的诊断函数，本来只是想做个健康检查，结果它第一次运行就吐出四个。

于是这个函数被留了下来，并写成测试：

```javascript
test('602-605 在两个方言中意义不同，必须被隔离', () => {
  const ops = conflictingOpcodes().map((c) => c.op).sort();
  assert.deepEqual(ops, ['602', '603', '604', '605'],
    '已知冲突就是这四个；若多出来代表新加的方言撞号了');
});
```

**这条测试的价值不在守住现在，而在守住未来**——下次有人加第四个方言时，如果又撞号，测试会立刻爆掉并指出是哪一个码。

**优点 / 罩门**：profile 设计的优点是**冲突被结构性地消除**，而且添加方言只是加一张表。罩门是需要可靠的方言判别；判别错了，整套 opcode 表就错了。本项目的缓解措施是「没命中目前 profile 时，若该码在**所有** profile 中唯一，仍然采用」——让不冲突的码跨方言可用，冲突的码严格以目前 profile 为准。

**架构对照**：

| 设计 | 撞号时的行为 | 可测性 | 添加方言成本 |
|------|-------------|--------|-------------|
| **单一合并表** | 静默覆盖，无任何征兆 | 差 | 低，但会坏 |
| **分 profile**（本项目） | 隔离，且能列出冲突 | 好 | 加一张表 |
| 每方言一套解析器 | 不会撞 | 好 | 高，大量重复 |

**效益**：三个方言、89 个扩充 opcode、4 个撞号全部隔离，且经典 mudlib 的行为零退化（有专门的回归测试守住）。

> 💡 君之一席话
> **最危险的 bug 不会让你的程序崩溃，它会让你的程序安静地做另一件事——而合并命名空间，正是制造这种 bug 的标准工法。**

> 🔍 老手视角──真正的门道
> 撞号的根源是**协议演化时没有中央注册**：两个团队各自从 600 开始编号，谁也不知道对方。这在私有协议里极常见，解法从来不是「协调大家」（做不到），而是**在客户端承认多重宇宙的存在**。真正的门道在于：一旦你决定支持多方言，就必须同时提供三件事——**判别机制**（怎么知道现在是哪个）、**隔离机制**（冲突时谁赢）、**诊断机制**（能列出所有冲突）。少了第三件，你会在半年后加第四个方言时重蹈覆辙。可落地的做法：把「列出跨命名空间冲突」写成一个导出函数并纳入测试，成本二十行，回报是每次扩充都自动体检。

## 011　变长 opcode — 一个 `1085` 逼出的消歧义规则

**标签**：`#opcode` `#解析` `#消歧义` `#边界条件` `#回归测试`
**证据等级**：🟡 `others/zjmud.h`

**起源**：指游方言的 header 里藏着一行：

```c
#define ZYMAP   ESA + "1085"   //地图查看框
```

**四个字符。** 整套协议只有这一个。

**技术内核**：解析器原本固定取 3 个字符。碰到 `ESC1085地图内容` 会解成 opcode `108` 加上 payload `5地图内容`——`108` 不在任何表里，于是整行降级成一般消息，把控制字符连同内容印在画面上。

改成「取 4 个字符」更糟——`ESC004` 后面接「5 个人站在这里」会被读成 `ESC0045`。

**安全的消歧义规则**是：

```
1. 先取 3 字符
2. 只有在「4 字符版本认得、而 3 字符版本不认得」时，才改用 4 字符
```

```javascript
const three = line.slice(1, 4);
if (/^[0-9a-z]{3}$/i.test(three)) {
  const four = line.slice(1, 5);
  if (/^[0-9a-z]{4}$/i.test(four) && isKnownOpcode(four) && !isKnownOpcode(three)) {
    return { op: four, payload: line.slice(5) };
  }
  return { op: three, payload: line.slice(4) };
}
```

这个规则的关键在**两个条件都要成立**：4 字符的认得、3 字符的不认得。少了后者，`ESC0045…` 就会被误判。

**解决的痛点**：在不破坏既有 99% 情况的前提下，支持一个例外。

**踩过的坑**：这一节的真正教训不是「支持四字符」，而是**原本的正则写错了两次**：

```javascript
/^\d{3}$/       // 第一版：只认数字 → 10a、2k1 全部失效
/^[0-9a-z]{3}$/ // 第二版：认英数 → 1085 仍失效
```

扩充方言里有 `10a`、`11a`、`2k1`–`2k4` 这六个**带字母**的 opcode。第一版正则会把它们全部当成一般消息。

**优点 / 罩门**：这个规则的优点是**向后完全兼容**——所有既有的三字符码行为不变。罩门是它依赖 `isKnownOpcode()`，也就是**依赖表的完整性**。如果某天出现一个没登记的四字符码，它会被解成三字符加残字。

因此配套的防线是：**未知 opcode 一律降级成一般消息并保留完整原文**，同时在事件上标记 `unknownOpcode`，方便日后补表。**绝不静默丢弃**——那会让新 mudlib 的内容凭空消失且无从察觉。

**边界案例对照**：

| 输入 | 期望 | 为什么 |
|------|------|--------|
| `ESC1085地图` | op=`1085` | 4 认得、3 不认得 |
| `ESC0045 个人…` | op=`004`，payload=`5 个人…` | 3 认得，不可误判 |
| `ESC2k1内容` | op=`2k1` | 带字母的三字符码 |
| `ESC[31m红` | op=`null` | ANSI 样式码不可被误判成 opcode |
| `ESCzzz某些` | op=`null`，标记 unknown | 降级但保留原文 |

这五条全部写成测试，因为每一条都代表一种曾经或可能的解错。

**效益**：一条十行的消歧义规则，让解析器同时容纳 3 字符与 4 字符 opcode，且零退化。

> 💡 君之一席话
> **支持例外的正确姿势，不是放宽通则，而是替例外加一道「只有它成立、通则不成立」的窄门——放宽通则会伤到所有人。**

> 🔍 老手视角──真正的门道
> 这类「格式突然多一个字符」的问题，在协议演化里有个标准诊断法：**看它是不是唯一的例外**。如果只有一个，用窄门规则；如果超过三个，代表格式本身已经变了，该考虑版本化（例如用握手字符串切换解析规则）。本项目只有 `1085` 一个，所以窄门是对的选择。老手还会多做一件事：**把消歧义规则的每一个分支都写成测试，包括「不该触发」的那些**——因为这种规则的 bug 几乎都出在误触发，而不是漏触发。可落地的提醒：任何带「只有在…才…」的条件判断，测试至少要有两条，一条证明它会生效，一条证明它不会乱生效。
