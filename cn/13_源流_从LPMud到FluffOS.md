# 第八篇　源流：连接的另一端是什么

> 前七篇都站在**客户端**这一侧：字节进来、opcode 解析、画面更新。
> 这一篇把镜头转过去——**送出那些字节的东西，到底是什么？**
>
> 答案是一台 1989 年设计、2026 年还在维护的虚拟机。
> 本书那 116 个 opcode 不是它的协议，它甚至不知道 opcode 存在——
> 这件事听起来很怪，但它解释了本书前面一半的谜题：
> 为什么协议可以那么随便、为什么会撞号、为什么换了 driver 协议还在。

## 033　1989 年的那次分家 — driver 与 mudlib 为什么要拆开

**标签**：`#LPMud` `#架构史` `#虚拟机` `#关注点分离` `#热更新`
**证据等级**：🟡 上游一手史料（`fluffos/docs/archive/Credits.LPmud`）＋ 🟡 官方文档

**起源**：1989 年 4 月，瑞典查尔摩斯理工学院的 Lars Pensjö 写了一个 MUD 服务器。
他遇到的问题非常具体：**他想让别人来帮他盖世界，但他不想让别人碰 C 原代码。**

那个年代的 MUD 服务器（DikuMUD、AberMUD）都是把游戏内容编进 C 里的。
加一间房间要改 `.c`、重编译、踢掉所有在线玩家、重启。
一个十人团队要协作写一个世界，这条路走不通。

Lars 的解法是把服务器切成两半，这个切法后来定义了整个 LPMud 家族：

```
┌──────────────────────────────────────────────┐
│ mudlib —— 用 LPC 写的游戏框架                  │
│   房间、NPC、武器、战斗、登录流程、指令          │
│   ★ 没有编译步骤，改完存盘就能加载新版本         │
├──────────────────────────────────────────────┤
│ driver —— 用 C 写的运行引擎                    │
│   LPC 编译器 + 字节码虚拟机 + 网络 + efun     │
│   ★ 几年才换一次版本                           │
└──────────────────────────────────────────────┘
```

**技术内核**：这不是「加一层脚本」，而是**把整个游戏搬到脚本层**。
driver 里没有任何一行知道什么是「剑」或「客栈」；
mudlib 里没有任何一行知道什么是 socket 或 `malloc`。

`Credits.LPmud` 这份 30 行的文件，是 LPMud 现存最早的一手史料，
它记下了几个至今还在跑的决定：

| 一手纪录 | 今天的样子 |
|---------|-----------|
| 「Lennart Augustsson **说服我**去实作一个虚拟堆栈机的编译器。他也实作了内置的预处理器」 | §037 描述的双堆栈机，架构没变过 |
| 「shadow 这个想法是 John S. Price 从 Team Cthulhu **转述**给我的」 | `shadow()` efun，本项目的 mudlib 有整个 `shadow/` 目录 |
| 「regexp 套件是 Henry Spencer 做的」 | 后来被 libpcre 取代 |
| 「Sean T Barrett 做了 `smalloc.c`」 | 后来被 jemalloc 取代，WASM 版又换回 dlmalloc（§041） |

注意第一条的动词是「说服」。**LPMud 一开始并不打算做成虚拟机**——
是有人说服作者多做这一步，而正是这一步让 mudlib 得以热更新，
让「driver / mudlib 分家」从一个文件组织方式变成一个运行模型。

**解决的痛点**：三个，而且每一个在今天都还是问题：

1. **协作**——写世界的人只要会 LPC，不必碰 C、不必有编译环境。
2. **热更新**——`update /d/city/inn` 就换掉一间客栈，在线玩家无感。
3. **隔离**——mudlib 写爆了是 LPC runtime error，driver 不会死。

第 3 点是本项目亲眼验证过的：§032 那批 mudlib 兼容性问题里，
`/adm/daemons/kuafu` 因为调用不存在的 `socket_create` 而**编译失败**，
driver 照常完成开机——只是那个对象不存在而已（`libs/lpmudname/NOTES.md`）。
换成把游戏编进 C 的架构，同一个错误是链接期失败，整台服务器起不来。

**踩过的坑**：这条分界线的代价，本书第三篇整篇都在写。
**driver 不认识 mudlib 的协议**，所以 mudlib 想加一个 opcode，不必跟任何人报备——
于是三个世代的方言各自加码，撞了 4 个号（§010）。
分家带来的自由度，同时也是「没有注册中心」这件事的来源。§043 会把这条因果讲完。

**设计对照**：

| 系统 | 游戏内容住在哪 | 改一间房要做什么 | 谁能改 |
|------|--------------|----------------|--------|
| **LPMud（1989）** | LPC 文件，driver 之外 | 存盘 → `update` | 会 LPC 的人 |
| DikuMUD（1990） | C 原代码 + 数据档 | 改 `.are` 数据档或重编译 | 有原代码与编译环境的人 |
| TinyMUD／MOO | 数据库内的对象，可在线编辑 | 在游戏里打指令 | 有权限的玩家 |
| 现代游戏服务器 | 通常也是「引擎 + 脚本」 | 热载脚本 | 脚本作者 |

第四列才是重点：**这个分法后来变成了业界常识**。
Unreal 的 Blueprint、Unity 的 C#、各种服务器的 Lua 层，都是同一个形状。
LPMud 在 1989 年就把它做完了，而且做到了「脚本层 = 整个游戏」的极端程度。

**优点 / 罩门**：优点是三十七年后，一份 1990 年代的 mudlib 还能在 2026 年的 driver 上跑起来——
本项目收录的 17 个 mud 就是证据。罩门是**兼容性责任全落在 driver 这一侧**：
mudlib 从来不需要声明它依赖哪个版本的什么，driver 只能尽量不要动到既有行为。
§035 会看到这笔帐最后是怎么算的。

**效益**：对本项目而言，这个分家决定了**逆向的着力点在哪里**。
ZJMUD 的协议不在 driver 里、不在任何 RFC 里，
它在 `include/zjmud.h` 这个 mudlib 文件里——一份 LPC 的标头档。
本书第二篇之所以能拿到 27 个 opcode 的中文注解，正是因为 1989 年那次分家
把「游戏的协议」留在了**可读的脚本层**，而不是编进 5.5 MB 的运行档里。

> 💡 君之一席话
> **把系统切成「几年才换一次的引擎」与「每天都在改的内容」，不是为了好看——是为了让改动的频率决定它住在哪一层；而一旦分对了，三十年后那份内容还读得懂。**

> 🔍 老手视角──真正的门道
> 分层架构人人会说，但 LPMud 的分法有一个常被忽略的细节：**它把「网络协议」留在了上层**。多数人设计引擎／脚本分层时，会直觉地把协议算成引擎的责任（它离 socket 最近），结果就是加一个字段要改引擎、要跟引擎团队排期。LPMud 反过来——driver 只保证「一条可以双向送字节的线」，在线跑什么由 mudlib 说了算。代价是本书第三篇那些撞号，好处是**协议可以用内容的速度演化**，而这正是那三个世代的方言得以出现的原因。可落地的做法：设计引擎边界时，把「这个东西改动的频率」画成一条轴，比「这个东西在技术上属于哪一层」更能决定它该住哪里——**频率相同的东西放在一起，才不会互相绑架**。

## 034　1992 年的改名风波 — MudOS 是怎么来的

**标签**：`#MudOS` `#分支` `#兼容性声明` `#开源治理` `#一手史料`
**证据等级**：🟡 一手史料（1992-08-28 `rec.games.mud.lp` 贴文，收在 `fluffos/docs/archive/History.MudOS`）

**起源**：本项目的 driver 是 FluffOS，FluffOS 说自己是 MudOS 的后继者。
那 MudOS 又是谁？这件事有一份**一手证据**：
1992 年 8 月 28 日，Erik Kay 在 `rec.games.mud.lp` 贴了一篇 190 行的长文，
标题就叫〈MudOS (long)〉。它至今原封不动躺在 FluffOS 仓库的 `docs/archive/` 里。

这种东西在逆向工程里的价值极高：**它不是后人整理的年表，是当事人在事发当下写的**。

**技术内核**：分支的成因，按贴文自己的说法有三条：

> we changed the name in the version string because
> (a) we're not compatible with standard 3.0 mudlibs.
> (b) we wanted a convenient version numbering scheme
> (c) we wanted to differentiate ourselves from being "yet another custom hacked lpmud driver".

(b) 这条特别有意思。他们原本的版号长这样：

```
3.0.53.A2.2
 └─┬──┘ │ └── 自己的第二层修订
   │    └──── A = American version（相对于 Lars 的官方版）
   └───────── 跟着 Lars 的版号
```

三个人在三个不同的地方各自改 code，挂在别人的版号后面往下加，
最后版本控制先崩溃了。于是他们**从 0.8 重新开始编号**——
不是 1.0，因为「我们知道还有一大堆要改才算做完」。

名字则是玩笑话变成的：他们原本在聊一个「driver + mudlib 一起发」的计划叫 mudos，
后来有人半开玩笑地提议把驱动叫做 “MudOS enhanced LPmud driver”，
觉得听起来还挺酷，就这么定了。再后来嫌太长，砍成 `MudOS driver`，最后连 driver 也砍掉。

**解决的痛点**：(a) 才是技术上的真理由，而且它的形状值得记下来——
**不兼容不是他们的目的，是他们的处境**：

> Our communications are done completely differently. The backend was completely
> rewritten to be more efficient, and to deal with socket efuns. Function handling
> was completely rewritten. Much of the internal storage was completely rewritten.

改到这个程度，还叫「Lars 的 driver 的一个版本」，只会让人拿旧 mudlib 上去撞墙。
**改名是为了让兼容性声明诚实**。贴文里抱怨的正是这件事：
「用我们 driver 的人一直在问为什么 compat mode 不能用」——
因为名字让他们以为可以。

**踩过的坑（1992 年的，不是本项目的）**：这篇贴文是在一场网络骂战里写的。
社群指控他们抢 Lars 的功劳、指控他们「不过是又一个魔改版」。
贴文花了三分之一篇幅回应人身攻击，结尾写着 “All flames to /dev/null.”

技术上的教训在中段：他们试过社群共治。
TMI 找了约十个人开会、开了两个月的布告栏收集意见——

> However, nobody really had the time to get together and work on the code. […]
> But to get *everyone* together to agree? That would be next to impossible,
> and the result would probably be crap.

**「开会的人很多，写 code 的只有两个」**——这句话在三十四年后读起来一点都不陌生。

**优点 / 罩门**：分支的优点是 MudOS 真的把 driver 往前推了一大截，
而且它的「batteries-included」路线（大量内置 efun、套件化）
后来成为中文 MUD 圈的事实标准——本项目收藏的 17 个 mudlib，
以及 `mudlibs.fluffos.info` 上那 199 个，几乎全部长在 MudOS 系的 driver 上。

罩门是**社群分裂**。1992 年之后 LPMud 家族再也没有统一过：
Lars 的 3.x 线由别人接手成为 LDMud，MudOS 走自己的路，Genesis 那边改叫 CD。
一份 mudlib 从此必须知道自己是给哪一支写的。

**设计对照**：

| 分支时的做法 | MudOS 的选择 | 后果 |
|-------------|-------------|------|
| 版号 | **重新从 0.8 起算** | 版号终于能表达自己的进度 |
| 名字 | **改掉** | 没有人再以为它和 3.0 mudlib 兼容 |
| 兼容声明 | **明说不兼容** | 承受一次骂战，但没有累积技术债 |
| 上游关系 | 全发行版里都挂 Lars 的名字 | 功劳归属与兼容声明分开处理 |

最后一列是这件事做对的地方：**「我们不兼容」与「这是他做的」可以同时是真的**。
骂战的多数混乱来自把这两句话当成同一句。

**效益**：对本项目而言，这段历史有一个非常实际的用途——
**它告诉你手上这份 mudlib 的年纪与血统**。
本项目收录的 lib 里，`is_killing(ob)` 声明成 `string` 却传 object（§032），
旧 MudOS 放行、FluffOS 不放行。看到这种错，你就知道这份 code 是在
「driver 对类型很宽松」的年代写的，而不是作者当时写错了没发现。
**知道 code 写于哪个年代，比逐行读 code 更快定位兼容性问题。**

> 💡 君之一席话
> **改名不是背叛，是诚实**——当你的东西已经和上游不兼容，继续共用一个名字，受害的是每一个以为自己在用同一个东西的人。

> 🔍 老手视角──真正的门道
> 这篇贴文最值得学的不是分支的技术理由，是**分支的沟通顺序**。他们先改了版号（解决自己的痛），再改名（解决用户的误解），最后才被迫解释动机（收拾社群的情绪）。顺序倒过来的项目——先开大会宣布愿景、再谈兼容性、最后才发现版号早就烂掉——通常什么都没做成。老手看一个分支项目是否会活下来，第一个看的不是它的技术路线图，而是**它敢不敢在版本字符串里写「我和你不一样」**：敢写的，它的兼容性声明可以信；不敢写的，你得自己一个一个试。可落地的做法：任何 fork 的第一个 commit 就把 identity 改掉（名字、版号、`--version` 输出），这比任何 README 上的说明都有效——**因为用户不读 README，但一定会看到版本字符串**。

## 035　四条血脉 — 从 1989 到 2026，以及兼容性的价钱

**标签**：`#FluffOS` `#LDMud` `#DGD` `#兼容性` `#技术债` `#长期维护`
**证据等级**：🟡 FluffOS 官方 README／文档 ＋ 🟢 本项目实测（17 个 mudlib 的兼容性落差）

**起源**：本项目为什么能把一份 1990 年代末的中文 mudlib，
丢进一个 2026 年编出来的 WebAssembly driver 里跑起来？
答案不是运气，是**有人花了三十年守着一个兼容性承诺**。

**技术内核**：LPMud 家族的四条主线：

| 年份 | 名称 | 谁 | 定位 | 与 LPMud 的关系 |
|------|------|-----|------|----------------|
| 1989 | **LPMud** | Lars Pensjö | 原型；driver/mudlib 分家；Genesis mudlib | 本体。官方线走到 2.4.5 / 3.x |
| **1991 末** | **CD** | Johan Andersson 等（Chalmers Datorförening） | **为 Genesis 量身维护**；至今仍在跑 1989 年那个世界 | 从 Lars 的 3.0 开发版分出。**分家比 MudOS 还早** |
| 1992 | **MudOS** | Erik Kay、Truilkan、Jacques 等（TMI） | 「batteries-included」分支，大量 efun 与套件 | 从 3.0.5x 分出，**明说不兼容** |
| 1993 | **DGD** | Felix “Dworkin” Croes | 极简内核、完整持久化、原子函数、JIT | **概念衍生，非代码衍生**——重写的 |
| 1997 | **LDMud** | Lars “Mateese” Düning | 接手 3.2（Amylaar driver）并现代化 | LPMud 官方线的延续 |
| 至今 | **FluffOS** | 社群 | MudOS 的现代化延续：C++、跨平台、CI、**WebAssembly** | **保持与 MudOS 兼容** |

> **这张表只给定位，不给技术细节。** 五支 driver 在 apply／周期机制／安全模型／
> 持久化／intermud 上做了**方向相反**的选择——完整的技术对照在**第十篇 §063–§065**。
> 那里也有一份文献化石：**CD 与 FluffOS 各自封存的 `CREDITS`，
> 开头一字不差，然后在 1991 年分家处各自往下长了十年。**

五条线里，只有 FluffOS 把「兼容」写进了自我定义：
官方 README 的说法是 *“the modern successor to MudOS”*，
并明列 *“Full backward compatibility with existing MudOS code”*。
这句话就是本项目 17 个 mudlib 能跑起来的全部理由。

FluffOS 在保持兼容的同时换掉的东西不少：

| 面向 | MudOS 时代 | FluffOS 今天 |
|------|-----------|-------------|
| 语言 | C | C++（`src/` 全面 C++、clang-format/clang-tidy） |
| 事件循环 | `select()` 手写循环 | libevent（WASM 版换成 host 驱动的 tick，§040） |
| 内存 | `smalloc` / `wrappedmalloc` | jemalloc（WASM 版 dlmalloc） |
| 字符串 | byte 字符串 | **UTF-8 原生 + ICU**，含 EGC（延伸字素集群）感知 |
| 整数 | 32 比特 | 64 比特整数与浮点 |
| 网络 | telnet | telnet + **WebSocket + TLS**，IPv6 |
| 数据库 | — | SQLite3／MySQL／PostgreSQL，线程池异步 |
| 平台 | Unix | Linux／macOS／Windows(MSYS2)／Alpine／**WebAssembly** |
| 品质 | 靠用户回报 | GTest 单元测试 + `testsuite/` 的 LPC 集成测试 + GitHub Actions |

**这张表是本书 §032 那八条修正的背景**。兼容不是无缝，是**有价的**。

**踩过的坑：兼容性的价钱，本项目付了八次。**
§032 列了修正清单，这里补上它们各自对应到上表的哪一格——
**每一条落差都是「三十年来某样东西被收紧」的痕迹**：

| §032 的症状 | 背后被收紧的东西 | 属于哪种兼容性债 |
|------------|----------------|----------------|
| `master.c` syntax error（`static` 修饰词） | LPC 语法：`static` 语意含混，FluffOS 改用 `nosave`/`protected` 并提供 `__SENSIBLE_MODIFIERS__` 分岔 | **语言层**：旧语法被移除 |
| `is_killing(ob)` 声明 `string` 却传 object | 类型检查：旧 MudOS 放行，FluffOS 不放行 | **语言层**：检查变严 |
| `is_chinese()` 逐字节判断失效 | 字符串模型：byte 索引 → **码点／字素索引** | **运行期语意**：同一段 code 意思变了 |
| `valid_write` 找不到 SECURITY_D 就拒绝 | 安全模型：无 uid 环境下的缺省 | **环境**：不是 driver 变了，是跑法变了 |
| `log_file("static/logon")` 找不到目录 | 文件 I/O：不再自动创建中间目录 | **运行期语意** |
| 设置文件名 `config.ini` / `config.hell` 不一 | 没有惯例可循 | **生态**：从来就没统一过 |
| config 里写着 `c:\hell` 绝对路径 | 原营运者机器的残留 | **封存品质**，与 driver 无关 |
| `external_port_1` 决定编码分支 | WASM 版的来源端口规则 | **移植层**（§041） |

**八条里只有三条是「driver 真的改了」**，其余是环境、封存与生态问题。
这个比例本身就是结论：**一个宣称兼容的 driver，三十年下来真的只欠你三件事，
其他都是你自己那边的问题。**

**优点 / 罩门**：优点是**时间轴上的可携性**——一份没人维护的 mudlib，
在原作者消失二十年后，还能被别人跑起来、看见它当年长什么样。
本书收录的 `mudlibs.fluffos.info` 那 199 个中文 mudlib 就是这件事的规模化版本。

罩门有两个。其一，**兼容性承诺会冻结错误**：
`sscanf("%s %s")` 那个和 C 不一样的语意（第二个 `%s` 吃掉剩下全部）
是 1989 年的设计，今天所有人都得继续忍受它，因为改了会坏掉几千个 mudlib。
其二，**兼容不等于等价**：本项目 17 个 lib 全部「跑得起来」，

**效益**：对逆向工作的直接效益是**断代**。
拿到一份陌生 mudlib 时，先看它踩到上表的哪几格，就能推它写于哪个年代、属于哪一支血脉；
知道血脉，就知道该去哪份文档找 opcode 语意、该预期哪些 efun 存在。
本项目 17 个 lib 的导入之所以能从「不可行」变成「几分钟」，

> 💡 君之一席话
> **兼容性不是一个布尔值，是一份帐单**——宣称兼容的人替你挡下了大部分的改动，剩下那几笔会直接寄到你桌上；先把帐单分类，再开始付。

> 🔍 老手视角──真正的门道
> 这一节真正的门道在「**谁承担兼容性**」。LPMud 家族把它全部压在 driver 一侧：mudlib 从来不声明自己依赖什么版本、什么 efun、什么语意，driver 只能尽量不要动。这个设计在 1989 年是对的（那时 mudlib 只有一份），在今天则造成一个很有意思的现象——**driver 不敢改，mudlib 不能改**（原作者早就不在了），于是兼容性由第三方（像本项目）在中间手动弥合。现代生态的解法是把契约明写出来：`package.json` 的版本范围、Rust 的 edition、C++ 的 `-std=`。它们的共同点是**让「我依赖什么」变成可读的数据，而不是靠跑跑看**。可落地的做法：任何要活过十年的东西，第一天就给它一个能声明依赖的字段——哪怕当下只有一个值。没有这个字段，十年后的维护者只能用本书 §032 那种方式：**跑一次、看它死在哪、修、再跑**，一个一个试出来。
